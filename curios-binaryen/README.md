# curios-binaryen

WebAssembly-level optimization for the Curios native product via a statically linked Binaryen: the build script builds a pinned Binaryen source release, which the task files pin and `cargo xtask` fetches, and the library exposes its optimizer over serialized module bytes, after `curios-wasm` encoding and knowing nothing about any Curios IR.

## Design

### Built from a pinned source kept beside the crate, cached outside Cargo's target tree

**Decision.** Binaryen's source is data of the task files, `[data.binaryen]` of `xtask/tasks.toml`: one release, its whole tree, and the digest of its files, which `cargo xtask` fetches before the first step of any run and keeps beside this crate, in `.artifacts/binaryen-<version>/` ([`xtask`'s README](../xtask/README.md#data-a-step-or-a-build-reads-is-fetched-at-its-version-checked-by-the-digest-of-its-files-and-kept-beside-what-reads-it)). The build script fetches nothing: where it holds no library for this build it builds the kept source with CMake in its `OUT_DIR`, and of what that installs only the static library is kept, in a locked, target-specific cache in `.artifacts/` beside this crate, not under `target/`, which every Cargo mode and feature set reads. A cache entry is valid only against a marker naming the Binaryen version, a hash of the build script itself, the target triple, and the C++ toolchain's own version string.

**Rationale.** An `OUT_DIR` is fingerprint-scoped, so every Cargo mode and feature set would repeat a build that takes minutes; the shared cache pays it once per target, and the lock makes concurrent invocations safe. The library is all a link reads, so CMake's build tree is scratch in the `OUT_DIR` of the configuration that builds. The source is kept, though a link does not read it, because a build that fetched would put a network client under this crate and need the network whenever its cache missed, a toolchain's upgrade among the causes: kept, every build after one `cargo xtask` run is offline, at the price of the source's tree in each checkout. Beside the crate, `cargo clean` stays ordinary and no build script reconstructs Cargo's undocumented layout: `CARGO_MANIFEST_DIR` is an interface, `OUT_DIR`'s ancestry is not. Hashing the build script makes a changed CMake flag invalidate warm caches with no step to remember, and the toolchain string closes the other half: the entry's path carries the triple, so an architecture cannot be confused, but two machines of one triple on different distributions produce incompatible libraries under identical paths — beside the crate, one `rsync`, shared checkout or restored CI cache away.

**Rejected.** A hand-bumped `BUILD_SCHEMA` constant, correct and forgettable: nothing but memory connects a changed flag to the bump, so one commit could link a library built with old flags here and new flags on a cold machine. The library itself in `OUT_DIR`, built again by every configuration, after every `cargo clean` and in every worktree. CMake's build tree and the archive kept in the entry, which neither a link nor a later build reads. The source fetched by the build script where its cache missed and never stored: a build that reaches the network.

### The last stage, over bytes

**Decision.** Binaryen runs last, over the serialized module `curios_wasm::to_bytes` writes, and this crate knows nothing about any Curios IR. Semantic optimization belongs to `curios-anf`'s and `curios-cps`'s optimizers. What Binaryen makes of the module is good to have and no more: nothing the compiler guarantees rests on it, and a measurement of the pipeline is taken over the module it is handed. It stays a target of measurements of its own, since the module the compiler emits is written to be friendly to it.

**Rationale.** What a program means is held in the IRs above, so a rewrite that needs it is written where it is known; Binaryen's passes need only the module, and taking it as bytes keeps the library behind one seam that names no Curios type. The module it is handed is the last one the compiler controls, so a guarantee or a figure resting on Binaryen's output would move with Binaryen's version rather than with the compiler.
