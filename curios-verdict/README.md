# curios-verdict

The cabinet as a compilation sees it: the `Cache` the fold consults for units already judged, and the payload family an invocation consults before compiling a program it has already compiled — both believed on a verified record rather than on an address. The cabinet's families belong to `curios-package`, the addresses filed under them to this crate, what a stored unit is to `curios-unit`, and why believing one is sound to [Cached verdicts](../documentation/design/soundness/cached-verdicts.md) and [Reused payloads](../documentation/design/soundness/reused-payloads.md); the mechanism belongs to the crate rustdoc.

## Design

### Beside the pipeline, over the package, and under neither

**Decision.** This crate depends on `curios-pipeline`, whose `Cache` trait it implements, and on `curios-package`, whose cabinet layout it reads and writes through; neither holds the implementation, and the addresses a unit and a payload are filed under are this crate's, beside the record each is verified against. It links no back end: `cargo tree -p curios-verdict --edges normal` contains neither `curios-binaryen` nor `curios-native`, and the one machine-dependent fact a payload's header carries, the engine that will run it, is handed in by the crate that owns the runtime.

**Rationale.** `Cache` in `curios-package` would make the crate answering what is in a compilation depend on the driver that folds stages over the answer; in `curios-pipeline` it would make the pure fold name a manifest. The `wonder` engine reads verdicts for every question it answers and links neither Binaryen nor Wasmtime, and a cabinet read has no use for either. `curios-package` depends on `curios-module` and so links Curios's tree, its lowering and `curios-core`; the dependency this boundary keeps out is the driver's.

**Rejected.** The implementation in `curios`, handing the `wonder` engine a `dyn Cache`, whose trait cannot keep a unit without filing it; computing the engine fingerprint here behind a feature, which unifies across a workspace build and puts Cranelift under every consumer.

### A disagreeing object is a baseline, for a question and for a build

**Decision.** `Verdicts::earlier` hands back an object's unit when the object is intact, whatever the files it names and the units before it hold now, another project's object for a package of the same name among them, and says which units of the fold contain what the object's record names them by (`curios_pipeline::After`). The cabinet's own `Cache` offers the fold the nearest earlier compilation of a unit as its baseline — what an attached session last had in hand for it, then that object, then the same two of the unit compiled for the other kind, built or tested (`curios_module::UnitSource::other`), then what the scope offered — and the `wonder` engine's cache asks it for the same answer, so `run`, `compile` and `test` compile a moved unit over its baseline as a question does, and file it. What a question compiled over a baseline it files as it files what it compiled whole: it asks `Verdicts::taken_on_disk`, and files where the disk holds every text its fold has read.

**Rationale.** A unit compiled over a baseline is stored as the index a whole compile of the same text stores, naming the same blobs ([A stored unit is a baseline for an item-level recompile](../documentation/design/compilation/a-stored-unit-is-a-baseline-for-an-item-level-recompile.md)), so the object is the one a whole compile would have written whichever command wrote it, and the next baseline is no further from a whole compile than the last. No verdict a build files rests on what the elaborator kept: which of a baseline's verdicts stand is the certifier's decision, from the reads its own walk filed ([Cached verdicts](../documentation/design/soundness/cached-verdicts.md)). A baseline is offered whatever moved before it, since what a declaration read of another unit is asked again by the stage that read it, by the digest it recorded, wherever that unit is not the one the record names.

**Rejected.** A build compiling a moved unit whole, and withholding what a question compiled over a baseline, for the reasons [A stored unit is a baseline for an item-level recompile](../documentation/design/compilation/a-stored-unit-is-a-baseline-for-an-item-level-recompile.md) gives.

### An entry's unit is filed by the executable it is, and a handle with no cabinet keeps for its session

**Decision.** A handle is told which executable the entry its fold ends in is (`Verdicts::executing`), and files the unit of that entry's own declarations under `entry_address`: the package's name and the executable's, and what it declared. A handle told of none files no entry's unit. A handle with no cabinet behind it (`Verdicts::kept_by`) reads and files nothing, and keeps in its session what its fold compiles, each unit told from another by the prefixes it claims and where it reads from.

**Rationale.** Every entry claims the empty prefix, so a unit's address would file every program of a project in one place, each overwriting the last. What tells two entries apart is what tells their payloads apart, the one identity in a compilation that cannot collide. A file no package declares has no project, hence nowhere to file a unit, and a session asking about it at every keystroke still has the last unit it compiled of it: a kept unit is believed on what a recompile over it asks again, which needs no cabinet ([Cached verdicts](../documentation/design/soundness/cached-verdicts.md)).

**Rejected.** The entry's path as its identity, which keys a unit on where a project sits and not on what it builds. A cabinet beside a loose file, a generated directory nobody pointed the compiler at.

### An address names what a unit is, and a cabinet keeps one compiler's objects

**Decision.** An object's address names what its unit is — its mounts or its executable, what it declares, its kind, and the archived root it stands in for (`unit_address`, `entry_address`) — and a payload's its package and executable (`payload_address`), its object holding one file for each target; neither names a compiler. An object lies under the compiler that filed it, in the directory of the family that bears the compiler's identity (`curios_package::Cabinet::objects_of`), and a compiler reads, counts as held and merges what lies under its own name alone. A cabinet keeps one compiler's objects: a filing takes away every other compiler's directory whole and says nothing of it, so a switch of compiler compiles each unit again. No file names its compiler: what another compiler filed lies under another name and is never opened, so it is neither a hit nor a baseline and nothing of it is decoded. A native payload's record names the engine it is machine code for, and one filed for another engine is a miss, decided before the payload is read. An object keeps the record its last filing replaced beside its own, `replaced` beside `unit`; a hit, a baseline and the candidates a compile takes come from either, the newer first, and a candidate only where one of them names its blob (`Offered`).

**Rationale.** What a compiler files is laid out as that compiler lays it out, and a blob's name does not always say so: a blob stored whole is named by the digest of its bytes and reads alike whoever wrote them, where a member of a run is named by the digest of its form archived alone and stored in a table of its writer's layout. Packs every compiler shares count such a member as held for a compiler of another layout, which names it in its own record and reads the run as its own. Under its own name a compiler meets none of another's, with no lock and whichever of two files first: a filing that stopped short, and two filing at once, leave nothing a third reads. One compiler's objects are kept because a cabinet is one compiler's at a time: a change of compiler is rare outside the compiler's own development, what it costs is a compile and never a belief, and every compiler's objects kept would leave most an object no reader comes back to and nothing to collect it, as Cargo keeps every compiler's artifacts side by side, its version hashed into their names, and leaves their collection to an outside tool ([cargo-sweep](https://github.com/holmgr/cargo-sweep)). The address names no compiler, so one statement of a unit's place serves every compiler and stays the unit's own through every edit. A record another build laid out differently is never decoded, nothing under another compiler's name being opened, where rustc's incremental cache reads a header ahead of each of its files and discards a mismatch ([`file_format.rs`](https://github.com/rust-lang/rust/blob/master/compiler/rustc_incremental/src/persist/file_format.rs)): a directory's name says once what a header says in every file. Keeping the replaced record lets an edit undone hit the record it replaced.

**Rejected.** Packs shared by every compiler filing at an address, a blob two compilers make alike stored once: sound of a blob stored whole, and not of a run's member. The last two compilers' objects kept, so that two used in turn each hit their own: twice the space and a rule for which to keep, for a use a cabinet does not have. A mark in the cabinet naming the compiler its objects are, and the objects cleared where it differs: it holds only while no two compilers run at once, and a compile holds its view of the cabinet for its whole run, so an editor's server and a terminal of two compilers each file into what the other took for its own. The compiler in a pack's table, a run at a time, which the format, below the cabinet, cannot be handed, the prelude's image writing runs before its binary exists. The compiler in a candidate's name, which every stage that names or looks one up would be handed, a fact only the cabinet knows, and which the prelude's image, built before the binary that embeds it, cannot name. The compiler in `curios_unit::Record`, which the prelude's image writes before its binary exists and which a reader would decode before it could read whose record it is. A header ahead of every file naming the compiler that filed it, beside the directory that names it already: one fact in two places, and a read of each file to learn what its place says. A warning before another compiler's objects go, or a flag that lets them: nothing is lost but a compile, and a cabinet's state never fails one.

### An object's blobs are kept in packs beside it, at its address

**Decision.** An object is a directory of the cabinet, its address's own (`curios_package::Cabinet::object`). An executable's holds its precompiled payloads, one file for each target, each framed as a unit's file is. A unit's holds its record and its index in one file, `unit`, and the blobs the index names in packs beside it: each pack a file named by the digest of its bytes, closing on a sorted table of the digests it holds (`curios_unit::Pack`). A filing writes the blobs its address lacks, as the packs' tables say, in one pack, then the object, renamed into place, so an object never names a blob not yet written. A pack is held to its name the first time a blob of it is read, which vouches for every blob it holds, and one that is not its name is damaged and taken away, so what only it held is written again by the next filing that names it. The filing that writes a pack merges the smallest packs of the address into one, wherever each no longer holds at least twice the blobs of the one before it, the runs of each kind run again into one ([A compile costs what it reads](../documentation/design/compilation/a-compile-costs-what-it-reads.md), the sixth bound).

**Rationale.** An object's address names no unit before it, so it is a unit's address through every edit, and a unit's baseline is its own address's object, its other kind's, the unit a session holds, or the prelude's image: what an object names is in its address's packs once a filing there wrote what the image held, and no lookup asks across addresses, where a table of every pack in the cabinet, git's multi-pack index or restic's index files, would be one file every filer of a shared cabinet writes. Packs are written once and named by what they hold, as restic's are ([restic's design](https://restic.readthedocs.io/en/latest/design.html)), so two filers writing the same blobs write the same pack, and a merge never rewrites an object. Which blobs a pack holds is read off its end, so a filing reads no pack whole to know what it lacks, and a compile finds the candidates filed for what a declaration was lowered to by the prefix their names share, read out of each pack whose table names one (`curios_common::Candidates`).

**Rejected.** A family of payloads beside the objects, a file a target and an address: a second tree for what is put there as a unit's file is, a record ahead of what it vouches for, replaced whole, with a pass of its own in every collection. An index naming the pack each blob is in, which makes what a unit stores follow the order it was filed in. A family of unit files beside a family of pack directories, one address in two trees, which a collection and a restore probed apart and an object's staging stood outside of, as Cargo's build directory groups by content type where its layout v2 gives each cacheable unit a self-contained directory ([Call for Testing: Build Dir Layout v2](https://blog.rust-lang.org/2026/03/13/call-for-testing-build-dir-layout-v2)). One directory of packs for the cabinet, which every filer of a shared cabinet lists and every restore probes. Merging only at a collection run now and then, which leaves the saves between two in hundreds of packs; merging every pack into one past a count, as git's `gc.autoPackLimit` does ([`gc.txt`](https://code.googlesource.com/git/+/v2.20.0/Documentation/config/gc.txt)), which writes the whole unit again.

### A filing keeps what its object's two records name, with no clock

**Decision.** Every filing collects its address (`Packs::collect`): it keeps the blobs its own record names and those the record it replaces names, writes again without the rest a pack at least half of whose blobs neither names, and takes away a pack neither names any blob of; and the smallest packs are merged, keeping what the two records name, wherever they are no longer geometric. A blob neither names, where its pack is less than half such, stays until it is, and no compile takes it, since a candidate is offered only where a record names it. A staging file of the object's directory, a unit file's or a pack's an interrupted filer left, is taken away a day after it was written (`STALE`), the one time the cabinet keeps. A read writes nothing.

**Rationale.** The two records an object keeps are what its readers can believe: a hit, a baseline and a candidate each rest on one of them, so a blob neither names serves no reader, and keeping exactly those leaves nothing to a clock. Two writers alternating at one address, as two checkouts sharing a cabinet are, lose nothing, since each reads a record of its own, and a filer naming a blob a filing beside it dropped reads a miss and never a belief. Rewriting a pack only once half of it went pays for every blob a rewrite carries with one that went, as restic's prune leaves a partly used pack alone up to its `--max-unused` ([Removing backup snapshots](https://restic.readthedocs.io/en/latest/060_forget.html)), where dropping each blob as it went would write again the pack a unit was first filed in, its largest, at nearly every filing of an editing session. So a candidate reaches one filing back: an edit undone before the next filing finds what was made of the text it brings back, and a branch checked out again past that is judged again.

**Rejected.** A time a collection first found a blob unnamed, the blob dropped five days after, as Go's build cache trims what went unused for five days ([`cache.go`](https://go.dev/src/cmd/go/internal/cache/cache.go)): it kept the candidates of texts filed before the last two, at the cost of a table of times beside the packs, a daily interval and a clock every test of it stood in for, and the two records serve the alternating writers it was kept for. A time renewed by reads, which never collects a dead blob of a unit in use, since every restore of the unit reads the packs it is in. Dropping each blob as it goes, which writes the largest pack again at nearly every filing.

### A project's own cabinet keeps what the project reaches

**Decision.** A filing command collects its project's own cabinet as it ends, once its filing is done whatever the filing came to, and the `wonder` server after a check that filed (`collect_project`). What it keeps is read off the project's manifests (`curios_package::Reach`): every package its governing root holds, each member an umbrella enumerates or the one package, with the graph each folds; an object for every unit of those graphs and for every executable's own declarations, built and tested; a payload for every executable and every test subject on every target; and every tree and foreign module the manifests pin. Everything else of the cabinet and of `.curios/` is taken away, an entry no family of the running compiler holds among it, so a layout a move leaves behind needs no migration; a name holding a dot is a staging, the extension or the prefix of what a filer, a fetch or a pin has yet to rename into place, and stays until it is a day old. Nothing is taken where the reach cannot be read whole. A run filing into a cabinet named for every project a run sees collects nothing, its project's own cabinet included, since it filed nothing there: the cabinet named is collected within each address, and of every other compiler's objects, alone, and what no project reaches stays in it until whoever named it clears it.

**Rationale.** A project's manifests are the one statement of what its compilations can ask the cabinet for, so what they do not reach serves no reader, and an address naming no compiler leaves nothing that only an age could find. A reach read in part, a manifest refused or a tree not yet curated, would take away what the part not read reaches, so a partial read takes nothing. Collecting as the command ends keeps every handle what it was, one input fewer than a reach handed to each, and costs one read of the manifests a command; a check that filed nothing has moved nothing to collect, which spares a keystroke. A run knows its own project and no other, so a cabinet several projects file into cannot tell what none of them reaches. A compiler from before a move of the layout loses its cabinet at every run of a later one in the same project, and rebuilds it, since nothing tells a layout in use from one left behind: a move is rare, and what it costs is time, never a belief.

**Rejected.** A handle handed its project's reach as it opens, collecting after each unit it files: an input every handle carries, a question's among them, for a collection a command needs once. Each project filing its reach in a shared cabinet under a name for its root, a collection keeping the union of the projects whose root still exists, as Nix keeps a closure while its root link resolves ([gcroots](https://nixos.org/manual/nix/stable/package-management/garbage-collector-roots)): a registry of roots beside the families, against a cabinet whoever named it can clear whole. A build's product for an executable the manifest dropped, which is what a command emitted beside the project and not what it keeps for reuse. Sparing an entry no family holds while something in it was written within some period, which keeps an older compiler's layout while it is in use: a second clock, and a walk of each such entry at every collection, for two compilers on either side of a move.

### A history is walked over a cabinet of its own

**Decision.** `test_support::History`, behind `test-support`, walks units one step at a time as builds walk them, for the soundness board. Each step writes a unit's text, a program or Core text, into a temporary directory and builds every unit over the prelude and the units before it, through a fresh `Verdicts` over a cabinet of its own, which no build reads, so a unit's later step is compiled over its earlier one as the cabinet offers it, as a recompile is over its baseline. A program step is compiled by the fold a build runs; a Core-text step is read and compiled where a program is lowered and elaborated (`curios-pipeline`'s `compile_read`), its source reading its `.crsc` file so the cabinet keys and verifies it as any text. `built` hands the prelude and every unit to what the history closes with.

**Rationale.** A proof of `False` through a blob one walk filed and a later walk read is put only by walking the cabinet a build walks, so a history walks it, and a cabinet of its own keeps what it writes from every cabinet a build reads. What a history reaches is what a build reaches: every record in its cabinet is one a walk filed, whole, as [the soundness board](../documentation/design/soundness/the-soundness-board.md) holds a believed record to be.

**Rejected.** Handing a step's earlier unit to the next as its baseline, past the cabinet: a unit read from Core text would never be mounted as a build mounts one. A record written back with a verdict dropped, added or altered: bytes no walk wrote, outside the claim, and a unit the certifier would read as its construction bug. A refused program step's error carried out to the board: a build reports a refusal as text, and carrying the error out would put in the compiler what only the board reads.
