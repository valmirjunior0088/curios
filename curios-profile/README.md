# curios-profile

Programmatic profiling for the workspace: the recorder of what [`curios-common`](../curios-common/README.md#a-span-is-this-crates-macro-not-tracinginstrument)'s `profile!`, `sample!` and `note!` instrument. `trace` and `install` are the two scopings of the subscriber that writes [Perfetto's trace](https://perfetto.dev/docs/reference/trace-packet-proto) as it happens, one packet per span boundary and event, a track for each thread; `fold` recomputes timings, allocation figures and magnitude distributions from that trace; and beside them stand the counting allocator a program installs and the instruction count a measurement reads. The trace's messages are generated from Perfetto's schema, which the build script fetches at a pinned revision and checks by its digest through `curios-download`, only the messages and fields the recorder uses. It is the authority for `libc` and for `tracing`'s subscriber ([One crate is the authority for one external concern](../documentation/design/one-crate-is-the-authority-for-one-external-concern.md)), and no crate that instruments depends on it, so the trusted base reaches none of it. What a packet holds and what a fold returns belong to the crate rustdoc.

## Taking a profile

Every build carries the instrumentation, and `--profile <PATH>` is what makes something listen. `cargo xtask profile debug <PATH>` runs `<PATH>` under the compiler with a destination and folds what the run filed, in debug, the build iterating already has, and `cargo xtask profile release <PATH>` measures the shipped compiler:

```sh
cargo xtask profile debug programs/hello_world.crs
```

The flag is not a mode, so it measures whatever the invocation does anyway — `run`, `test`, `document`, a package build — and it takes its destination rather than defaulting to one, so no path lives in the compiler. A stream is one file, whole: it grows for as long as its run records. A run nobody asked records nothing, which keeps every compiler a test spawns from filing anything; instrumentation nobody listens to costs one relaxed atomic load per span.

Nothing waits for the end: each packet is on disk before the step after it runs, so a compilation that hangs, overflows its stack or aborts loses nothing a buffer held, and the first write that fails ends the stream, so a disk that fills leaves a file read the same way. Ask `curios profile` of a killed run's file and its summary states the spans still open: the stack each thread was inside when the run stopped. A question the summary does not answer is asked of the file in [Perfetto's UI](https://ui.perfetto.dev), which opens it as a timeline, a track a thread, and answers SQL on its query page:

```sql
select name, count(*) as calls, sum(dur) / 1e6 as ms from slice group by name order by ms desc limit 20
```

The prelude is built by a build script, the compiler run over the standard library, and a build script takes no flag, so it records nothing. Its work is a crate's, `curios-prelude-build`, which a measurement among `curios`'s profile tests runs again under the recorder, filing the stream at `curios/.artifacts/prelude.pftrace`. `cargo xtask profile prelude` runs it and prints `curios profile`'s answer for the stream, which `curios profile` gives again, with any view:

```sh
cargo xtask profile prelude
```

The measurement is `curios/tests/profile.rs`'s `prelude_build_profile`, and its stream holds each root's elaboration, certification and erasure. It is a test of `curios` rather than a program of the build's crate because the prelude's image key reads every crate that crate's tables reach, and a recorder among them would elaborate `/std` again at every edit to it.

## Design

### Three questions, three tools

**Decision.** How much a run spends in the compiler's own terms — a stage, a pass, a declaration, a magnitude, a reason — is this crate's to answer. What a running compiler is doing now, how it got there and how often it calls a function is a debugger's: gdb stops or attaches to any build that keeps its symbols, and a breakpoint's hit count is an exact count of calls. Where time goes beneath and between spans is a sampling profiler's, `samply` over the kernel's performance events, which reads the guest's emitted functions through the map the engine writes under `--profile` (`curios-native`) and which a kernel at `perf_event_paranoid` above 1 refuses. A permanent span names a unit of the compiler's own work; a question about code no span covers is a debugger's or a sampler's, not a new span's.

**Rationale.** A span sees only what was instrumented, in the build that compiles it in, and says what a frame means; a stack sees every frame of the build at hand and nothing of what one means; a breakpoint counts any function exactly and costs a trap a call. A check that does not finish inside a certifier comparison tens of thousands of frames deep is a debugger's question at once, where no span stands, and what each frame was working on is the recorder's or a print's.

**Rejected.** Retiring the recorder for a debugger, which counts nothing a measurement reads and names no declaration; spans in every hot function, which makes the recorder a sampler paying a row a call.

### Profiling is configured in code, never from the environment

**Decision.** There is no environment-variable switch and no metrics API. What is instrumented is decided by the call sites, which every build carries; whether anything records, and where, is one argument at the call site — `curios`'s `--profile <PATH>`, or a destination a caller hands `trace`. Nothing records unasked, a build script included: one takes no argument, so the work of the prelude's two is profiled by a program beside each that takes a destination. `trace` runs one operation under a thread-local subscriber, and `install` makes the recorder the process's global default, which a binary needs because its work is whatever subcommand the arguments selected and it has no closure to wrap; a thread-local `trace` still overrides the default for its closure. Stage entry points and optimizer passes carry permanent spans; a span added for one investigation is removed once it is answered.

**Rationale.** A measurement is already specified at its call sites, and an out-of-band specification could only disagree; an argument is that specification, in band and read where it is written. Carrying the instrumentation is no ask, since every build carries it, so a build script that recorded for carrying it would record at every lint and every test build, for nobody.

**Rejected.** Recording on every invocation: every `curios` a test spawns would file a stream onto one path concurrently. An exclusive lock on the stream, which makes an arbitrary process the winner, or a stream per process, which files one per spawned compiler, treat that symptom. A profiling subcommand, which could profile one synthetic compilation and nothing else; `curios profile` reads a stream back instead. A build script that records: it takes no argument, so the prelude's two would file their whole run at every build, read by nobody; and a variable to ask one by is the out-of-band specification this section refuses.

### Every build carries the instrumentation

**Decision.** The macros expand in every build, and `trace`, `install`, `fold`, the counting allocator and `Instructions` compile in every build, so `--profile` and `curios profile` are every compiler's, the one a user installs among them. No crate declares a feature for it.

**Rationale.** A span no recorder listens to costs one relaxed load and a compare, `tracing-core`'s maximum level standing at `OFF` until a subscriber raises it, and a sample's or a note's fields are evaluated only past it. The instrumentation as a build of its own costs more than it saves: what only its features compile takes a compilation of the workspace of its own at every check, a profile of a change compiles the instrumenting crates again, and the compiler a user installs can profile nothing. The node looks of `curios-core` count in every build for the same reason, a thread-local increment a look.

What every build pays is counted, in the user-space instructions a process and every thread and process it starts retire, so a loaded machine reads what a quiet one does. At `0c26dff30`, six release builds of one copy of the tree, made with features of that copy alone that set the macros, the look counter and the allocator apart and told apart by digest, each ran the prelude's build (the program `cargo xtask profile prelude` runs, its recorder taken out) and `curios compile -o` over the 31 programs of `programs/`, each with a fresh `CURIOS_CABINET`, under `BINARYEN_CORES=1 RAYON_NUM_THREADS=1`, read by a wrapper that opens `Instructions` and then starts the subject:

| | the prelude's build | the corpus compiled |
| --- | --- | --- |
| no instrumentation | 1,323,874,529,180 | 480,562,435,429 |
| the macros and their sites, over none | −0.22% | +0.05% |
| the look counter counting, over the macros | +0.31% | +0.01% |
| the allocator counting every allocation, over the macros | +3.42% | +0.53% |
| the allocator counting behind one relaxed load, over the macros | −0.78% | −0.06% |

One build repeats to 0.02%, and two builds of one source differ by up to 0.8% for being different binaries, which is how a build doing more reads below one doing less; only the allocator counting every allocation stands past it, by its four locked read-modify-writes. The release `curios` grows by 0.49% of its bytes and the browser bundle's module by 0.26%, and every program's executable and the prelude's images were one digest across the builds.

**Rejected.** A `profile` feature each instrumenting crate declares, the instrumentation compiled only where it is on: every cost the rationale names. The counting allocator counting in every run, which the allocator's own section refuses.

### Four instruments, because time and bytes cannot tell waste from bad inputs, and neither sees everything a stage does

**Decision.** Beside duration (`profile!`) and allocation (the counting allocator), `sample!` records a *magnitude* — how many, how wide, how deep — whose count, total, min, max and mean a fold reports. `note!` is the third call-site macro and measures nothing: it states why a decision went the way it did, on a path taken rarely — a solver giving up, a level defaulting, a candidate rejected. `Instructions` is the fourth instrument: the user-space instructions the thread that opens it retires, with every thread it starts afterwards, read by a measurement before and after what it measures and recorded at no span.

**Rationale.** A duration and a byte count are equally consistent with an operation that is wasteful and one handed inputs it should never have seen, and optimizing the wrong one buys a constant factor against something structural; the distribution of input sizes chooses the fix. A refusal nobody can explain is what sends a reader back to `println!`, and a note that fires on everything explains nothing. A count of looks or of bytes misses a walk that reads without allocating — a frame stack searched at every step — and everything that is not Rust, Binaryen's passes among it, where a retired instruction is what every one of them costs, counted by the processor: a reading on a loaded machine is the reading on a quiet one, which a duration is not.

**Rejected.** A `sample!` of a constant, a call counter in this instrument's clothes that the enclosing span already counts, and that drowns every other event of a stream. Instructions read at every span boundary: a read is a system call, and a span that runs per declaration would pay one each. An external crate wrapping `perf_event_open`: a dependency to pin and seal for one call, where `libc` names it.

### The library emits records, and aggregation is one of its consumers

**Decision.** `trace` writes one packet of Perfetto's trace per span boundary and event as it happens and nothing is summed in the process measured; `fold` recomputes the aggregate from the packets for every consumer that wants one. Each thread that records is a packet sequence and a track of its own, as Perfetto's own writer keeps one. The sequence's first packet states its track and the counter tracks its slices read as defaults, and declares an incremental clock, so no later packet names either and each is stamped with the step since the one before. A span's entries are slices on the track, its fields on each, names and string values interned once a sequence. The fold credits each slice's extent to the slice it was begun inside on its track, reports what a span kept for itself, in time and bytes, and `curios profile` summarizes it in one block: the ten span names that took the most time themselves, with their shares of it. Every other question — one call's arguments, what ran inside what, a timeline — is the trace's, asked in Perfetto's UI or by `trace_processor`. A stream is one file, a whole prefix of its run: the first write that fails ends it.

**Rationale.** A capture that returns its report can return it only once the operation ends, so the runs most worth profiling, the ones that hang, would produce nothing. Every aggregate figure is a difference of two slices' readings, and the packets keep what no aggregate holds: the order of events, the spans still open, and any question thought of after the run. A terminal is read at a glance, so `curios profile` answers with what a glance needs — where the time went and what a stopped run was inside — and leaves every listing to the tools made to browse one. An inclusive row counts every span entered inside it, which overstates work that re-enters itself, and the nesting of one thread's slices is what self time needs, so each thread keeps its own stack: the `wonder` server parses on its protocol thread while its analyst compiles, and one stack would credit either's spans to the other. Perfetto's trace is a format the standard tools read — `trace_processor`'s SQL and Perfetto's UI, a timeline a track a thread — where a format of the workspace's own is read only by a reader it writes. What a thread's packets share is said once on its own sequence, which one sequence for every thread cannot hold, since what is constant differs from thread to thread. A stream that stopped at a failed write is read as a killed run's is, up to its last whole packet, where one that went on past it would hold a hole the fold reads as whole.

**Rejected.** Rotating a stream at a size, to bound what an endless run writes. Every packet is flushed as it is written, so a run that hangs has filed all it did with no rotation, and what the bound cost was the head of every finished stream past it, dropped with nothing said: a count read from such a file was its tail's. Tab-separated rows of the workspace's own, read by its fold and by `awk`, every other reader the workspace's to write. One sequence for every thread, whose packets each restate their track, their counter tracks and a whole timestamp. One record an interval, written at its end, as rustc's `measureme` writes one, which halves the events and loses the spans a killed run was inside. Writing on past a failed write, which leaves packets missing from a stream's middle. `curios profile` listing every span by name and group, each span's costliest calls and what ran inside what as rows: thousands of rows for the prelude's build, and a copy of what Perfetto's UI and `trace_processor` read off the same file.

### Each thread counts what it takes while someone reads, and a program installs the allocator

**Decision.** The counting allocator, `CountingAllocator`, counts for each thread the bytes it takes and its trips through the allocator, and for the process its live bytes, their peak and the threads' totals. A slice carries its thread's two counts, written as steps on its sequence as Perfetto writes a thread's time, and the process's live bytes and peak whole, so a span is charged what its own thread took and what the process retained while it was entered. A program that reads the counts installs the allocator as its `#[global_allocator]`: `curios`'s binary, which records under `--profile`, the test binaries whose measurements read memory — `curios`'s suite and its `profile` tests — and this crate's own suite, so a test can hold a slice's readings to the allocation made inside it. A recorder asks once whether the allocator counts, and where it does not — a program that installed none — writes no readings, so a memory column of its stream reads `-` and never nought. It counts only while someone reads the counts — a recorder, `install`'s for the rest of the process and `trace`'s for its closure, or a measurement that asked with `count_allocations` — so its live bytes are counted from where counting began, and fall below zero where more was returned since than taken.

**Rationale.** Counted for the process alone, a slice carries what every thread took while it was entered: the `wonder` server's protocol thread allocates into the analyst's spans, and Wasmtime's, Binaryen's and Cranelift's pools into whatever span their caller has entered. A thread's counts are thread-locals initialized as constants with no destructor, which never allocate and are never torn down, so the allocator reaches them without re-entering itself. A block one thread takes another may return, so live bytes and their peak are the process's. Perfetto reads a counter written as steps only where one sequence writes it, so a thread's counts are steps and the process's gauges, which every sequence reads, are whole. A library that installs it puts it in every binary the library is linked into, the certifier's and the browser bundle's among them, where nothing reads a count; a program names the one static it reads. Counting is four atomic read-modify-writes an allocation, each a locked instruction on x86, and two thread-local additions; behind one relaxed load, a run nobody records pays the load alone, as [Every build carries the instrumentation](#every-build-carries-the-instrumentation) counts.

**Rejected.** This crate installing it in every binary it is linked into, which put it wherever the compiler is linked. Counting every allocation of every run, which every compile would pay for a count nobody reads. Counting for the process alone, which charges a span every thread's allocations. The process's gauges written as steps, which a reader of several sequences cannot sum.
