# `Prop` non-informativeness

**Assumes.** A `Prop`-sorted structure or concept carries only non-informative fields

**Status.** **probed**, in both checkers, and the two predicates deciding it held to each other differentially by `both_checkers_decide_non_informativeness_alike`. The rule is inert in production: the standard library declares no `Prop`-sorted structure, so the field loop never runs over it. The certificate idiom is why that is unsurprising rather than alarming — `/syn/Str` is a `Type`-sorted structure with a `Prop`-sorted *field*, which this rule does not restrict. The kernel's *refusal* fires in no surface program and exactly once anywhere, in this crate's own unit test, for the reason the entries above record. Both directions are therefore exercised, unlike the accepting excuse in the elimination guard, but only just, and never by the library. One clarification the row's own wording invites: "structure or concept" is two rules in the elaborator and *one* in the certifier, since a concept's record shape reaches this same gate — so the concept half needs no separate kernel coverage

**This row is about declarations, and one `Prop`-sorted shape has none.** An anonymous tuple type reaches no declaration gate, there being no declaration to reach it with; its non-informativeness comes from formation instead, a record being `Prop`-sorted only where no component pushed a level. That is the same claim the [Coverage](coverage.md) row leans on when it says the tuple arm carries no sort guard of its own — stated at the consumer and, until the [Sort formation](sort-formation.md) row above, nowhere at the producer
