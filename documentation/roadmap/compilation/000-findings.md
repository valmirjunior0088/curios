# Compilation: findings

- **Contify and sink each bind a continuation to keep a switch edge off a function's return, which the machine lowering lowers.** `contify_call` (`curios-cps/src/optimize/contify.rs`) binds a `return_bridge` continuation in every contified function, its body and scope two of the three nodes `CONTIFICATION_NODE_OVERHEAD` charges each loop-entry copy, so that the callee's switch edges to its return land in a continuation rather than on the call's, which may be the caller's own return; and `sink_computations` (`curios-cps/src/optimize/sink.rs`) binds an `arm` continuation where the operation it carves handed its result straight to the function's return. A switch edge to the return lands in a block of its own that returns (`lower_branch`, `curios-emit/src/machine.rs`), so both passes can retarget it as they retarget a jump. Fix: retarget a switch edge as a jump in both, drop the bridge from contify's scaffolding and its overhead to the one initial transfer, and restate `contifies_a_single_entry_tail_loop_and_bridges_switch_returns` and the extents the contify and specialize suites charge. Check: `curios-cps`'s suite and the corpus, `curios-prelude`'s tests. One commit.
- **Loop-entry separation takes one copy a round, and a whole test program pays a round of every pass for each.** `separate_loop_entries` (`curios-cps/src/optimize/contify.rs`) plans and applies one `LoopEntryPlan` a call, the first its function and site order finds, so each copy `ENTRY_CLONE_LIMIT` allows a module waits for the next round of `optimize` (`curios-cps/src/optimize.rs`), which runs every pass over the whole module. `curios test` in `curios-prelude/std` with no filter compiles the 291 tests `/std` declares as one program: at `af56540c5`, release with the `profile` feature over a cold store, one reading, `cps_optimize` converges in 71 rounds and the pass fires in 64 of them, its whole allowance, counted; it takes 127.2 s of the link stage's 384.5 s, about 1.8 s a round over a module of about 64,000 live nodes, timed, `flatten_indexed_lists` 40.0 s of it and `sink_computations` 20.9 s, firing in 4 rounds and in 23. Every round also builds the call analysis once for each reader [An optimizer query costs what its answer uses](202-an-optimizer-query-costs-what-its-answer-uses.md) counts. Fix: the pass discovers its candidates against one analysis and applies the independent ones in order, each spending the allowance, as [A pass applies the independent plans its snapshot admits](../../../curios-cps/README.md#a-pass-applies-the-independent-plans-its-snapshot-admits) states of the splitters and the specializers, and that decision names it among them. Check: `curios-cps`'s suite and the corpus, `curios-prelude`'s tests; `fixpoint_pass_measurements` (`curios/src/tests/instrumented/fixpoint.rs`) taken again for its rounds and the pass's firings; and that program's rounds counted again, since how many of the 71 the other passes need is not known until then. One commit.
- **Uncertain: a slot read twice on one path is taken for shared, and the zipper fixture loses its rebuilds to it.** `curios-cps/src/sharing.rs` counts two reads of one slot of one value on one path as aliases of one object, both shared, since a rebuild of either would show through the other. A zipper's descent reads its focus where only one arm uses it and again on the other, the first read dead on the path to the second, and the rule leaves it unrebuilt. Not known: whether telling a dead alias from a live one — the liveness of each read along the other's paths — admits it soundly, and what else it admits. Settled by: that rule, the hazard suite in `curios/src/tests/codegen/rebuild.rs` and a fixture reading one slot on two exclusive arms. Size unknown until then.
- **Uncertain: a map threaded through a closure is copied on every insert.** `/std/Map/union` and `Map/filter` insert into an accumulator `Node/fold` hands a closure, and a parameter an escaping function receives is shared, so those inserts never reach a version that rebuilds. Not known: whether the specializer makes those calls known in practice, or how often a program threads a map through a closure. Settled by: `cps-optm` of a program unioning two maps and filtering one, read for rebuilds in `Node/insert`. Size unknown until then.
- **Uncertain: what a rebuild's dead memory costs while it waits.** A rebuild writes into a value the descent before it took apart, so that memory stays held through the calls between, bounded by the depth of the descent. Not known: whether any program holds it longer than its descent, through a loop between the read and the rebuild. Settled by: the corpus's and the harness's rebuilds, each read for a loop between the value's last read and its rebuild. Size unknown until then.
- **Uncertain: what a mutable row costs beyond `/std/Map`'s node.** A slot some rebuild writes is declared mutable, which Binaryen no longer reads as the constant its construction stored and V8's collector charges a barrier on. Measured for `Node` alone, where it costs nothing measurable. Not known: whether any other row a rebuild reaches pays for it. Settled by: the corpus's and the harness's run times with that row's written slots mutable and with the rebuild of it suppressed, interleaved. Size unknown until then.
- **Uncertain: a whole test program hands Binaryen a module that one of its passes holds for most of the link.** `curios test` in `curios-prelude/std` with no filter, at `af56540c5`, release with the `profile` feature over a cold store, one reading, timed: 251 s of the link stage's 384.5 s pass between `compile_entrypoint`'s exit and `precompile`'s entry, which is `optimize` (`curios/src/compile.rs`), the module's encoding, its validation and Binaryen, against 1.3 s in Cranelift. The same run under `BINARYEN_PASS_DEBUG=1`, which runs each pass a function at a time, spends 646.7 s of its passes' 658.5 s in one run of `simplify-locals-nostructure`, the next pass 2.3 s. The plain run takes 444 s of processor time over 409 s, so a pass that takes a function a thread held about one thread, and one function is suspected of holding it. Not known: which function, what of its shape the pass grows faster than, its size, its locals or its nesting, and what builds it, the entry the optimizer inlines 291 tests into being one candidate. Settled by: the functions of the encoded module ranked by size and by locals, and the pass timed again with the largest kept apart. Size unknown until then.
- **A dispatch key past 32 bits is refused.** `narrow_case_key` (`curios-erase/src/eraser/intrinsic.rs`) refuses a `Nat` dispatch literal above `u32::MAX`, so `match n | 0 => 1 | 5000000000 => 2 | _ => 3 end` is refused with `natural dispatch key 5000000000 does not fit a branch table`, where a dispatch literal is any natural written whole ([Natural-number dispatch](../../language.md#natural-number-dispatch)). Fix: erasure keeps the keys that fit in the switch and tests the rest by `Nat` equality on its default edge. Check: a run matching a key past `2³²`, its neighbour and a small key takes each arm, and `NatCaseKeyOverflow` goes. One commit.
