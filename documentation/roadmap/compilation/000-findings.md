# Compilation: findings

- **Uncertain: a wide type alias costs its width in every declaration that reads it.** For `pub let T: Type = {Nat, …}` of width `w` and `w` functions `pub let f{i}(x: T) -> Nat = x.{i};`, each function's elaboration forces `T` to classify its parameter (`Sort::of_under`, `curios-elab/src/convert/sort.rs`) and to project `x.{i}` (`elaborate_proj`), the closed machine conses the alias's body into the declaration's table each time (`ClosedMemo::remembered`, `Sharing::share`), and the kernel classifies it again (`curios-cert`'s `Sort::of`): five of seven gdb samples at width 2 000 in the probe at `25125304c`. The anonymous-row materialization investigated separately by [An item materializes only what it reads of a row](103-an-item-materializes-only-what-it-reads-of-a-row.md) is another cause; this investigation isolates the alias reads. Every table lives one declaration ([A reduction step costs what it builds](../../design/soundness/a-reduction-step-costs-what-it-builds.md)), so what one declaration read of `T` the next reads again, and [Every stage but reduction costs the graph it is handed](../../design/compilation/every-stage-but-reduction-costs-the-graph-it-is-handed.md) has a declaration read a fact at a time. Not known: whether a declaration pays `T`'s width because a table forgets it, which the decision accepts as the budget's price, or because a projection and a sort read the whole type where they need one field and one sort. Settled by: the counted cost of one such function at widths 1 000 to 8 000, apart from the program's other declarations. Fix, if a read takes the whole: the field's type and the tuple's sort read off the alias's body by facet, as a structure's are. Size: unknown.

- **Uncertain: what the rebase's sequence monoids save, timed.** [A recursion closed by a monoid is a loop](../../../curios-ersd/README.md#a-recursion-closed-by-a-monoid-is-a-loop) makes a list, a run of bytes and a text built under their own recursion loops over accumulators. Read off the code, an element goes from a frame and three allocations to three allocations, and the first forcing of the left-leaning rope the accumulator builds grows a worklist to one entry an element. Not known: what either side takes in time, which waits on a quiet machine. Protocol: two release compilers, at `34f5e7600` and at `d8360a177`, each compile one program that builds a million elements by `List/range`, `List/zip`, `List/take` and a recursion over `Str/concat`, and reads each answer's length; five groups of five runs, the two variants interleaved inside each group and one untimed run opening each group; a variant's figure is the median of its group medians, and its span their least and greatest. Fix: the reading goes to the decision as its figure, named with its commit, and a slowdown its spans prove is a finding of its own. Check: the reading stated. Size: unknown.
- **Uncertain: a left-leaning rope's first forcing grows its worklist to the rope's depth.** `$<carrier>/force` (`curios-emit/src/rope_emitter.rs`) descends through `ForceWalk::push_uncached_node` (`rope_emitter/force_walk.rs`), which goes left and pushes every right child on an `$elems` worklist grown by doubling, so a rope that leans left — what `List/fold`'s builders and the rebase's accumulators build — holds one entry an element at its deepest, where a right-leaning one holds about one. Not known: whether the worklist costs anything a program notices beside the three allocations an element the rope already took. Fix, if it does: copy a flat right child in place at its offset and descend left without pushing it, which keeps the worklist small on either lean. Check: forcing a fold-built list of a hundred thousand elements grows no worklist past its first size, counted. Size: unknown.
- **Uncertain: a large run's room may want a taper.** [A flattening extends the payload its first piece wrote last](../../../curios-emit/README.md#a-flattening-extends-the-payload-its-first-piece-wrote-last) gives a payload room twice its run (`ForceWalk::place_first`, `curios-emit/src/rope_emitter/force_walk.rs`), so a run read, grown and read again holds as much room as run for as long as any run over its payload is held. SpiderMonkey grows a flattened string by 12.5% past 1 MiB and Erlang a binary by 20% past 16 MB, bounding a large run's room for a few more copies an element. Not known: whether a Curios program holds a run large enough for the room to cost it — a heap that must grow, or an allocation the engine refuses where the exact run would have fit. Protocol: one program that grows a `Bytes` to 256 MiB in 64 KiB arrivals and reads its first byte after each, run under `curios_native::test_support::collected` once as the walk stands and once with the doubling replaced by a 12.5% taper past 1 MiB, the peak heap read off the engine's last growth record and the collections counted. Fix, if the doubled run's heap is the one that grows: a taper past the threshold the reading names, in `ForceWalk::place_first`. Check: both runs' peak heaps and collections stated, counted. Size: unknown.
