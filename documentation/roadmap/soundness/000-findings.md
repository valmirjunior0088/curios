# Soundness: findings

- **The proof mark withholds a definition's value sort in the kernel and not in the elaborator.** [`curios_core::Definition::proof`](../../../curios-core/src/module.rs) states that a proof's body "is then read by its own check and by nothing after it: a judgment that asks what the name unfolds to is answered with nothing, in both checkers", and `curios-cert/src/kernel/globals.rs`'s `held` states the pairing that follows: the mark withholds the body and the sort that body inhabits together, as `define_as_stated` writes a proof, routing a marked definition to `Kernel::declare`, which inserts neither. `curios-elab` spells the two apart at four sites: `Context::publish` gates the body by the mark and records the value sort unasked; `established.rs`'s `definition`, the elaborator's one function a unit in scope answers for a name by, gates `body` and not `value_sort`, which is the shape `held` carried before it was fixed; `same.rs`'s `Parts::of` makes the body part move with the mark and never with the body, and compares the sort part beside it with no mark read; and `same.rs`'s `Question::Sort` digests the stated sort where the body part digests nothing. `Defined`'s own documentation states the pairing for `body` and not for `value_sort`, and the one reader is `convert/sort.rs`'s `Sort::published`, which the elaborator's irrelevance gate and its erased-position record ask before anything is run — the two consumers `declared_into_prop` and `erased_half` are on the kernel's side. So for a definition carrying both fields the elaborator answers a sort where the kernel answers none, a disagreement the kernel-side gate introduced, both having read the stated sort before it. Nothing reaches the field today: `proof_binders.rs`'s `value_sort` returns `None` for a marked definition and for any type not written as a sort, `proves` demands an authored definition so no former is marked, and a group's member states no sort — so only a caller in Rust builds a definition carrying both, and the elaborator is no part of the trusted base, where a program it admits and the kernel refuses is refused. What the unpaired reading costs where a writer does reach it is shown on the kernel's side, by the mutation check of `curios-cert`'s test of the pairing: with `held` restored to the unpaired reading, a unit in scope holding an alias marked a proof and stating `Prop` for a value that is `Nat` makes that alias a proposition to the irrelevance gate, and a coercion between two of its inhabitants is admitted with no verdict. The defect is the spellings, under what `.claude/rules/rust.md` asks of a value that only makes sense relative to another. Fix: state the pairing once where the fact is, as a `curios-core` accessor on `Definition` answering the body and the value sort together off the mark, which `held`, `Established::definition` and `same.rs`'s comparison and digest all read, so no later reader can pick a third pairing; `Defined::value_sort`'s documentation then states the pairing as `Defined::body`'s does. Check: `cargo test --package curios-elab`, `cargo test --package curios-cert`, `cargo xtask workspace lint` and `cargo xboard report`. Size: one commit.
- **Strict positivity and variance descend a declaration's parts with no `recurse` bracket, so a deep finite type dies rather than refusing.** [The soundness board](../../design/soundness/the-soundness-board.md) requires the Rust implementation to fail closed, a panic, an abort or a stack overflow being acceptable only where it refuses, and `.claude/rules/rust.md` asks of every walk over data-shaped depth that it recurse inside `curios_utilities::recurse` and work on the default test-thread stack. `curios-analysis/src/positivity.rs`'s `Walk::walk` and `curios-analysis/src/variance.rs`'s `Walk::walk` each descend into every child of every part of a declaration with no bracket in the cycle and nothing charged per level, the budget being spent only through `Env::force` where a `FuncType` is already a weak-head value. Both are in the trusted base and both run in both checkers: the kernel recomputes a module's vectors after walking its items and computes those of a mounted unit whose record files none, and the elaborator computes them when a group finalizes. Shown at `f2199702f` by a payload type that is a tower of five thousand arrows, `tower(0) = False` and `tower(k + 1) = (x : tower(k)) -> False`, declared to a kernel and put to `positivity_vectors` and to `variance_vectors`: each prints `has overflowed its stack` and aborts, `signal: 6`, on the default test-thread stack, and each answers with the bracket added. The depth is the kernel's as well as a test thread's, since `recheck` takes one `grown` segment for a whole walk and the same tower at four hundred thousand inside it dies as a bare `signal: 11, SIGSEGV` with nothing on stderr, where with the bracket it is answered in about one and a half seconds. Fix: put each walk's recursion under `curios_utilities::recurse`, as `Sort::of` was put at `f2199702f`, with a test of each tower beside the suites that drive those walks. Check: `cargo test --package curios-analysis`, and `cargo xtask workspace lint`. Size: one commit.
- **Uncertain: index inversion descends a pair of index terms with no `recurse` bracket.** `curios-analysis/src/invert.rs`'s `unify_index`, `unify_node` and `unify_all` are the shape the entry above shows dying: a mutual recursion over a pair of index terms, descending a variant's payloads and a tuple's fields, forcing both sides at each level, with no bracket in the cycle and no charge per level, since `whnf` returns a weak-head value before it spends. Seen by reading at `f2199702f`, beside the two walks shown there. Not known: whether a constructor whose index target is a deeply nested value reaches it, which no fixture has been built for. Settled by: building that target and putting it to `solve_indices`, which either dies, and the entry above's fix covers this site too, or refuses, and this is dropped. Size: unknown.
- **Two counts of a `rec` group are related by nothing, so a module built by hand aborts the kernel's walk rather than being refused.** [`curios-cert`'s README](../../../curios-cert/README.md) states that reduction is total on arbitrary terms, a projection out of range among the shapes that go stuck rather than assert, and that the counts no typing rule reads are checked where the declaration is consulted; [The soundness board](../../design/soundness/the-soundness-board.md) requires the implementation to fail closed. Neither count of a `RecGroup` is checked anywhere. `RecGroup::new` takes its member scopes without relating each scope's arity to their number, and `member_type` and `member_body` open each over one term per member, so `Scope::open`'s assert is the first thing that reads either; and while `Term::rec_proj` relates its index to the group's length, an instance of a member states the index on the node, where `Term::instance` relates it to nothing, so `RecGroup::item`'s `expect` is the first thing that reads that one. Both are Core terms a module built by hand carries, which `xboard`'s witness decision makes an input the board can put and which `Zonked::project` does not look at, reading the metavariable, transient and universe-metavariable gates and no count. Shown at `f2199702f` by two fixtures put to the whole-module walk: an instance of member one of a one-member group panics `recursive member index in bounds` at `curios-core/src/term/shape.rs`, and a group whose one member's scopes bind two panics `scope arity mismatch in `open`: expected 2, got 1` at `curios-core/src/scope.rs`. Fix: make each count unrepresentable or check it at the boundary — `RecGroup::new` relating every member scope's arity to the member count, and the member index checked where an instance states it, as `Term::rec_proj` already checks its own — with the row added to the README's boundary sentence, and each fixture then expecting a verdict. This part sets: it adds a row to a boundary the kernel's README enumerates. Check: `cargo test --package curios-cert -- recursion_tests`, and `cargo xtask workspace test`, since what the kernel refuses reaches every stage after it. Size: one commit.
- **Uncertain: a `rec` group's universe context has two readings, and the kernel picks between them by the position the group is met in.** `curios-cert/src/kernel/module.rs`'s `check_group` decides the group's own context, closed and satisfiable, and then checks its members under whatever constraints the kernel holds assumed, which it does not itself set. Reached from `infer`'s `Instance` arm those are the group's own, put there by `Kernel::under_universes`; reached from its `Rec` arm, which a bare `Term::rec_proj` is, they are the enclosing item's, and `under_universes` is not called. A level parameter is positional, so one spelling of a level means the group's own parameter under the first reading and the item's under the second, and nothing in `curios_core::RecGroup` says which — the same field is the group's own scheme where the elaborator spells a member at an instance, and the enclosing item's scheme restated where `check_rec_group` exports a member as a bare projection. Seen at `f2199702f` by a fixture the kernel admits with no verdict at all: the member `Type (param 0)` at its declared type `Type (param 1)` is well-sorted exactly where `param 0 + 1 ≤ param 1`, which the item grants and the group's empty constraint set does not, where the same group written at the instance spelling is refused, which `curios-cert`'s `recheck::variance_tests::one_spelling_of_a_level_is_judged_again_under_a_groups_own_context` holds as the right answer; the control, the group carrying the constraint its member needs, is admitted, so the fixture is otherwise sound. Not known: whether it reaches `False`. Three routes stop short — the instance spelling re-certifies the group under `under_universes`, so a group admitted bare is refused the moment it is written at an instance; `whnf`'s `step_instance` unfolds a stored body that is a bare projection through `RecGroup::instantiate_universes`, whose width check forces the group's parameter count to equal the instance's; and where a stored body merely holds the projection, `instantiate_universes_scoped` shadows the group's own levels and leaves them free in the reading item. Settled by: a witness put to `cargo xboard report`, filed open where the kernel admits it, the `False` it would reach being a type believed at a universe below the one it inhabits, which is type-in-type and Hurkens' route, so what is still owed is a judgment that reads such a level and admits rather than refuses. Where none is found, the reading is `curios-core`'s to state, a group's context being its own scheme or none and the two cases two shapes rather than one field read two ways, as [A rule is held by the grammar and the tree](../../design/a-rule-is-held-by-the-grammar-and-the-tree.md) asks. Size: unknown, and the narrow patch — `under_universes` around the `Rec` arm's `check_group` too — refuses what the elaborator produces, since `RecGroup::new` is monomorphic and only `RecItem::try_new` ever states a context, so every in-term group carries an empty one and a `rec` inside a universe-polymorphic definition whose member needs that definition's cumulativity would stop compiling.
- **The `rec` cycle guard both shared analyses use reads a member one level deep, and at one of its two spellings.** `curios-analysis/src/positivity.rs`'s `rec_member` is the guard of the positivity walk and of the variance walk, whose comments say a member the walk is already inside is left folded because forcing it again exposes the same node one level deeper and the descent would not terminate. It reads its member as an `Apply`'s immediate head and then asks `as_rec_proj`, and both halves depart from what `curios-core` states. `Term::spine_rec_proj` states the relation through every enclosing application and says why in as many words — that this, and not `as_rec_proj` on an application's immediate head, is what recognizes a folded recursive call, since a member whose result is a function is applied past its own parameters — and a family with both parameters and indices is applied in exactly two spines, while a mutual `induct` group's type constructors lower into a top-level `rec`. And `as_rec_proj` answers only for the `Rec`-node spelling, where `Term::has_group` states the relation as a `Rec` node or the member a universe instance is taken of, which is the spelling `d3fb81ca3` fixed one layer up in `obligation.rs` and the kernel's call recorder was fixed for in `xboard/src/totality/a_member_reached_through_an_instance_is_a_call_the_kernel_does_not_record.rs`. Shown at `f2199702f` by putting all five spellings of one member to the guard: `has_group` holds for every one and `spine_rec_proj` answers for the three `Rec`-node ones, while the guard reads three as no call at all — a projection applied in two spines, a projection at a universe instance, and that instance applied in one spine. `curios-analysis/src/totality/grade.rs`'s `readable` is the same cause at a second site, refusing a `rec` head by matching `Subterm::Rec` where its own `forceable` admits an instance, so the one shape its documentation names as refused is refused at the bare spelling and admitted at the instance one. Each consequence is the budget's, which is the refusing direction: a guard that does not fire leaves a walk forcing a path with no end until the driver refuses, and both walks then keep the refusal, so a declaration set is refused for the budget rather than quietly accepted. What the guard's own comment claims, that a walk which reaches one never meets it and so what it costs is nothing any declaration can observe, therefore holds only for the spelling it reads. Not known: whether a declaration set the walks accept today reaches a path the missed spellings leave unguarded, which would turn a quiet guard into a whole budget spent and a refusal naming no fault of the program's. Fix: `rec_member` asks `Term::spine_rec_proj`, which closes the two-spine half with no choice to make, in one commit. The instance half sets: `curios-core` states the containment over both spellings and states no head reader that sees the second, so closing it means either `spine_rec_proj` reading through an instance whose head is a projection, which moves what the restuck rule and `Sort::of` read and is a public contract, or a second reader beside it, which is one more relation stated twice. Two further sites share the cause and the sweep owes them. `curios-core/src/term.rs`'s `mentions_rec_member` asks `as_rec_proj` at each node of a walk, so a node spelled as an instance of a member answers that the member is not mentioned while it is, and the walk then descends into the group's member scopes where the occurrences are bound indices and nothing is found; it is the restuck rule's occurrence test at all three of its statements, the kernel's `finished`, the closed machine's `Frame::RecGuard` and the elaborator's reducer, and its own doc states the question as structural over a `Rec` node alone, which is the sentence that fails. Its reachable half is the value side, a neutral holding an instance of a member inside it, and the consequence is the one the kernel's own comment states for a guard that does not fire, a term growing one more copy of its body at every demand until the budget refuses. `curios-cert/src/kernel/whnf.rs`'s `forced_group` reads a folded term three ways and answers nothing for an instance, which is sound rather than a site — `step_instance` rewrites every instance of a member into the projection before any caller of `force` runs, so a fourth way would be dead code — and what is wrong there is the comment's count of a folded call's spellings. Not a site, checked and held: the closed machine's `Frame::Memo` keeps a folded spelling out of the memo by both readers, and its own `Instance` arm instantiates before any value is produced. Fix: `rec_member` asks `Term::spine_rec_proj`, `readable` and `mentions_rec_member` ask the relation `curios-core` states over both spellings, and `forced_group`'s comment says why an instance cannot arrive. Check: `cargo test --package curios-analysis`, with the demonstration restated to the guard that reads each spelling, and `cargo xtask workspace test`, since what positivity and variance decide reaches every unit the build certifies.
- **Uncertain: a model small enough to run locally can be the candidate oracle of a hunt.** [A probe asks the board's question of a program on no ticket](../../../xboard/README.md) puts a candidate to the checkers exactly as a witness and exits 0 where it is admitted, so a hunt needs of its oracle programs, not judgment: every ticket on the board was found by a frontier model under an agent, and nothing shown says the question needs one. Seen by the paper's review of 2026-10-24, as an observation on the discipline, not a measurement. Not known: whether a model small enough for one RTX 4070 Super, run on its own, produces an admitted candidate against a commit known to admit one (a fixing commit's parent, its ticket's witnesses withheld), how long it takes to the first, whether different models reach the same flaw or different ones, and so whether a hunt scales out to many small oracles rather than a few large ones. Settled by: a run per model, sequential on that machine, against that commit under a time cap, each candidate put to `cargo xboard probe`, the time to the first admission and the flaw it shows recorded; an admission within the cap restates this as a finding on the hunt's harness, and none within the cap drops it. Size: unknown.
- **Uncertain: the size order reads a proposition's own case as structure, which irrelevance leaves no room for.** [Totality of the erased program](../../design/soundness/totality-of-the-erased-program.md) reads what reduction took apart, and an arm's case is read for a `Prop`-sorted scrutinee as for any other (`refined_by_arm`, `curios-analysis/src/totality/grade.rs`), so a recursion descends on an inductive proposition's constructors. A match on a proposition fires with the proof unreduced ([`Prop` is strict, proof-irrelevant, and definitionally K](../../design/theory/prop-is-strict-proof-irrelevant-and-definitionally-k.md)), so the arm's payloads are no part of the value it was handed, and where `Prop` is a subsingleton a strict decrease between two proofs is a decrease in a one-element set. `curios-analysis/src/totality.rs`'s module doc defends the reading by finiteness — every payload is sized under its family, so none is applied at the family to hand a value of it back — which argues the payload tree is finite and not that the order respects the equality irrelevance imposes. Seen by `wonder diagnostics -` at `aaaf861d2`, which accepts an accessibility recursion with its predicate declared `Prop` and another with it at `Type`, against a control refusing a proof recursion with no descent. Not known: whether the reading reaches `False`. Agda restricted it and reverted it (`agda/agda` PR #6639, commit `cca1e0d`), Lean keeps it at the cost of a definitional equality Carneiro shows undecidable and non-transitive, and Felicissimo, Leray, Pujet, Tabareau, Tanter and Winterhalter (LICS 2026) answer the undecidability by unfolding an accessibility predicate propositionally rather than definitionally — a price Curios does not pay, since irrelevance decides a `Prop` comparison before either side reduces and a proposition holding a payload its indices do not pin eliminates into no data. Settled by: a witness put to `cargo xboard report`, filed open where the kernel admits it; where none is found the reading is the totality decision's to state, naming what the alternative costs — `/std` descends on a bound and declares no accessibility predicate ([`curios-prelude`'s README](../../../curios-prelude/README.md)), and a predicate declared at `Type` keeps the recursion while erasure retains its tree. Size: unknown.
