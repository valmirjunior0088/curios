# Lowering: findings

Small fixes and possible bugs, worked as one pass. Each entry names where, what is wrong, the fix, its check and its size.

- **A `Nat` shift by a count of `2³²` or more computes a different number.** `CodeEmitter::word` (`curios-emit/src/into_wasm/code_emitter.rs`) hands `big/shl` and `big/shr` their count through `big/word` (`big_emitter.rs`'s `emit_big_word`), which saturates every boxed value to `2³² - 1`; the saturation is licensed by the claim that no count reaches that value, which is false for a shift, whose result can. Compiled natively with the count read at run time, `Nat/shr(Nat/shl(1, k), k - 1)` prints `2` at `k = 4294967295` and `1` at `k = 4294967296`, where the answer is `2`; the mirror, `Nat/shr(Nat/shl(1, k - 1), k)`, prints `1` at `k = 4294967296`, where the answer is `0`. Each run takes about 1 GB. The checkers and Core's reduction shift exactly, so an accepted program gets a different number at run time, with no refusal and no trap, against [Nat and Int are an i31 until they outgrow it](../../design/arithmetic/nat-and-int-are-an-i31-until-they-outgrow-it.md)'s rule that a narrowing never hands a consumer a changed value. The decision already states the rule the code lacks: a shift's count, which a result can reach, is taken exactly, and a result past what the runtime can hold is refused. `Int`'s shifts take the same path. A switch key is safe from the same word, since `curios-ersd` decides a key at or past `2³⁰` by equality. Fix: hand both shifts their count as a 64-bit word saturating at `2⁶⁴ - 1`, which changes no answer since no magnitude has that many bits. A right shift is then exact and refuses nothing; a left shift refuses a nonzero value whose result needs more limbs than the limb array's `u32` length holds, and answers zero for zero whatever the count. The refusal is a new class in `curios-cont`'s `Panic` roster, a value past what the runtime holds, which the entry below shares, with its sentence in `refusal.rs` and its name in [A refusal is a panic the emitter renders](../../design/lowering/a-refusal-is-a-panic-the-emitter-renders.md); `curios-cont`'s `Repr` documentation and `code_emitter.rs` state the rule as the decision does. Check: both probes as a corpus test gated like the other gibibyte measurements, printing `2` and `0`, and an `intrinsic_tests` fixture that a shift's boxed count does not pass through `big/word`. Size: medium.
- **A sequence of `2³²` elements or more answers a wrong length, or stops on a bare engine trap.** A rope's length is an `i32` read unsigned (`curios-emit/src/into_wasm/types.rs`), and the helpers size in `i32`. `$bytes/to_bits` seals its leaf at `len << 3` (`emit_reinterp_func`, `rope_emitter.rs`), which wraps with nothing downstream to stop it: with the count read at run time, `Bits/len(Bytes/to_bits(Bytes/replicate(n, 0)))` prints `4294967288` at `n = 536870911`, `0` at `536870912` and `8` at `536870913`, in about 770 MB each, with no refusal and no trap. `$bits/replicate`'s `(count + 7) >> 3` wraps from `2³² - 7`: `Bits/len(Bits/replicate(n, true))` prints `4294967288` at `n = 4294967288` and stops at `4294967289` with `wasm trap: out of bounds array access`, and concatenating two runs of `2³¹` bits stops with the same trap in `bits/norm`. A count saturated at `2³² - 1` reaches the engine whole: `Bytes/replicate(4294967296, 0)` and a used channel of that capacity both stop on `wasm trap: allocation size too large`. The first is a changed value, against [Nat and Int are an i31 until they outgrow it](../../design/arithmetic/nat-and-int-are-an-i31-until-they-outgrow-it.md), whose saturating positions and counts rest on a bound nothing enforces; the rest are refusals that are no [panic the emitter renders](../../design/lowering/a-refusal-is-a-panic-the-emitter-renders.md). Fix: every constructor that sums or scales a length — `concat`, `append`, `replicate`, `to_bits`, `embed` — and a channel's creation refuse past `2³² - 1` with the class the entry above adds, and the i31 decision's narrowing clause states the bound its saturation stands on. An allocation the heap cannot hold stays the engine's to report. Check: the three probes refuse with the sentence, as a corpus test gated like the other gibibyte measurements. Size: medium.
- **`Function::droppable` licenses a deletion no pass performs, and dead droppable calls stand in every program.** The door computes it (`droppable_functions`, `curios-ersd/src/into_cont/lowerer.rs`): total, with no host effect, state read or write, exit, divergence or mutable allocation. `inline.rs` and `clone.rs` copy it, and its one reader is `sample_droppable_dead_calls` (`curios-cont/src/cps/optimize.rs`), compiled only under `profile`, which counts droppable calls still standing and those whose result the demand lattice reads as `Unused`; its documentation records `present` 7 over one program and `dead` never taken. Taken over `programs/`, the count is 5 for `hello_world` and `dependent_vectors`, 15 for `state_monad` and 14 for each of the other twenty-two. The protocol is a `profile` build, `echo 5 | curios --profile <stream> run <program>`, and the last `cont::droppable_dead_calls` value in the stream, which is the converged round's; the workload size is immaterial, since the sample is taken while compiling. In `hello_world` and `parse_digits` every one is `/std/Handle`'s `of_masks`, as `wonder stage cont-optm` shows: `read_waiting`, `write_waiting` and `flush_waiting` (`curios-prelude-archive/std/Handle.crs`) discard `poll`'s answer, so the readiness list is decoded after each host poll and never read — the case `droppable_functions` exists for, a list built and never read. About 150 hand-built functions in `curios-cont`'s and `curios-emit`'s tests spell `droppable: false`. Fix: splice a call whose callee is droppable and whose result is `Unused` to a jump, at the point of the round where the sampler stands, as [LLVM](https://llvm.org/docs/LangRef.html#function-attributes) deletes an unused call only where the callee is both free of effects and `willreturn`; the sampler and its reading go. The return continuation keeps its parameter, since `eliminate_dead_parameters` skips a return target, so the jump hands it an argument nothing reads, and what that argument is — `Atom::Filler`, which a reference slot admits, or the zero of the register a later round may raise the parameter into — is the one thing the splice has to settle. Check: the count reads zero over `programs/`, `wonder stage cont-optm` over `hello_world.crs` holds no call of `of_masks`, and every program's output is unchanged. Size: medium.
- **The multi-width tuple merge may be unreachable.** **Uncertain, and warrants investigation:** whether any program reaches it. `Origin::Constructed(BTreeSet<usize>)` (`curios-cont/src/cps/origin.rs`) merges the widths of the structural tuples reaching one value, and `fields.rs` travels such a region at the widest. The door pads every family construction to its row, so only structural tuples of different arities can meet, which only a type a large elimination computes allows. Such a program compiles and runs — `make(b) -> Shape(b)`, answering `(1, 2)` or `(3, 4, 5)` by a `Bool` read at run time — but the optimizer specializes each arm before any join carries both widths, and only `fields/tests.rs`'s hand-built fixtures reach the merge. `admit` (`fields.rs`) takes a parameter only where its demand is `Projected`, so the widths must meet at a join whose own body projects, and a polymorphic function, which could receive tuples of two widths, projects from neither. The library's types computed by elimination — `/std/Cli`'s `Carrier`, `Lookup` and `Claim`, `/std/Fmt`'s `format_type_with` — are where a program would reach it, and none is in `programs/`. Fix: count merged-width facts over the corpus, `programs/` and a `/std/Cli` program with a temporary `curios_profile::sample!`; at zero, keep one width per fact and delete the merge; otherwise name the shape that reaches it in `origin.rs`'s documentation, with a corpus fixture. Check: the count, then the corpus suite. Size: medium.
- **Branch specialization reads any literal first field as a tag.** **Uncertain, and warrants investigation:** whether the product and structural cases it specializes today pay for themselves. `tagged_tuple_values` (`curios-cont/src/cps/specialize.rs`), which `specialize_call_patterns` and `specialize_jump_patterns` read, takes a structural tuple or a row construction whose first field is a literal `Nat` and calls that field its tag, but only a variant family's row carries a tag at slot zero: a product row's first field is data, and a structural tuple has no tag. The specialization stays correct, since the literal is known, but what it reaches is arbitrary: a product whose first field is a literal is specialized, and one whose first field is computed is not. The pass names itself for [SpecConstr](https://www.microsoft.com/en-us/research/publication/system-f-with-type-equality-coercions-2/), whose pattern is the constructor application a callee takes apart, with no literal field selecting it: a product has one pattern, its construction, and `split_workers` (`fields.rs`) may already deliver that one. Fix: key the tagged case on a family row, and measure what the product and structural cases specialize over the corpus today, and what `split_workers` leaves for them; keep them only if they pay, keyed on the construction and under a name that says so. Check: `specialize_tests.rs`, and the corpus's `cont-optm` rungs. Size: medium.
- **CSE's debug assertion states the one-parent rule a second way.** `debug_assert_single_owner` (`curios-cont/src/cps/cse.rs`) counts owning links over every live node, while `Module::verify_function_body` (`curios-cont/src/cps.rs`) walks each function from its body and refuses a node reached twice. The two part on nodes no body reaches: an orphan, or a node linked from an unreachable one beside its own parent, fails the assertion and passes the verifier. Fix: factor the verifier's walk into one checker the assertion calls. Check: `cse_tests.rs` and the verifier's tests. Size: quick.
