# Tools: findings

- **A release ships no editor grammar.** The release workflow (`.github/workflows/release.yml`) attaches the three compilers, `curios-js.tar.gz`, `curios-docs.tar.gz`, `checksums.txt` and `install.sh`, and no grammar: the TextMate grammar (`editors/vscode/syntaxes/curios.tmLanguage.json`) and the tree-sitter grammar with its queries (`editors/grammar/base`, `editors/zed/languages/curios/highlights.scm`) are read from a tag's source or not at all. The website pins the compiler bundle it fetches to a release and would highlight Curios with the same release's grammar; its session reports the TextMate grammar loads unmodified in Shiki 3.23's JavaScript regex engine and tokenizes every Curios snippet the site holds. The fix: an archive of the editor grammars — the TextMate grammar, the tree-sitter grammar's `src/` and its queries — built by the release workflow and attached beside `curios-js.tar.gz`, so a grammar is a published contract of the release it came with. Check: the workflow run on a tag in a fork, and the archive's listing. One commit.
- **The language's words are listed four times, and nothing holds the lists together.** `KEYWORDS` in `curios-common/src/qualifier.rs` reserves eleven words, `true` and `false` among them; the TextMate grammar states keywords, contextual words and definition heads in its own patterns; Zed's queries capture thirteen as keywords (`editors/zed/languages/curios/highlights.scm`), the contextual `concept`, `satisfy`, `test` and `and` among them and `true` and `false` as booleans, held to the tree-sitter grammar by `editors/grammar`'s `npm test` and to nothing else; and `KEYWORDS` in `curios-document/src/pages/context.rs` sets nine apart in signatures. Some differences are deliberate — a contextual word is no reserved one, a signature holds no `match` — but no test says which, so a word added to the language reaches whichever list its author remembers. The fix: one statement of the vocabulary, the reserved words and each contextual word with the position it is a keyword in, beside `KEYWORDS` in `curios-common`, and a test reading the TextMate grammar, the Zed queries and the documentation's list against it, each difference stated where the test states it. The report roles of `curios-common/src/style.rs` — bold, dim, troubled, aside — are the same colouring's other half, which each consumer maps to its own palette. Check: the test, and a word taken out of one list failing it. One commit.
- **Uncertain: whether highlighting should come from the compiler's own parse.** Both editor grammars approximate the language — each takes a capitalized name for a type by convention — and the documentation sets words apart in signatures from a list (`curios-document/src/pages/context.rs`), where the formatter already parses a file with its comments (`curios-surface/src/format.rs`), so every token of a file is recoverable with its span and, from the tree, its class. A command emitting classified spans, `curios highlight` say, would be exact where the grammars guess, and could serve the documentation generator, the website's build and the editors. Not known: which classes a token takes and who names them, beside the vocabulary and the report roles above; what a file that does not parse is highlighted as; whether an editor would take spans from a command where it now runs a grammar incrementally; and what the browser pays, where the bundle the playground loads is no build a page would fetch to colour a snippet. Settled by classifying the tokens of `/std` and the corpus from the formatter's parse against what each grammar paints, which ends in a specification of the capability or in the grammars staying the answer. Size unknown.
