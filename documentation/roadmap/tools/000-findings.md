# Tools: findings

- **Uncertain: a failed assertion names neither where it was written nor what it asserted.** `Test/assert` (`curios-prelude/std/Test.crs`) fails with `the condition was false`, which `curios test` relays under the test's path, so a test that asserts twice gives its reader no way to tell which failed; `Test/equal` reports the two values and no place. A library function cannot learn where it was called from: an assertion is an ordinary call, `/std` has no macros, and a value carries no place. Not yet known: whether a parameter the compiler fills with the call's place at each call, as Rust's `#[track_caller]` with `Location::caller()` and Swift's `#file` and `#line` defaults do, fits beside `@` and `use`, which fill a parameter by unification and by resolution, and whether the written expression is shown too, as Rust's `assert!` and pytest's rewriting show it. Settled by a design for that parameter, which makes this a capability specification, or by a reason no assertion needs one, which drops it. Size unknown.
- **`wonder` writes Core text that nothing in the product reads back to the checkers.** `curios wonder --stage core` and `core-elab` reprint a program as Core text, whose writer states every field so that it reads back as the term it writes ([Core text is Core in the program's grammar, and reads back as the term it writes](../../../curios-surface/README.md#core-text-is-core-in-the-programs-grammar-and-reads-back-as-the-term-it-writes)), and `curios format` formats a `.crsc` file and the editors colour one, but no command checks one: `wonder` reads a `.crsc` subject as a program and refuses its first form, and the one door to the checkers is `cargo xboard probe`, a tool of this tree's that puts the text as a proof of `False` through the checkers' `test-support` puts, so the question an investigation of a checker asks — a dumped module, edited, under the certifier — needs the tree and a build of the board. Fix: a `.crsc` subject is read by `curios-surface`'s reader over the standard library and handed to the certifier as a unit read from Core text, its closing term, where it has one, judged at `Io({})` as a program's is: the check reports the reader's and the certifier's refusals at their places in the text, `--stage` reprints its rungs from `core-elab` on, and `--name` answers its declarations. `Unit::read` and the pipeline's `compile_read` leave `test-support` for it, and the board's probe reads its candidate through the same path. Check: the module `wonder --stage core-elab` prints for a program, read back by `wonder`, checks clean; a declaration the certifier refuses is reported at its place; report tests in `curios-pipeline` beside the program's. Size: a few commits.
- **Uncertain: no command answers in a terminal what a module exports, so a reader with the CLI alone cannot find the names a module offers.** A reader that works through the command line alone, as an agent does, finds a declaration it can name — `--name` prints its kind, its type, its prose and its text — and no way to learn the names it could ask about, the standard library's included. `curios wonder --name` answers a declaration's path, and at a module's path answers the declaration exported there, if any: `--name /std/Map` gives the `Map` structure, and `--name /std` is refused as an unknown declaration. `--declarations` answers a file the subject reaches on disk, which the standard library's never are, being archived in the compiler, and `curios document --std <DIR>` writes what each of its modules exports as pages to open in a browser. Peers answer it where the code is written: GHCi's `:browse`, Idris's `:browse`, `go doc` of a package and `pydoc` of a module print a module's names in the terminal, and a language server's completion offers them under a path. The answer is a query of its own, `curios wonder --exports <PATH>`, what a module exports, each with its kind and its head, as its documentation page lists them, beside `--name`, which keeps answering the declaration a facade exports at the same path. Not yet known: how private names and a module's submodules are shown, a reader inside the module's subtree reaching what one outside does not; whether the language server completes a path from the same answer; and what of it the documentation's record already holds, `curios-document`'s pages being read off it. Check, once designed: from the root down, every exported name of the standard library reached by queries alone. Settled by a survey of those peers and a design restating [`wonder`'s queries](../../usage.md#wonder) and the record they read, which makes this a capability specification, or by a reason a terminal needs no such answer, which drops it. Size: unknown.
- **Uncertain: the certifier's own verdict on a module the elaborator refuses is asked by no command of the product, so the compiler is probed for a proof of `False` only through the tree's board.** `cargo xboard probe` puts a program to the elaborator with its erasure obligations reported rather than raised, so a program only the elaborator refuses still yields a module the certifier judges, puts Core text to the reader and the certifier, judges the closing term at `False` at the board's step budget, and exits as a search does, 0 where a proof was admitted ([A probe asks the board's question of a proof on no ticket](../../../xboard/README.md#a-probe-asks-the-boards-question-of-a-proof-on-no-ticket)). Its **Rejected** paragraph keeps the question off `curios wonder`, since a closing term judged at `False` "answers about a compilation that would never be built, and ships a question about this tree's checkers in the product". The first ground is answered by a declaration: `let proof: /std/Bool/False = …;` is judged at `False` within a compilation that builds, which `wonder` checks through both checkers today, elaborator first; what no command asks is the certifier past the elaborator's refusal. The second is what peers do: Rocq ships `coqchk`, a checker of compiled libraries whose exit says whether every check held, and Lean ships `leanchecker`, a replay of an environment through its kernel, with every toolchain. Not yet known: whether `wonder` reports each checker's verdict apart, the certifier's over what the elaborator built where its refusals leave a module, under a query of its own or as part of the check; what the exit says where the certifier admits what the elaborator refused; whether the board's probe then becomes its tickets, its budget and its exit over that query, sharing the put so the two cannot drift; and what of the elaborator's reported-obligation mode the product may hold, `test-support` keeping it out of every shipped build today. Settled by a design restating the probe's decision and `wonder`'s queries, beside the entry that has `wonder` read Core text, which it needs. Size: unknown.
- **Uncertain: no manifest table says how a package's lints are reported, so `curios lint` holds every package to every lint alike.** [A lint is an exact finding read off the compilation](../../design/tools/a-lint-is-an-exact-finding-read-off-the-compilation.md) reports six lints, every one always on, with "nothing to configure", on the ground that "exactness leaves nothing to configure": a fact of name resolution has no false positive, so levels, groups, suppressions and `expect`, which manage heuristic rules over a legacy corpus, have nothing to do. That holds of what a v1 reports, and it says nothing of two questions a table answers. Which exact findings fail a package's check is the package's policy, as a line width is a fact of the page and no judgment of the code: a prototype, an exercise or a package of examples may want `unused-declaration` reported and not failing. And a lint that is no fact of resolution, a heuristic or a threshold, would bring the false positive the decision rules out. The peers split along that line. Where findings are exact, nothing is configured: Go and Zig refuse an unused name, Elm has no warnings, and Elixir plans no option to skip a warning but for one that may be a false positive. Where findings are judgments, one table states them: Cargo's `[lints]` gives each lint a level of `allow`, `warn`, `deny` or `forbid`, a group a `priority` that orders it against a lint's own (TOML tables being unordered), and a workspace's table to a member that opts in with `workspace = true` ([manifest](https://doc.rust-lang.org/cargo/reference/manifest.html#the-lints-section)); Biome gives each rule and each group `error`, `warn`, `info` or `off`, where `warn` leaves the exit code alone unless `--error-on-warnings` says otherwise, and a rule's options beside its level ([linter](https://biomejs.dev/linter/)); Ruff resolves `select` and `ignore` from the broadest selector to the narrowest, `ALL < category < linter group < linter prefix < rule` ([linter](https://docs.astral.sh/ruff/linter/)); Lean sets linter options for a package or a library in Lake's `leanOptions`; dune's `dev` profile turns warnings into errors and `release` does not. In the source, Rust's `#[expect(lint, reason = …)]` warns where nothing it expects fires, and Ruff's `RUF100`, ESLint's unused-directive report and golangci-lint's `nolintlint` hold suppression comments to firing, to naming a rule and to a reason; elm-review refuses disable comments by design and admits ignores only in its configuration, for generated or vendored code ([elm-review's design note](https://github.com/jfmengels/elm-review/blob/master/documentation/design/suppress.md)). Curios has no comment the compiler reads and decorators only for Core text, and a binder, an import and a declaration are already kept by their own spelling, so in the source nothing would change: the one place is the manifest, as it is for the format. A design would follow [A file is formatted as one place states](../../design/tools/a-file-is-formatted-as-one-place-states.md) in its housekeeping: what the manifest and the command line take is one list, kept where it is changed, and both read it, so no setting is a key without a flag or a flag without a key, and a change to the list does not compile until every reader of it is changed too, as a field added to `FormatSettings` does not until `format_under` reads it. For the lints that list is `LintKind` (`curios-core/src/lint.rs`), each kind named by its exhaustive `name()`: the table's keys, `unused-binder = "warn"`, and the flags, `curios lint --unused-binder warn` for standard input and a file no package governs, are both read off it, so a kind added is a setting at once and a key no kind names is refused listing them, and one test holds the two spellings equal as the format's does; the table is refused as a flag where a package governs, and inherited from an umbrella a member does not restate; a level of three words, `error`, reported and failing `curios lint`, the default, `warn`, reported and leaving the exit alone, and `off`, reported nowhere; and a value whose table form, `{ level = "warn" }`, leaves room for a later heuristic lint's options. `curios lint` might also one day write each lint's way out, since every lint's message names one mechanical edit — delete the import, write `_` — as `format` writes its canonical text; that is only a possibility, recorded so a design leaves room for it. Not yet known: whether levels alone serve, or groups too, and then whether a lint's own key wins over its group's with no priority to state; whether a setting can be scoped below the package, to a module path rather than to files found by where they sit, which the format's design rejects for the format; whether the language server's severity and `wonder`'s report follow the level, or only `lint`'s exit does; whether `unused-dependency`, decided over a package, takes a level as the others do; and what of the decision's **Rejected** paragraph stands — disable comments, since comments are not syntax, and a suppression file with a ratchet, which a package that lints clean never needs. Settled by a design restating the lint decision's "exactness leaves nothing to configure" and its rejections, beside the format's. Size: unknown.
