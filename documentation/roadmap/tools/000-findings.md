- **Uncertain: a subject's tests run one at a time, though nothing of one test's run is shared with the next.** `run_tests` (`curios/src/test_runner.rs`) runs a subject's scheduled tests in a loop, each through `TestRun::run` (`curios/src/testing.rs`), which reads the program by a shared borrow and takes a host that is `Send + Sync + 'static`, and each test's writes are relayed through a frame of its own (`Frame`, `curios/src/test_runner/host.rs`): a pool of threads could run several at once, as cargo's test harness and nextest do by default and Go's `t.Parallel` does on a test's word. Seen between: **the live drawing** holds one open node a tree, and a test is a node of its program's tree, so tests running at once need the rule it keeps for subjects one level down — each running test shown in the region, each node written whole in schedule order, which keeps the order [`test`](../../usage.md#test) states — where the plain drawing names each line's test already; **what a test reaches past its frame**: of the host's 41 operations (`curios-abi/src/host/ops.rs`), four reach what one test at a time can hold — the terminal (`tty_take`), standard input (`handle_read` on it), a child given an inherited stream (`proc_spawn`), which writes past the transcript, and a serial device (`serial_open`) — of which the test host intercepts the first and the third; the file system's writes and `socket_listen` race only where two tests name one path or address; and no operation writes the environment or the working directory, which `proc_env` and `proc_cwd` only read; so whether tests run side by side by default, one reaching an exclusive resource alone, or on a test's word is a decision to make; and **the browser target**, whose runner runs every test in the page's one thread (`curios-browser/src/runner.mjs`), where side by side needs workers. Overlapping one subject's tests with the next subject's compile is [A compilation is a graph of item tasks](../compilation/301-item-tasks.md)'s executor's; running one program's tests side by side waits on nothing of it. Not yet known: what share of a `curios test` run its tests take beside compiling, on `/std`'s suite and on a package of the corpus, which bounds the gain; and whether the browser target follows. Settled by timing a run's tests against its compiles with `curios-profile`; the figures make it a specification or drop it. Size: unknown.
- **Uncertain: narrowing a terminal that reflows while the live region is drawn leaves the old region's rows in the scrollback.** The live drawing erases its region by moving up the rows it drew (`Live::erased`, `curios/src/report/live.rs`), each cut to the width measured for that frame; a terminal that reflows on resize — VTE, kitty, WezTerm, iTerm2, Windows Terminal — wraps a row wider than its new width onto more lines, so the next frame moves up too few and leaves the upper part of the old region above it, as indicatif's redrawn bars do. A terminal that does not reflow, as xterm does not, keeps each row one line and is unaffected; widening is clean on both. Fix: where the width is narrower than the last frame's, move up by the lines each row drawn now takes. Not yet known: how the drawing tells a terminal that reflows from one that does not, since moving up by the wrapped count on one that does not erases lines written for good above the region; settled by reproducing it on each terminal and surveying how a redrawing tool learns which it is, if any does. Size: unknown.
