# Tools: findings

- **The server writes no inlay hint beside a binder written without its type, though a check's record holds the type each binder was opened at.** `textDocument/inlayHint` writes a type beside a binder that states none, as rust-analyzer writes one off its inferred types, and the record holds the type each written binder of a text was opened at, spelled for a reader standing in the text (`Written::binders`), and where it is bound (`Written::bound`, `curios-wonder/src/named.rs`); it does not hold which binders state their type, which the lowering reads where it reads the binder. Fix: the record notes the binders written with no type, and a handler writes beside each, after its name, `: ` and the type `Written::binders` spells, the spelling a reader could write there ([A diagnostic spells what its reader can write](../../design/tools/a-diagnostic-spells-what-its-reader-can-write.md)), over the range asked, read off the document's last check, and the capability advertised. Check: a scripted server session over a lambda and a `let` written without a type and one written with one, a hint beside the first two only, each the type `--at` answers at the binder; the `--server` row states it. Size: one commit.
- **A stream is read through the fold's summary and `awk` alone, where a trace viewer would lay it out as a timeline.** `curios profile <STREAM>` prints the fold's summary (`fold`, `curios-profile/src/fold.rs`), and a question it does not answer is asked of the rows by hand, as `curios-profile`'s README does with `awk`; the rows hold what a timeline needs — each span's entry and exit with its time, its fields and the allocator's readings, and each event (`curios-profile/src/trace.rs`). Clang's `-ftime-trace` writes Chrome Trace Event JSON, rustc's self-profile is turned into it by `crox`, and Lean's `trace.profiler.output` writes the Firefox Profiler's own format, each opened as a flame chart and a timeline in Perfetto, the Firefox Profiler or speedscope. Fix: `curios profile <STREAM> --timeline <PATH>` writes the stream as Chrome Trace Event JSON beside the summary it prints — each entry and exit a `B` and an `E` event at its time in microseconds, the span's fields as its `args`, the allocator's live bytes a counter, each event an instant one, and a span still open where the stream ends left open, as the run left it. Check: a `curios-profile` test writing a stream of nested spans, an event and an open span, its events in order and paired; `documentation/usage.md`'s `profile` row states the flag. Size: one commit.
- **A term cannot be printed from a debugger, so a stopped compiler shows where it is and not what it holds.** gdb stops the compiler in any function of a build that keeps its symbols, and a `Term` it holds there is the pointers of a hash-consed graph: nothing in the workspace is callable from a debugger to print one, as LLVM's `dump()` methods and GCC's `debug_tree` are called from gdb. Telling which recursive group each climb of `group_held` was of took a temporary print and a rebuild of a scratch copy. Fix: `curios-core` exports a function under an unmangled name, `curios_dump_term`, which takes a term's address and writes its `Debug` form to standard error; the `unsafe` its attribute takes states at its site that the name is the workspace's alone, and gdb calls it as `call curios_dump_term(<address>)`. Check: the symbol present in the release `curios` binary, read off its symbol table by a test of `curios`; the which-tool paragraph of `curios-profile`'s README names it. Size: one commit.
- **A summary names a declaration its reader cannot write, and no build says so.** The summary of `/std/Tui` named `Frame/fit`, a private definition, where a consumer writes the constructor `View/fit`; prose reaches a page as text and code (`curios-document/templates/prose.html`), a code span resolved by nothing. Fix: a code span that reads as a path is resolved as a signature's name is, and linked where it names what a consumer writes; whether one that names only what they cannot is a lint is the user's to decide. Size: one commit, and a second for a lint.
- **Uncertain: what a file writes is read off its subject's whole lowering on every check.** `PreparedText::texts` (`curios-module/src/into_core/mention.rs`), which both transports read a file's texts by, took 9 ms of each check's 21 ms of stating its answers (`placed`) over `curios-prelude-build/std/Nat.crs` in a copy of the `std` package at the commit that landed as `6e611c13d` (its pre-rebase `289149bbe` is on no branch), to be retaken at this entry's timing, timed by spans added for the reading in `curios-wonder`'s README keystroke scenario, one session of ten keystrokes; a check has paid it since its answers were read off the lowering. Seen: it builds the unit's module bodies over every declaration's record (`Bodies::of`, once a lowering), and a recompile makes a new lowering each keystroke, so a check of one file reads the library's. Not yet known: whether `Bodies::of` is the cost, or the canonical spelling of each module's file `lies` asks for, or reading the restored half's records; settled by spans inside `texts` over the same scenario. Size: unknown.
- **Uncertain: a subject's tests run one at a time, though nothing of one test's run is shared with the next.** `run_tests` (`curios/src/test_runner.rs`) runs a subject's scheduled tests in a loop, each through `TestRun::run` (`curios/src/testing.rs`), which reads the program by a shared borrow and takes a host that is `Send + Sync + 'static`, and each test's writes are relayed through a frame of its own (`Frame`, `curios/src/test_runner/host.rs`): a pool of threads could run several at once, as cargo's test harness and nextest do by default and Go's `t.Parallel` does on a test's word. Seen between: **the live drawing** holds one open node a tree, and a test is a node of its program's tree, so tests running at once need the rule it keeps for subjects one level down — each running test shown in the region, each node written whole in schedule order, which keeps the order [`test`](../../usage.md#test) states — where the plain drawing names each line's test already; **what a test reaches past its frame**, a test that takes the terminal (`tty_take`) or gives a child an inherited stream (`proc_spawn`) writing past the transcript and so running alone, and tests that touch the file system, the working directory or the environment racing, so whether tests run side by side by default or on a test's word is a decision to make; and **the browser target**, whose runner runs every test in the page's one thread (`curios-browser/src/runner.mjs`), where side by side needs workers. Overlapping one subject's tests with the next subject's compile is [A compilation is a graph of item tasks](../compilation/301-item-tasks.md)'s executor's; running one program's tests side by side waits on nothing of it. Not yet known: what else the native host holds process-wide beyond the terminal and an inherited stream; what share of a `curios test` run its tests take beside compiling, on `/std`'s suite and on a package of the corpus, which bounds the gain; and whether the browser target follows. Settled by timing a run's tests against its compiles with `curios-profile` and listing the host's operations by what each reaches of the process; the figures make it a specification or drop it. Size: unknown.
- **Uncertain: narrowing a terminal that reflows while the live region is drawn leaves the old region's rows in the scrollback.** The live drawing erases its region by moving up the rows it drew (`Live::erased`, `curios/src/report/live.rs`), each cut to the width measured for that frame; a terminal that reflows on resize — VTE, kitty, WezTerm, iTerm2, Windows Terminal — wraps a row wider than its new width onto more lines, so the next frame moves up too few and leaves the upper part of the old region above it, as indicatif's redrawn bars do. A terminal that does not reflow, as xterm does not, keeps each row one line and is unaffected; widening is clean on both. Fix: where the width is narrower than the last frame's, move up by the lines each row drawn now takes. Not yet known: how the drawing tells a terminal that reflows from one that does not, since moving up by the wrapped count on one that does not erases lines written for good above the region; settled by reproducing it on each terminal and surveying how a redrawing tool learns which it is, if any does. Size: unknown.
