# Tools: findings

- **Uncertain: `wonder` could answer a structural, type-aware search and replace over a package, as rust-analyzer answers one over a Rust workspace.** Renaming `curios_core::Module` to `Definitions` across this workspace ([spec 100](../100-a-witness-reaches-whatever-the-trusted-base-judges-or-believes.md)'s names) needed what no rewrite of the text could see: a binding called `module` that holds a unit's definitions reads exactly as one holding a WebAssembly module or a parsed module body, and a bare `Module` named a different crate's type from one file to the next. What did it was rust-analyzer answering from its own resolution and inference — a hover read each binding's type, and its rename rewrote the binding with every use and shorthand field — and its structural search and replace matches a pattern's paths "if they resolve to the same item, even if they're written differently" ([`ide_ssr`](https://rust-lang.github.io/rust-analyzer/ide_ssr/index.html)). A Curios program renamed or restated meets the same wall: a declaration renamed with its uses across the units that import it, or a call restated wherever its callee is that one declaration and not another of the name. `wonder` already resolves every name and settles every term's type, and answers both at one position ([The editor is answered at a position](300-the-editor-is-answered-at-a-position.md)). Bringing it to `wonder` would shift the engine's focus, from a read-only tool to a tool that knows a codebase, and the read-only tenet is pierced already: [`curios-wonder`'s README](../../../curios-wonder/README.md) has a query read "the compiler's answer" and compute "none of its own", while a question compiles only as far as its answer needs and files on disk the units it compiled ([A command compiles only as far as its answer needs, and a project keeps what it compiled](../../design/tools/a-command-compiles-only-as-far-as-its-answer-needs-and-a-project-keeps-what-it-compiled.md)), so the engine writes a store as it answers. Not known: how `curios-wonder`'s README states the engine's mission once it writes code as well as a store; whether what `wonder` resolves and settles, kept per unit, can be asked across a package and every unit that imports it at once; what a pattern is written in — surface text with holes, or the Core text spec 100 introduces, whose `#{…}` decorator states what the surface leaves to inference; and whether a replacement is answered as text the formatter then lays out, or as a tree. What would settle it: a survey of rust-analyzer's `ssr`, Comby and Semgrep for what a pattern binds and how a replacement is checked, read against `wonder`'s queries, and a probe renaming one `/std` declaration across its importers through what `wonder` already answers. Size: unknown until then.
- **Uncertain: what `xtask` runs could be stated in a notation of its own, which `xtask` checks and performs.** The steps are hard to read as a system off Rust: "I myself would find it easier to read and to understand the system if it had some notation for the role that xtask fills". The run is data already, since `Step::plan` (`xtask/src/steps.rs`) hands the runner closed `Task`s, so a notation is a printer and a reader over them held together by a round-trip, as spec 100's Core text is over Core: make-like files in a directory beside `xtask/src`, as `xbench/readings/` sits beside `xbench/src`, read by `curios-parse` and the source of truth for the run, with `xtask` the checker and runner of what they state, as the paper's inventor and checker are (`../curios-papers`). A printed plan alone derives what is already data and settles nothing. `just`, cargo-make and the monorepo runners were weighed and leave `xtask` in place: each is a second entry point, its prerequisites written by hand, with the steps that are no shell command still in Rust beneath it. Not known: how the narrowing a request makes — check mode, `--package`, a filter, Biome's tracked files, the edition, `cargo metadata` — is stated, whether the files state the whole run and `xtask` narrows it or the notation takes parameters; what becomes of what Rust checks at compile time, the plans' exhaustiveness and clap's derive; what `xtask` reading `curios-parse` costs an edit that breaks `curios-common` or `curios-unicode`; and how the notation reads against [`xtask`'s README](../../../xtask/README.md), which rejects a Makefile as a second entry point and each step's prerequisites as a hand-written column. What would settle it: the paper's inventor and checker passage read against `Task`, and a printer and reader for the gate's run held to a round-trip. Size: unknown until then.
