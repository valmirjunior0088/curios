# Tools: findings

- **A conversion left undecided because an implicit argument was never solved says no way out.** `usage.md`'s *What a command reports* closes a report on "the way out, said as what to write", and `curios-elab`'s `undecided conversion` (`curios-elab/src/error/display.rs`) states only `never solved: the implicit argument `A` of `/std/Monad/bind`, the implicit argument `A` of `Proc/exit`` for `use /std/{print, Proc}; let _ = Proc/exit(3)!; print("x")`, which a reader fixes by writing the argument, `Proc/exit(@{}, 3)`. Fix: where each metavariable left unsolved stands for a written call's implicit parameter, the report closes on writing it, `write it in the call, `Proc/exit(@…, 3)``, the call spelled from where the reader stands. Check: the program above reports that way out, as a `curios-pipeline` report test beside the reports that pin `undecided conversion`. One commit.
- **Uncertain: a failed assertion names neither where it was written nor what it asserted.** `Test/assert` (`curios-prelude/std/Test.crs`) fails with `the condition was false`, which `curios test` relays under the test's path, so a test that asserts twice gives its reader no way to tell which failed; `Test/equal` reports the two values and no place. A library function cannot learn where it was called from: an assertion is an ordinary call, `/std` has no macros, and a value carries no place. Not yet known: whether a parameter the compiler fills with the call's place at each call, as Rust's `#[track_caller]` with `Location::caller()` and Swift's `#file` and `#line` defaults do, fits beside `@` and `use`, which fill a parameter by unification and by resolution, and whether the written expression is shown too, as Rust's `assert!` and pytest's rewriting show it. Settled by a design for that parameter, which makes this a capability specification, or by a reason no assertion needs one, which drops it. Size unknown.
- **Uncertain: whether the span a match keeps on one line is a setting.** `FLAT_MATCH_COLUMNS` (`curios-surface/src/print.rs`) fixes at 70 the columns a match may span from `match` to `end` and stay on one line, so at the default width of 100 a match of 71 to 100 columns breaks though it fits. Its comment holds the span a property of the reader rather than of the page, the same at every width, and [A file is formatted at the width one place states](../../design/tools/a-file-is-formatted-at-the-width-one-place-states.md) keeps one setting, the width, every other layout choice keeping one answer. Peers split: rustfmt exposes spans of this kind, `fn_call_width` and `single_line_if_else_max_width` among them, each derived from `max_width` by `use_small_heuristics`, while Prettier and gofmt expose none. Not yet known: whether the span is a package's to state, a second field of `FormatSettings` and so a key and a flag, which reopens the decision's one setting; whether it follows the width as a share of it, no setting, a narrow page then breaking a match its reader takes in at once; or whether it stays fixed. Settled by the decision restated one of those ways, or by the drop, reassessing on the way whatever the decision and the formatter settle around the one setting where the answer moves it: the width's bounds held as the only knob, the laws held over the tree at the narrowest, the report's window, and the key and flag every setting derives. Check, where it moves: `print/ladder_layout_tests.rs` and `print/call_layout_tests.rs`, which read the constant, and the formatter's laws at every width. Size unknown, one commit if it becomes a setting.
