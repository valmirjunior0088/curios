# A test answers what it found, and its runner presents it

Adopted (the user, 2026-11-18): a failing test tells its reader which check failed, what that check compared and the steps that reached it, because the test answers what it found as data and the runner, which draws every line of the transcript, presents it. Today a test formats its own failure as a sentence and writes it on its standard error, where the runner quotes it in the frame it quotes everything the test writes, so a reader cannot tell what went wrong from what the test printed; the runner learns a `bool`; `Test/assert` says "the condition was false" and nothing of what it checked; and a table stops at its first failing case. Probed at `368b8ab82` (`curios test` over a file of failing tests): a test that prints `hello` and then fails on `Test/equal(1, 2)` shows `> hello` and `> expected 2 but got 1` as two lines of one kind, and `Test/all([Test/equal(1, 1), Test/assert(false), Test/equal("a", "b")])` reports case 1 alone.

This revisits two settled texts, each restated as its stage lands: [A command narrates on one transcript and reports in blocks](../../design/tools/a-command-narrates-on-one-transcript-and-reports-in-blocks.md) rejects "an entry that reports its own failure", on the ground that "a failing test's message is its own output"; and [A test is a declared description, and a proof is a `let`](../../design/tools/a-test-is-a-declared-description-and-a-proof-is-a-let.md) judges the tail at `Io(Bool)`. What changed is where the words live: a failure written as a sentence by the test is a rendering, and a rendering cannot be drawn twice — beneath a verdict, in a browser's transcript, in a suite's assertion — without being parsed back. The answer a test program already gives its runner carries the verdict, so no host row is added and no program's `execute` changes: a program stays self-contained, and a test program, whose answer has always been read, answers more.

The next step is stage 1, a delivery.

## What the tree holds

- **`Test` is a monad over outcomes** (`curios-prelude/std/Test.crs`): `Test(A)` is `success(A)`, `failed(Failure)` or `action(Io(Test(A)))`, `bind` skipping its continuation past a failure. A `Failure` is a message and a list of contexts; the private `context` prepends a label, and `Test/all` labels a failing case `case N`. The failures a test can meet: `Test/fail(message)`, `Test/assert` ("the condition was false"), `Test/equal` ("expected # but got #", its sides spelled through `Spell`), an error lifted from a `Try` (shown through `Show`), and `Test/timeout` ("the test timed out").
- **`answer` alone prints** (`curios-prelude/std/Test.crs`): the test the runner selected writes its failure on standard error. `Test/main`, handed the tests' thunks in schedule order, runs the one its index names, and answers `false`, with nothing said, for an index the program does not hold. The `curios` suite runs a test program as the runner does, each test by its index (`run_tests_under`, `curios/src/tests/test_support.rs`), and draws what each wrote and how it ended.
- **The runner learns one `bool`.** The elaborator judges the synthesized tail at `Io(Bool)`, stated as intrinsics (`curios-elab/src/elaborate/module.rs`); the native engine reads the entry's i31 as `TestEnd::Answered(bool)` (`curios-native/src/engine.rs`); the browser harness reads it as `held` (`curios-browser/src/harness.mjs`), the page posts it (`curios-browser/templates/index.js`), and the run's socket carries it as `Posted::held` (`curios-browser/src/runner.rs`). No backend stage reads the tail's type. Both runners already read a byte string from the guest: natively as an `(array i8)`, in a page through the bridge's `bytes_len` and `bytes_load` (`curios-browser/src/bridge.rs`).
- **One printer draws a test's node** (`Tree::ended`, `curios/src/report.rs`): its mark and verdict, then what only the runner holds beneath the verdict, which today is a trap's text. The `curios` library runs tests and shows nothing (`curios/src/testing.rs`); the binary draws (`curios/src/test_runner.rs`).
- **A second presenter**: `curios-prelude/tests/std.rs` formats each failing `/std` test from what the mock host captured.
- **A derived `Spell` writes a value as Curios writes it, and Curios reads it back.** `satisfy Spell(T) { .. }` writes a structure as `Finding { steps = ["case 3"], ... }` and a constructor as `Check/unequal("3", "b\"\n")`, and that text parses and checks as the program's own (probed at `368b8ab82`); `curios_surface::Term` is `FromStr`.
- **What a verdict's writer weighs**, counted at `368b8ab82` over a program spelling one finding from its arguments, so nothing folds — functions at the `wasm` rung, then the page's module after Binaryen: no writer 113 and 19.2 KB; a derived `Spell` 148 and 36.7 KB; `Json/encode` 240 and 86.5 KB, its `num` arm linking `Flt/to_str`; a length-prefixed framing 120 and 24.4 KB.
- **The counts**, at `368b8ab82`: `/std` declares 320 tests and writes `Test/equal` 640 times, `Test/assert` 107 and `Test/all` 137, of which 132 are written lists of checks and 5 build theirs from a table; outside `/std`, `Test/assert` 86 and `Test/equal` 24 times.

## Peers

**What Curios takes.**

- **The failure is data and the runner draws it.** Elm's test answers an `Expectation` whose `Reason` holds `Equality String String` and the like, and "Test runners can use this to provide nice output" ([`Test.Runner.Failure`](https://github.com/elm-explorations/test/blob/master/src/Test/Runner/Failure.elm)); Hspec's `ExpectedButGot (Maybe String) String String` ([`Test.Hspec.Core.Spec`](https://hackage-content.haskell.org/package/hspec-core-2.11.18/docs/Test-Hspec-Core-Spec.html)); a Jest matcher answers `pass` and a `message` built with the runner's `printExpected` and `printReceived` ([`expect.extend`](https://jestjs.io/docs/expect)); ExUnit's failure shows `code:`, `left:` and `right:` ([`ExUnit.Assertions`](https://ex-unit.hexdocs.pm/ExUnit.Assertions.html)); tasty's `Result` ([`Test.Tasty.Core`](https://hackage.haskell.org/package/tasty-1.4.1/docs/src/Test.Tasty.Core.html)).
- **A failure is a statement and labelled facts.** RackUnit reports a failed check as its check-info stack, name and value pairs such as `actual` and `expected` that `with-check-info` adds to ([RackUnit API](https://docs.racket-lang.org/rackunit/api.html)); TAP's diagnostics are a `message` and `data` with `got` and `expect` ([TAP 13](https://testanything.org/tap-version-13-specification.html)). That is the shape of a compiler report here, a tag and labelled facts (`curios_common::Report`), and its vocabulary, `expected:` and `obtained:` where two values disagree.
- **Independent checks all report.** GoogleTest prefers `EXPECT_*`, "as they allow more than one failure to be reported in a test" ([primer](https://google.github.io/googletest/primer.html)); Catch2's `CHECK`, Go's `t.Errorf`, Swift Testing's `#expect` ([Expectations](https://github.com/swiftlang/swift-testing/blob/main/Sources/Testing/Testing.docc/Expectations.md)) and Python's `subTest`, which reports each failing iteration with its parameters ([`unittest`](https://docs.python.org/3/library/unittest.html)), each go on past a failure.
- **A path of named steps.** Go names a subtest by "the name of the top-level test and the sequence of names passed to Run" ([`testing`](https://pkg.go.dev/testing)); GoogleTest's `SCOPED_TRACE` adds its message to "every failure" inside its scope ([advanced](https://google.github.io/googletest/advanced.html)).
- **A check states itself.** Alcotest's `check` takes a label beside the two values it compares, and prints them through the testable's own printer ([Alcotest](https://github.com/mirage/alcotest)) — `Test/equal`'s `Spell` and `Eql`; Gleam's `assert … as "message"` replaces the generic "Assertion failed" ([tour](https://tour.gleam.run/advanced-features/bool-assert)).

**What Curios avoids.**

- **A failure the test prints.** Zig's `expectEqual` writes its own sentence on standard error, as Curios does today, and libtest's message is a panic's text: the runner holds a sentence among the test's own output, which it can neither tell apart nor draw again.
- **Two verbs for one choice.** `ASSERT`/`EXPECT`, `REQUIRE`/`CHECK`, `Fatal`/`Error` and `#require`/`#expect` make each author decide at each check whether the test can go on. Here the program says it: a step that reads what an earlier one gave is sequenced by `bind` and stops at its failure, as a `!` does, and checks that read nothing of one another are `Test/all`'s, which reports each.
- **Stopping at the first of independent failures.** Elm's `Expect.all` answers its first failing expectation (`allHelp`, [`Expect.elm`](https://github.com/elm-explorations/test/blob/master/src/Expect.elm)), as `Test/all` does today.
- **A schema stated nowhere.** TAP leaves its diagnostics "not … standardized", and its own examples key the expected value `expect` once and `expected` once. The verdict's shape is one declaration in `/std/Test`, written by a derived witness and read by one reader, a test holding the two together.
- **A place as a check's identity**, and **a compiler that takes the asserted expression apart**: pytest's rewriting, Swift's `#expect` macro, ExUnit's and Gleam's `assert`, Catch2's decomposition and Roc's `expect` each give the compiler a rule for what a report needs, and Go's `t.Helper` exists because a place in a helper names the helper. Rejected below.
- **Events beside the answer**: Go's `test2json`, libtest's JSON and Zig's server protocol stream results because their tests share a process that may trap or hang; a Curios test runs in an instantiation of its own, and its runner already knows a trap, an exit and the time.
- **Hiding failures**: Alcotest prints only the first failing test's log unless asked; a verdict is drawn whole.

## Decided

Settled with the user on 2026-11-18, the first five when the specification was filed and the rest when it was rewritten from its objective:

- **The test answers a verdict.** It crosses as the answer a test program already gives its runner, with no host row added, and the native engine and the browser runner read it alike.
- **The runner presents**, and `/std`'s `Test` prints nothing of its own.
- **A check states itself**: `Test/equal` carries its two sides; a condition with no sides to show is checked under a label its author writes, so no check is anonymous.
- **Steps, and every failure**: a named step's label joins the path a verdict reports; `Test/all` reports every independent failure, while `bind` keeps stopping at the first of steps that depend on one another.
- **Left to specifications of their own**, should they be wanted: expect tests, seeds a runner replays a property by, and checks the compiler decides.
- **A verdict is the list of what failed**, empty where the test held, each entry the steps that reached it, a statement and labelled facts, the shape of a report: `Test/equal`'s statement and its `expected` and `obtained` sides spelled; a labelled condition's statement its label; a lifted error's its `error` shown; a timeout's its deadline spelled. A list from the first stage, so stage 3 changes no crossing.
- **It crosses as `Io(Bytes)`, the text a derived `Spell` writes**, and the `curios` library reads it back with the program's own parser: one reader for both runners, the sides a test spelled escaped once more as fields of the record, so nothing a witness writes can stand outside its field. An answer that is no verdict is a compiler fault.
- **The runner draws a verdict beneath the verdict's word**, where a trap's text stands, each failure its path and statement on a line and its facts beneath, the values in backticks; a suite drawing its own (`curios-prelude/tests/std.rs`) reads the same record, as the transcript decision has a test of the compiler draw a report its own way.

## Stages

1. **The verdict, its crossing and its drawing.** `Test.crs`'s failure becomes the verdict's entry with its derived `Spell`; `Test/main` answers `Io(Bytes)` and the elaborator judges the tail there; `TestEnd::Answered` and `Posted` carry the bytes; the harness reads them by their structure, as it reads a word today; the `curios` library reads a verdict; `Tree::ended` draws it beneath the verdict; `answer` prints nothing. Today's sentences become statements and facts: `case N` a step, `Test/equal`'s sides `expected` and `obtained`, the condition's `the condition was false` until stage 3 labels it. `documentation/usage.md`'s `test` section, the transcript decision, the test decision and `curios/src/test_runner.rs`' module documentation restated. Name the figure it moves: a test program's weight, by at most the writer's 35 functions. Check: a failing `Test/equal`, a table case, a lifted error and a timeout drawn by the runner natively and in a browser from the verdict alone; a test that writes and fails shows its writes above its verdict and its failure beneath; a passing test unchanged; an answer that is no verdict reported as a compiler fault. One commit.
2. **Every independent failure.** `failed` holds every failure; `Test/all` runs each case and reports each that fails, by its index, `bind` still stopping at the first. Check: a table with two failing cases reporting both. One commit.
3. **Checks that state themselves.** `Test/assert(label, condition)`, the label first, its statement the label; `/std`'s 107 uses and the 86 outside it rewritten with their labels, `documentation/language.md`'s example among them. Check: no check of `/std` anonymous; a failing labelled condition reported by its label. The site's cheatsheet example follows at the next release. One commit.
4. **Named steps.** `Test/step(label, test)`, its label prepended to the path of each failure its test reports. Check: a failure two steps deep reported under both labels. One commit.

## Rejected

- **A host row the test hands its verdict through**: the answer already crosses, and the host's contract grows for what one program kind says once.
- **Events on a channel the test host holds**, each step and check as it happens: they tell where a trapped or hung test stood, which a test running in an instantiation of its own does not need for its verdict; left to a specification of their own should traps and timeouts need it.
- **JSON as the crossing**: `Json/encode` links float printing the verdict never writes, a mapping into `Json` is written by hand, and the reader is a second grammar's.
- **A framing of the verdict's own**: the lightest writer, and a format stated twice by hand where the language has one.
- **A closed sum of check kinds the runner words**, Elm's `Reason` and Hspec's `FailureReason`: each new check changes the library, the reader and the printer together, and both peers keep a case whose words are the test's own beside the kinds the runner words (`Custom` with its description, `Reason String`).
- **A source place, a line and a column, as what identifies a check**: it says nothing of why the check failed and moves with every edit.
- **An implicit parameter the elaborator fills with the call's place**, as Scala's `sourcecode`, GHC's `HasCallStack`, Swift's `#fileID` and C++'s `source_location` do, and **the asserted expression taken apart by the compiler**, as pytest, Swift, ExUnit, Gleam, Catch2 and Roc do: a filling rule of the language's for what a report needs.
- **A place literal written at each check**, OCaml's `__POS__`: a burden on every author, silent where forgotten.
- **A case of a table named by its spelled input**, Python's `subTest(i=i)`: of `/std`'s 137 `Test/all`, 132 are written lists of checks, which no input names; a step names a case where it helps.
