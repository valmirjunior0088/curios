# A run is recorded as one Perfetto trace

**Adopted by the user on 2026-11-22.** The compiler's account of its own work becomes one stream a run, in the format the standard tracing tools read: a summary, a timeline and an SQL query are readings of one file; each span, event and allocation is on the track of the thread it happened on; and a term a span carries reads as Core text, written once a trace. The format is [Perfetto's trace](https://perfetto.dev/docs/reference/trace-packet-proto), read in process by `curios profile`, by `trace_processor`'s SQL, and as a timeline by [Perfetto's UI](https://ui.perfetto.dev). `curios-profile` writes and reads it ([its README](../../../curios-profile/README.md#the-library-emits-records-and-aggregation-is-one-of-its-consumers)); what remains is below.

## What is wrong today

- **A packet restates what its sequence could hold once.** Every packet of a stream (`Sink`, `curios-profile/src/trace.rs`) carries the sequence's id and flags and a whole timestamp, and every slice its thread's track and the four counter tracks' ids, each id with a tag of its own, proto2 packing no repeated field; a live reading below nought costs ten bytes. Interning names and strings saves less than that costs: the prelude's stream, which `cargo xtask profile prelude` files, is 1,499,668,122 bytes in Perfetto's format at `c8133bc65`, where the tab-separated rows of the same run, a few of them lost to a disk that filled, were 1,088,218,236 under the compiler that landed as `463b63cb7` (counted).
- **The summary answers as no other command does.** `curios profile` prints up to five tab-separated tables, each under a header row, with the run's peak and each table's name in header cells. A field with nothing in it is left blank. Memory is in mebibytes to a tenth, so a span's five allocations read `0.0`. The stack a killed run stopped inside is the last table. [A command narrates on one transcript and reports in blocks](../../design/tools/a-command-narrates-on-one-transcript-and-reports-in-blocks.md) gives every other answer a block, then one listing of rows with no header, `-` where a field has nothing, each row splitting alike.
- **No step reads a stream by SQL.** A question past the summary is asked in Perfetto's hosted UI by hand; no step of the task files runs `trace_processor` over a stream, so no check holds the summary's totals to what Perfetto reads of the same file.
- **A thread's allocations are the process's.** The allocator counts for the process (`curios-profile/src/count.rs`), so a slice carries what every thread took while it was entered: the `wonder` server's protocol thread allocates into the analyst's spans, and a hosted program's thread and Wasmtime's, Binaryen's and Cranelift's pools into whatever span their caller has entered.

## Goal

- A stream states once what its sequence holds: a packet sequence a thread, as Perfetto's own writer keeps one, whose defaults name its track and the counter tracks its slices read, and whose timestamps are steps on an incremental clock.
- A thread's allocations are its own: counters of its sequence, on its track, written as steps, as Perfetto writes a thread's time; a span is charged what its own thread allocated, and the process's live bytes and peak stay gauges of the process.
- Every report of a stream is a reading of that file: `curios profile`'s answer, read in process and drawn as every answer of the command line is, a block of what the stream states of its run and then one view's rows; a query through `trace_processor`, pinned beside the compiler or in Perfetto's UI; and a timeline in Perfetto's UI.

## Settled

- **The format is Perfetto's protobuf trace, written by the recorder over types generated from Perfetto's schema**, at Perfetto's v58.2, the release whose `trace_processor_shell` Perfetto's v59.1 tooling pins.
- **The summary is read in process**: `trace_processor` answers what the summary does not, by SQL, and backs Perfetto's UI.
- **Perfetto's hosted UI is the timeline**: it opens a trace in the browser without sending it anywhere, and keeps itself offline after one visit by its service worker.
- **A counter is written as steps only on one sequence.** Perfetto [delta-encodes a counter only where one packet sequence emits it](https://rust-digger.code-maven.com/src/perfetto_protos-0.48.1/protos/perfetto/trace/track_event/counter_descriptor.proto), as a thread's time is, so a thread's allocation counters are steps and the process's gauges, which every sequence reads, are written whole.
- **A span's beginning and end are two packets.** One record an interval written at its end, as rustc's `measureme` writes one, would halve the events and lose the spans a killed run was inside, which is what a stream is kept for.

**Rejected.** A build of Perfetto's UI pinned and served, a copy of what the hosted UI keeps. The process's counters written as steps, which a reader of several sequences cannot sum.

## Stages

**1. A sequence a thread, its allocations its own.** The writer opens a packet sequence for each thread the first time it records, its first packet clearing the sequence's state, declaring an incremental clock and stating its defaults: that clock, and its track events' defaults, its thread's track and the counter tracks its slices read — the thread's own allocated bytes and allocations, incremental and parented to its track, and the process's live bytes and peak; names and strings are interned per sequence. The allocator keeps each thread's counts in thread-locals initialized as constants with no destructor, which never allocate, beside the process's. The reader keeps each sequence's interned names, defaults, clock and counters apart, and charges a span its own thread's allocations. Check: a stream of two threads reads back as two sequences, each slice placed on its thread's track and charged its own thread's allocations; a slice costs fewer bytes than at `c8133bc65`; the prelude's stream measured again and stated beside the two figures above.

**2. The summary is an answer.** `curios profile <PATH>` answers with a block on the path asked. Its facts: whether the run returned or stopped, and whether the allocator counted; the peak; and the rows each other view holds, where it holds any, with a `try;` entry naming the command that lists them. For a run that stopped, each span it stopped inside is an entry, each thread's stack in turn and innermost last, with when it was entered. The block closes on `[trace]` and the path, a kind the decision gains. After a blank line comes one listing: the spans by default, or `--slowest`, `--samples` or `--within`, one at most. Its rows have no header and `-` where a field has nothing; their fields are named in `usage.md`, times in milliseconds and memory in bytes. The measurements that file a fold beside their stream file the default answer. Check: a stopped run's stack reads as its entries; each view's rows split into as many fields as every other row of it; `usage.md`, the decision and the READMEs that quote the summary restated.

**3. The reader beside the compiler.** `trace_processor_shell` pinned among `xtask/tasks.toml`'s `programs` by a minimum version, as Node is, since Perfetto publishes it a platform at a time, Linux's and macOS's alike: launched from the path, refused where it is absent, and fetched by no step; `cargo xtask profile query <STREAM> <SQL>`; and `curios-profile`'s *Taking a profile* naming the step and where Perfetto publishes each platform's binary. Check: the query step answers a total the summary states, alike, over the prelude's stream; and what `trace_processor` makes of a stream cut inside a packet, stated there.

## Verification and retirement

Each stage's check, then `cargo xtask workspace lint`, the suite and `cargo xtask docs build`, and the measurements that read a stream run by name. Once stage 3 lands, the decisions named above are restated, this file is deleted, and [A measurement files a record its figures are read from](../100-a-measurement-files-a-record-its-figures-are-read-from.md), which reads this trace, is released.
