# A browser test run is answered by whatever opens its page

`curios test` runs a subject's tests natively and nowhere else: `test` takes no `--target` (`curios/src/cli.rs`), where `run` and `compile` do, and `--port` beside it is an unknown argument. A test that reaches a `foreign` declaration a `[foreign.browser]` gateway answers is therefore refused natively unless a `[foreign.native]` module stands in for the gateway — the subject's program refused at its link after it compiles, its other tests with it, the subjects after it never reached — and the seam itself, the gateway answering the program's rows in a browser, is exercised by nothing the toolchain runs. The gateway is tested from JavaScript with the program mocked, the program natively with the gateway mocked, and the two meet only when someone opens the page and looks ([`documentation/usage.md`](../../usage.md), "Each side is tested with its own tools").

It has no prerequisite in another specification. The next step is a ready delivery, the stages below. [A delivery may be a Curios root](306-a-delivery-may-be-a-curios-root.md) states its "the same tests on both targets" check against this one.

## What is missing

- **`test` has no target.** `Mode::Test` carries a subject, `--filter` and the elaboration flags; `main.rs` compiles each subject through `TestSubject::compile`, loads it with `bindings_of` and runs each test through `Compiled::run_test` (`curios/src/testing.rs`). Nothing builds a test program for a browser.
- **The test runner is one loop.** `Run::subject` compiles a subject, runs each of its tests and prints its lines in one pass (`curios/src/test_runner.rs`), so nothing separates the plan — the subjects and their records — from the verdicts and the lines, and a verdict reaching the command from anywhere but `TestRun::run` has no door.
- **A test program is compiled for the native target alone.** `TestSubject::compile` keys the store with `Runs::Native` and finishes with `to_cwasm`; `Tested::built` and the archived `TestPayload::cwasm` are machine code, and `Tested::loaded` deserializes it (`curios/src/testing.rs`). `curios-prelude/tests/std.rs` runs `/std`'s own tests through `compile` and `loaded`.
- **The page carries no verdict out.** The harness's `run` resolves `{stdout, stderr, exitCode, trap}`, says of a program that answers "what it yields, which nothing here reads", and reads an exit with code 0 as it reads a return (`curios-browser/src/harness.mjs`); native reads the same reference as `TestEnd::Answered(bool)` and an exit apart from a return (`curios-native/src/engine.rs`). The harness keeps a stream only where no hook takes it, and the loader hands it hooks, so `start`'s outcome carries no output; the loader writes the element and the console and posts nothing anywhere (`curios-browser/templates/index.js`).
- **The server answers `GET` alone**, reads a request's head and no body, serves one page under `/<name>/` with `/` and `/<name>` redirected there, and keeps no state across requests (`curios/src/serve.rs`). `curios` has no JSON reader and no source of randomness (`curios/Cargo.toml`); `curios-browser` has `serde_json` and `curios-native` `getrandom`.
- **The `arg` key is spelled twice**, by `Served::url` writing the printed address and by the loader's `argumentsOf` reading the query, each pinned to the literal by its own test and neither to the other, against the tree's rule for a wire spelling: one constant, or a test that holds both.
- **`run --target browser` has no end-to-end test.** `curios/src/serve/tests.rs` serves fabricated files; the Browser arm of `main.rs`, building and serving a real page, is reached by no test. `--port 0` binds a free port and prints it on the `Serving` line, which usage does not state.

## What this builds on

- **`run --target browser` is the build and the serve.** `built` (`curios/src/browser.rs`) makes the page `compile --target browser` writes, and `Served` answers it on `127.0.0.1` at port 8000 unless `--port` names another, `Host` checked, every reply `Cache-Control: no-store` and `Connection: close`, printing `↳ Serving   http://127.0.0.1:8000/<name>/?arg=…` and opening no browser ([`documentation/usage.md`](../../usage.md), "Serving a page").
- **A test program picks its test by argument.** `Test/main` runs the test its second argument indexes and every test in order when it has none, and answers `false` without printing for an index that does not parse or names no test (`curios-prelude/std/Test.crs`); native passes `[argv0, index]` and instantiates the program once per test, "so one test's effects, traps and exits never reach another" (`TestRun::run`, `curios/src/testing.rs`). The page turns each `arg=` of its query into an argument after the page's name (`argumentsOf`, `curios-browser/templates/index.js`).
- **A test program is target-agnostic.** It is the subject's compilation with `EntryTail::Test { under }` in place of the final term (`curios-pipeline/src/compile.rs`); `payload_of` already takes the target and files a browser payload under `Runs::Browser`, the module Binaryen wrote (`curios/src/pipeline.rs`). The records a report prints — each test's path and body — are read off the compiled program (`TestRecord`).
- **The entry answers a word.** A test program's entry yields a `Bool` as the i31 `0` or `1`, and a program's the unit, a struct that is no word, so native refuses a program's return under a test's reading as `func/main answered no Bool` (`Ended for TestEnd`, `curios-native/src/engine.rs`). The GC JS API converts an i31 reference to a JavaScript number and a struct reference to an opaque wrapper, so a harness tells the one from the other.
- **The exit is a tri-state** (`documentation/usage.md`, "Exit codes"): `0` when every selected test passed, `1` on any that failed, trapped, exited or could not be built, `2` for goals.
- **Native's report is the one to reproduce.** The guest prints `path: passed`, or `path: failed` and its report; the runner prints a failing test's body indented beneath it, `path: exited N`, and `path: trapped` with the trap's lines, brackets a subject's lines between `↳ Testing` and `↳ Tested` with its tally, and ends with the count line; a library subject is shown by its mount, `/plain`, and an executable by its name, `plain`; a subject with nothing selected prints its compile and nothing more (`curios/src/test_runner.rs`, `curios/src/report.rs`). `curios/tests/harness_cli.rs` reads those streams off the spawned binary.
- **Both JavaScript suites run under Node.** `curios-browser/src/page.test.mjs` has the released compiler write a page and imports its loader, calling `start` with the program's bytes; `harness.test.mjs` runs the bundle's `compile` and `run` against scripted hooks ([`curios-browser/README.md`](../../../curios-browser/README.md)). The bundle's `compile` builds `EntryTail::Program`, so no test program crosses it. The README's rejection of a headless browser and a driver for the harness's own suite stands: this specification launches nothing.
- **The binary is spawned from `curios/tests/`.** `run.rs` and its siblings start `CARGO_BIN_EXE_curios` with piped streams; the in-process suites under `curios/src/tests/` cannot.

## Prior art

- **web-test-runner's manual mode** "Starts test runner in manual testing mode. Ignores browsers option and prints manual testing URL" ([CLI and configuration](https://modern-web.dev/docs/test-runner/cli-and-configuration/)).
- **testem** prints, in development mode, a URL that "is a normal page in Chrome, Firefox, Safari, etc."; its page "talks to the Testem server through a hidden iframe"; only `testem ci` launches browsers, and a job "relies on the exit code to fail" ([README](https://github.com/testem/testem/blob/master/README.md)).
- **Karma** serves a `client.html` that "connects back to the server via websockets", opens `context.html` in an iframe, bridges the two by postMessage and forwards what the iframe reports to the reporters ([How it works](https://karma-runner.github.io/5.0/intro/how-it-works.html), [client](https://github.com/karma-runner/karma/blob/a1049c6059db84ae7b14621d8df6a0db7b6d13cc/client/karma.js)).
- **jasmine-browser-runner** has `serve`, for "the browser of your choice", beside `runSpecs`, which drives one configured browser and exits nonzero on a failure ([Using Jasmine in the browser](https://jasmine.github.io/setup/browser.html)).
- **wasm-bindgen-test** drives a browser through WebDriver, polling the page's `#output` for `test result: ` and failing after a silent timeout ([headless.rs](https://docs.rs/crate/wasm-bindgen-cli/0.2.118/source/src/wasm_bindgen_test_runner/headless.rs)); with `NO_HEADLESS=1` it instead starts "a local server that you can visit in your Web browser of choice" ([browsers](https://github.com/wasm-bindgen/wasm-bindgen/blob/main/guide/src/wasm-bindgen-test/browsers.md)).
- **Dart's `package:test`** runs browser tests "in hidden iframes" ([README](https://github.com/dart-lang/test/blob/master/pkgs/test/README.md)): its host page reads the server's address off its own query, opens an iframe per suite, speaks to each over a `MessageChannel`, and rejects a window message whose origin is not its own or whose source is not the iframe it opened, since "a message on the Window can theoretically come from any website" ([host.dart](https://raw.githubusercontent.com/dart-lang/test/master/pkgs/test/tool/host.dart)).
- **Vitest's browser mode** has an orchestrator page that "only sets up iframes and doesn't actually import your code", one iframe per test file under `isolate`, a `BroadcastChannel` between frames, and a browser launched through a provider ([guide](https://vitest.dev/guide/browser/), [config](https://vitest.dev/guide/browser/config)).
- **Emscripten's `emrun`** with `--no_browser` only serves; a page linked with `--emrun` POSTs each stdout and stderr write to the server with a sequence number, `^pageload^` once it has loaded and `^exit^<code>` when it exits, the last synchronously "so we know for sure that the server has gotten the return code", and emrun quits "with the given process exit code" ([docs](https://emscripten.org/docs/compiling/Running-html-files-with-emrun.html), [emrun_postjs.js](https://raw.githubusercontent.com/emscripten-core/emscripten/main/src/emrun_postjs.js)).
- **On the wire.** A wildcard `targetOrigin` and an unchecked `event.origin` are the postMessage defects scanners flag ([ZAP](https://www.zaproxy.org/docs/alerts/220008-4/)); Vite's dev server was driven from any site through an unvalidated `Host`, a permissive CORS default and an unchecked websocket `Origin` ([CVE-2025-24010](https://db.gcve.eu/vuln/CVE-2025-24010)); Jupyter's server takes a per-run token because "access to the Jupyter Server means access to running arbitrary code" ([security](https://github.com/jupyter-server/jupyter_server/blob/main/docs/source/operators/security.rst)); the GC JS API: "If the value is an i31 reference, convert it to a JS number" ([MVP-JS](https://github.com/WebAssembly/gc/blob/main/proposals/gc/MVP-JS.md)).

Every runner above has one shape: a server the toolchain runs, a host page it serves, one frame per unit of isolation, a frame-to-host channel, a host-to-server channel, and one reporter that sets the exit code. The ones that serve a URL for any browser end with no exit code, and the ones that end with an exit code launch a browser; emrun alone does both, because its page tells the server when it is done. Here the selected tests are known before serving, so "every test has a verdict" is a condition the command can wait for, and the shape is taken whole, with Dart's discipline on the window and emrun's completion.

## Decisions

Settled 2026-11-01.

- **No browser is launched or assumed.** The command prints the address and waits; whatever opens it runs the tests — a person, a headless browser a script starts against the printed port, a device reaching the machine. Rejected: WebDriver and a driver binary, a dependency and a download for what any browser does by visiting a page; launching a named browser, a later convenience and not this specification; Node or jsdom in place of a browser, one with no DOM and the other a second DOM.
- **`/` is what the command runs.** For `run`, the program's page: its files at the root — `/index.js`, `/index.wasm`, a gateway at its page path — nothing redirected, and the address `http://127.0.0.1:8000/?arg=…`; `/` and `/index.html` are one resource. For `test`, the run: the runner at `/`, and the subject's page beside it as any static server places one, `index.html` being the page's own name for its document, so `/index.html?arg=<index>` is one test's page and its files stand at the root. The server reads the path and never the query, which is the page's. Rejected: a name per subject, which the library and the package's own `exe.crs` executable share, and whose nested layouts need a claim check across pages; the server reading the query to tell the run from the page, a peek into the page's interface; the redirect, with nothing left to point at; a runner written as a file of the page; a test mode in the loader, which cannot know the tests.
- **One subject at a time, in plan order.** The command builds every subject before it binds, serves the first subject with a test selected at the root, and switches to the next when the last report of the current one is taken; `no-store` and a fresh iframe per test make the next iframe fetch the next subject's files, and the runner removes an iframe once its report is taken, so no realm outlives its subject. A subject with nothing selected prints its compile and is never served. Rejected: every subject's page served at once, which needs names; a second serve inside one run.
- **One iframe per test, one at a time, in the plan's order.** A fresh iframe is a fresh realm — a fresh document and fresh instances of every gateway module — the browser's form of native's one instantiation per test. Rejected: one page running every test (`run_all`), where a trap or an exit in one ends the rest; a loader instance reused across tests, which shares gateway state; several iframes at once, which share one main thread and interleave the console.
- **A framed page posts to its parent.** When `globalThis.parent` is a window other than its own, the loader posts `started` before it runs and the outcome after, each with `"/"` as the target origin, which names the caller's own origin and needs no `location`; the outcome is `{stdout, stderr, exitCode, trap, held}` with the streams the loader kept copies of while it wrote them. It is a contract of the page, stated in usage, that any embedder may use. The runner admits a message only from the window of the iframe it opened, at its own origin, and reports a page whose document loaded with no `started` posted as trapped, naming the loader that did not start — the one way a gateway that fails to import could otherwise stall a run that has no timeout. Rejected: a wildcard target origin, which hands a program's output to any site that frames its page; reading the browser's console; the loader posting to a server, a test mode in the ordinary page.
- **The harness reads the entry's word.** `run` resolves `held`: `true` or `false` where the entry returned a Bool word, and `null` where it answered none — a program's unit, an exit, a trap. A test program's entry answers a word whenever it returns, so a report with no trap and no word is an exit, read with its code. Rejected: a second door beside `run`, where a test page is the ordinary page; a trap on a return of no word, which every program's unit is.
- **`POST /` reports the step in hand.** A report is a JSON body under `Content-Type: application/json` naming the run's token, the subject's and the test's index in the plan, and the posted outcome, its streams in base64; the step in hand is the first unreported in plan order, and a report for any other step is answered with nothing and ignored, a duplicate's and a second tab's alike. The reply carries the lines the command wrote for the report, on each of its streams, and the next step, or none when the run is complete. A body without the token, without the type or past a bound is refused; the type makes a cross-origin post preflight and fail before the token is read, and the token is minted per run from `getrandom` and rendered into the runner alone. Rejected: a websocket, a dependency for a bounded, one-way report; the command polling the page; a route of its own, where `/` is the run; buffering reports out of order, which the step in hand makes needless; an unauthenticated route, which any page the machine's browser loads could file verdicts through.
- **One printer, two sources.** The test runner is a plan, the subjects compiled with their records; a printer, which takes a subject's beginning and each test's end in plan order, prints what native prints today and tallies; and a source: native runs each test in process, the browser serve takes each from a report. A report's outcome maps to `TestEnd`'s vocabulary once, in Rust, beside native's: a trap is `trapped` with its text, a `held` a verdict, and anything else `exited` with its code. The runner page shows the lines the reply carries, so the page and the terminal are one rendering. Rejected: a second report path for the browser; a renderer of the lines in JavaScript.
- **The terminal shows what native shows**, from the same inputs, in the order the build imposes: `Processing`, `↳ Compiling` and `↳ Linking` for every subject, then `↳ Serving   http://127.0.0.1:8000/`, then for each subject with a test selected `↳ Testing` as it is served, one line per test as its report is taken, a failure's report indented beneath it with the test's body as written, `↳ Tested` with its tally, and the final tally. Refusals come before the listener binds: a `--filter` matching no test, named as native names it, and a reached row no gateway answers, as `compile` refuses it.
- **The run is complete when every selected test has one verdict.** The command then stops serving and exits with the tri-state; a rerun is the command run again, the rule `run --target browser` already states: "nothing reloads". Rejected: serving on after the report; a second run inside one serve, whose semantics would have to be defined; a timeout, since a page may be opened an hour later and the signal that stops the command is the timeout.
- **`no-store` stays.** Each iframe fetches its subject's files again over loopback, and a changed program keeps its one meaning: run the command again.
- **The `arg` key is stated once.** `curios-browser` owns it beside the page's three file names and its `output` id, renders it into the loader and the runner as it renders `output`, and `Served::url` reads it; usage spells it for the person who types it. The key stays: a keyless query cannot tell `?` alone from one empty argument, and it claims every key, where `arg` leaves the rest of the query to a gateway.
- **A subject's page is the ordinary page.** `index.html` and the files beside it are what `compile --target browser` would write for the subject's test program and nothing else; the runner is rendered when the command serves and written nowhere.
- **`--port` and `--filter` as they are.** `--port` as `run`'s, refused beside the native target; `--filter` as native's.

## Stages

### 1. The page hands back a verdict

One commit.

- `run` resolves `held` as the decision states, read off the entry's yield under either protocol.
- The loader keeps a copy of each stream as it writes it; when framed it posts `started` before `run` and the outcome after, to `globalThis.parent` with `"/"` as the target origin, and goes on writing the element and the console.
- `curios-browser` states the `arg` key once and renders it into the loader; `Served::url` reads it.
- Check: `harness.test.mjs` cases reading `held === null` off a program under each protocol and off one that exits; `page.test.mjs` cases starting a written loader under a stubbed `globalThis.parent` and reading `started`, then the outcome with the streams it kept, and one with no parent posting nothing.

### 2. One printer, two sources

Two commits: the printer apart from the native source, native's output unchanged; then the target.

- `test_runner.rs`: the plan, the printer taking a subject's beginning and each test's end, and the native source, with the lines and tallies as today — a pure reshaping, held by `curios/tests/harness_cli.rs`.
- `Mode::Test` takes `--target` and `--port`; `--port` beside `native` is refused as `run` refuses it.
- `TestSubject::compile` takes the target: for a browser it finishes through Binaryen alone, as `payload_of` does for `Runs::Browser`, files the payload under `Runs::Browser` with `TestPayload`'s field named for what it holds, and `Tested::page(subject)` links its rows through `linked_of` and lays the subject out through `curios_browser::page`, refusing a reached row with no browser table as `compile` refuses it; `Tested::loaded` stays native's. `curios-prelude/tests/std.rs` follows the signature.
- Check: `curios/src/tests/` cases building a test subject for the browser and asserting its page files, and a row stating only `[foreign.native]` refused naming the row and the table; a `curios/src/cli/tests.rs` case parsing `test --target browser --port 0`; a `curios/tests/` case asserting `--port` beside the native target refused.

### 3. The page at the root

One commit.

- `Served` loses its name; `/` answers `index.html` and every file of the page stands at the root; the redirect goes; `Served::url` prints `http://127.0.0.1:<port>/?arg=…`.
- Check: `curios/src/serve/tests.rs` revised to the root; a `curios/tests/` case starting `run --target browser --port 0` on a package, reading the port off the `Serving` line, fetching `/`, `/index.html`, `/index.wasm` and a gateway, and asserting `405` with `Allow: GET` for a `POST`.

### 4. The run at the root

Two commits: the server's side, then the command's.

- `curios-browser`: the report and the reply as types, parsed and rendered there; and the runner — `src/runner.mjs`, the loop over steps, admitting a message by its source and origin, removing each iframe once reported, reporting a loader that never started — embedded by `templates/runner.html` with the token and the first step as one JSON block, as the loader's `page` is.
- `serve.rs`: a site holding the root document, the current page's files and whether `POST /` is taken; a body read under its `Content-Length` to a bound; the report route answering as the decision states and switching the page on a subject's last report; completion signalled to the command, which exits once the last reply is written.
- `main.rs` and `test_runner.rs`: the browser source — every subject built, the refusals before the bind, `↳ Serving`, the printer fed by reports, the tri-state.
- `link.rs`: the native refusal of a browser-only row names `test --target browser` as what runs the code that reaches it, beside the stand-in; `curios/tests/bundle.rs` follows.
- Check: `curios/src/serve/tests.rs` cases — a report without the token, without the type or past the bound refused, one for a step not in hand answered with nothing, a duplicate ignored, the page switching on a subject's last report, completion ending the serve; a `curios/tests/` case starting `test --target browser --port 0` on a package with a library and two executables, one with nothing selected, fetching `/`, posting each step's report as the runner would with a pass, a failure, an exit and a trap, and reading the terminal's lines and the exit code; a `page.test.mjs` case starting the command on a package with a gateway and a test reaching its row, fetching the page's files, starting its loader under a stubbed parent with the first step's index, reading `held === true`, and posting the report; Node cases for `runner.mjs`'s pure parts.

### 5. Documentation

One commit.

- `documentation/usage.md`: the `test` section and the surface table gain `--target` and `--port`; "Serving a page" states the root, `--port 0`, and that a test serve answers the runner at `/` and the page at `index.html`; "Exit codes" states that `test --target browser` serves until its report is complete; "The page" states the post a framed page makes and revises "Each side is tested with its own tools" to name the seam's test.
- `curios-browser/README.md` gains the decisions: a framed page posts to its parent, the harness reads the entry's word, and a test run is one runner over one page at a time reporting to the command that serves it, with the rejections above.
- [A browser page is closed and laid out as its packages](../../design/tools/a-browser-page-is-closed-and-laid-out-as-its-packages.md) states that `run --target browser` serves the page at the root; [A foreign row states a delivery for each target](../../design/tools/a-foreign-row-states-a-delivery-for-each-target.md) gains, in its rationale, that the seam is tested by `test --target browser`.
