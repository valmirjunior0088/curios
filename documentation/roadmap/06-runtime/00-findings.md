# Runtime: findings

- **A stream's sending half cannot be ended before the close, so a TLS peer is never told and an early answer is lost.** `OsHost::handle_close` drops the resource (`curios-runtime/src/os_host.rs`), and no row ends a socket's sending half: nothing in `curios-runtime` calls `rustls`'s `send_close_notify`, and `tls_read_outcome` reads a peer's missing alert as the end of the stream. RFC 9112 §9.8 has a client and a server each send a closure alert before closing, and counts a reply framed by the connection's close as whole only where the alert arrived; §9.6 has a server that answers before it has read its request end its sending half and read on, since a close over unread bytes resets the connection under the answer. Over loopback, a reply written ahead of an unread request body and followed by `Handle/close` reaches a peer that writes its request whole before it reads as `other(104)`; where the handler reads and discards until the peer falls quiet, the reply arrives, late by that wait. Fix: one row that ends a handle's sending half — the socket's `shutdown` of its write side, and for a TLS stream a `close_notify` queued for `handle_flush` ahead of it — answering at once as every row but `handle_poll` does, `not_found` for a kind with no sending half, surfaced as `tcp/Socket/finish`, which `Socket/with` and `Listener/serve` call before they close; and `tls_read_outcome` answers a missing alert as `tls` once `/std/http`'s client reads a reply by its framing ([HTTP framing](../08-standard-library/01-http-framing.md)), since a client that reads every reply to the close would fail on each peer that skips the alert. Check: the mock host records the row and a test holds `Socket/with` and `Listener/serve` to calling it before the close; over loopback the early answer above arrives with no wait; the browser harness denies the row as it denies `socket_open`. Size: medium.
- **A reset connection has no name.** `/std/Io/Error` names nine statuses, and a peer that resets the connection reaches a program through the errno lane, as `other(104)` on Linux (`curios-runtime/src/host.rs`'s `failure_from_error`). `curios-abi`'s `codes::errno` names an errno only where both release targets give it one value, and `ECONNRESET` is `104` on one and `54` on the other, so a program telling a reset from any other failure spells a number per system. Fix: `status::CONNECTION_RESET` beside `CONNECTION_REFUSED`, answered for `ErrorKind::ConnectionReset`, mirrored by `/sys/status` and decoded as `Io/Error/reset()`. Check: over the mock host a scripted reset reads as `reset()` and shows as `reset`, and `curios-abi`'s roster test holds the new status to its rows. Size: quick.
