# Theory: findings

- **A bare reference has its hidden binders inserted at an expectation stuck on a metavariable.** [Plicity is part of function identity](../../design/theory/plicity-is-part-of-function-identity.md) inserts a bare reference's hidden binders only where a hidden-headed function type could never convert, so that insertion changes no accepted program and a flexible expectation keeps the polymorphic value whole. `insert_implicits_on_check` (`curios-elab/src/elaborate/metavar.rs`) reads an expectation as flexible through `flexible`, which answers only for an unsolved metavariable or an application headed by one. An expectation that waits on a metavariable under an elimination, `F(?b)` reducing to a match on `?b`, is therefore read as rigid and the insertion fires; its comparison against the stuck match waits rather than refusing, so the inserted shape is committed. Over `let take(@b: Bool, f: F(b), e: Eq()(b, true)) -> Nat`, with `F(true)` reducing to `(@A: Type, x: A) -> A`, `take(id, Eq/refl())` is refused as `inferred: (x: ?) -> ?`, `expected: (@A: Type, x2: A) -> A`, while `take(@true, id, Eq/refl())`, `take(pass(id), Eq/refl())` and the same parameters with `e` first are all accepted. `stuck_on_metavar` (`curios-elab/src/typing.rs`) is already the reading of the four shapes a reduct waits on a metavariable in for the checked introduction forms. Fix: `insert_implicits_on_check` holds an expectation flexible where `stuck_on_metavar` answers, in place of `flexible`; `check_witness_domain` (`curios-elab/src/elaborate/apply.rs`), the other reader of `flexible`, is read against the same question. Check: `bare_reference_keeps_its_type_at_an_expectation_stuck_on_a_metavariable` beside `bare_reference_keeps_its_type_at_a_hidden_expectation` in `curios/src/tests/binders.rs`, running the program above to `1`; `cargo xtask workspace lint`. Size: one commit.
- **An arm's solution for an index variable stands at the index's type, above the variable's, so the kernel, which substitutes it, refuses what the elaborator, which refines, admits.** [An arm is checked in a context specialized by index inversion](../../design/theory/an-arm-is-checked-in-a-context-specialized-by-index-inversion.md) runs one unifier for both checkers, `curios-analysis`'s `invert`, whose second direction (`invert_indices_outer`) refines an outer variable to the target it must equal, and its Rationale reads the two applications as one answer: "What differs is how each checker applies the solution — the elaborator through its refinement store, the kernel by substitution". An index variable is checked at the index's domain by subsumption, so its own type may sit below it, and the case target is typed at the index, so nothing relates the target's level to the variable's. In `induct Code: (Type) -> Type | big(): (Type) end` and `pub let f(X: Type, c: Code(X), x: X) -> X = match c | big() => id(@X, x) end;`, `X: Type.{u}` stands at `Code.{v,w}`'s index `Type.{v}` with `u ≤ v`, the target `Type.{w}` has `w + 1 ≤ v`, and the unifier solves `X := Type.{w}`, whose type `Type.{w+1}` is not below `Type.{u}`. The kernel's `check_arm` (`curios-cert/src/kernel/infer/eliminate.rs`) substitutes it through the arm, so `id.{u}(@X, x)` becomes `id.{u}(@Type.{w}, x)`, typed again and refused: "the kernel refused /f: expected `Type.{u}`, found `Type.{w+1}`"; the elaborator keeps `X` at its declared type and admits. The program is sound, since the arm is reached only at an instance where `X` is `Type.{w}`, which needs `w + 1 ≤ u`. No `False` follows: every position the substitution reaches that the kernel reads is typed again, so the cost is the refusal. `pub let f2(X: Type, c: Code(X), x: X) -> Type = match c | big() => {x} end;`, which needs the solution to read `x` as a type, is admitted by both. Fix (sets), two ways: (1) the second direction solves an outer variable only where the judge holds the target's type below the variable's, and leaves it unsolved otherwise, one rule in the shared unifier so both checkers agree by construction, at the cost of refusing `f2` in both; or (2) the kernel keeps the variable and holds the solution as a case equation where its type is not below the variable's, as an expression scrutinee's is, which refuses nothing new but is a second way of applying one solution, where [Case equations and their key](../../design/soundness/case-equations-and-their-key.md) calls an equation an elaboration convenience rather than a certification contract. Check: `f` and `f2` held to the verdicts decided, in both checkers, beside `curios`'s `tests::board::index_tests`; `cargo xtask workspace lint`. Size: one commit.
