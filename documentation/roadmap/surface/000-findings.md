# Surface: findings

- **In a group of families, a name unbound in the first family's parameter type is reported as the sibling its cases name, without the import hint.** `induct A(n: Nat): Type | mkA(other: Zed(true)) and Zed(m: Bool): Type | mkB(other: Third(true)) and Third(k: Bool): Type | mkC(other: A(0)) end`, with `Nat` not imported, reads ``Zed` is not in scope`` at the span of `Nat` at `0d7d13c32`, while the same `Nat` in a family alone reads ``Nat` is not in scope`` with the hint ``Nat` is `/std/Nat`: write it absolute, or `use /std/{Nat};``, and an unbound name in a later member's parameter is reported as itself; so the refusal names a name the program spells correctly, against [A diagnostic spells what its reader can write](../../design/tools/a-diagnostic-spells-what-its-reader-can-write.md). The lookup that fails is not located: a sibling's, raised while the group's first member is registered, would replace the parameter's own refusal and keep its span. Fix: report the unbound name the parameter spells, where it stands, with the hint a declaration alone gets. Check: a `curios` diagnostic test putting the group and pinning the name and the hint beside the lone family. Size: one commit.
- **Core text's reader reads a `max` that names one head or one constant twice as its last part, a level below the one written.** `level_read` in `curios-surface/src/core_text/sort.rs` folds each part of a `max` into a `Level` by assignment — the constant replaced, an atom's offset inserted over the one before — where `Level::max` keeps the larger, so `max(u + 1, u)` reads as `u` and `max(5, 0)` as `0`. The printer never writes a head twice, so the round trip holds, but a hand-written text is judged at a level its author did not write, against [`curios-surface`'s README](../../../curios-surface/README.md#core-text-is-core-in-the-programs-grammar-and-reads-back-as-the-term-it-writes), whose reader refuses by name a form Core text refuses: at `6b7b91bf7`, `#{universe_context = {parameter_count = 1, constraints = [max(u + 1, u) <= u]}} let /lastwins : #NatType = 0;`, a loop as written, is admitted by the kernel where `[u + 1 <= u]` is refused `UnsatisfiableUniverses`, and `(A: #{level = max(u + 1, u)} Type) -> #{level = u} Type` reads its domain at `u`. A board witness or a held attack written as Core text can so be judged at a level other than the one its comment argues from. Fix, one of two: refuse a `max` naming one head or one constant twice, by name and where the part stands, the canonical form holding one part per head (recommended, as the reader refuses every other form the printer never writes); or fold the parts with `Level::max`. Check: a `curios-surface` Core text test reading `max(u + 1, u)` and `max(5, 0)` and expecting the refusal. Size: one commit.
- **`wonder --stage` panics printing a library whose items are a recompile's version.** `Implied::of` (`curios-surface/src/spelling.rs`) maps each declared name to its item's count from `items.iter().enumerate()` and reads `&items[index]`, but `Items` is indexed by place: a made or a stored module's places are `0..len`, so a count is a place, while a recompile's version (`Held::Placed`) spaces its places, so count `0` names no place and `Items::entry`'s `.expect` panics, "a place the version holds" (`curios-core/src/items.rs:687`). The cause is read off the code and not yet confirmed by a fix. Seen with the released 0.16.18 (tag `0d7d13c32`): in a copy of `curios-prelude/std` from the release tree holding no `.curios/`, `curios wonder --stage core-elab lib.crs` exits 101 on its first run, having filed a verdict slot, and exits 0 printing the library on every run after, a plain `curios wonder lib.crs` first not helping; the backtrace runs from `curios_surface::spelling::print_items` through `Items::index`. Core text printing first ships in this release (`b3cb78339`), and the curios-papers harness counts the standard library through this query over a store a fresh CI checkout holds empty, so its CI failed at that step on both attempts of run 42039849860 where 0.16.17 ran it green. Fix: read each item by its place in `Implied::of`, walking `items` by place rather than by count. Check: a `curios-surface` test printing a version whose places are spaced, and the reproduction above over the tree. Size: one commit.
- **Uncertain: Core text's writer could build the tree the program printer lays out, so its layout is stated once.** The writer (`curios-surface/src/core_text/`) builds a layout of its own from Core terms, while its reader parses the same text into a `Term<CoreText>`, so Core text's layout is written by the writer and, wherever a printer lays out that tree, again there: a formatter over a `.crsc`, which keeps the comments a file holds, can print only the tree. A writer that builds the tree, the reader's inverse, leaves one layout to the printer and makes formatting a printed term its round trip. Not known: whether the tree can hold what the writer writes under a reader's spelling, which is no Core text — a name's instance as `.{…}`, an intrinsic as its operator — or whether those keep a path of their own; and what a writer building trees costs a dump that is bounded as a report is. Settled by: a scratch writer building the tree for every unit of the prelude, laid out by the printer to the text the writer writes today (`every_unit_of_the_prelude_reads_back_from_its_core_text`), and a reader's spelling of the same terms through it. Size: unknown.
