# Specializing on a known function, so an abstraction stops costing an indirect call

This document specifies recovering the identity of a function that reaches its call site as a value, so the call through it becomes direct and the machinery that already exists dismantles what sits on top of it.

It succeeds the return protocol, whose measurement scoped it. That work removed the allocation `/syn/Str/classify` pays to return a variant and moved `programs/parse_digits.crs` by one to two percent, because the per-character cost that dominates is an indirect call and an `Option` no return protocol can reach.

## Problem

Curios has no dictionary passing to remove. A `satisfy` witness is resolved during elaboration and spliced into its consumer, so `/syn/Monad/bind` is already `/std/State/bind` before anything runs, and `State/bind` is then inlined outright. **Neither `Monad` nor any witness value survives into the optimized CPS of `programs/state_monad.crs` or `programs/parse_digits.crs`.** What survives is narrower and more ordinary: a function that arrives as a value, at two boundaries that are not one problem.

**As an argument.** `/std/Str/fold` is called twice, from `/std/Nat/of_str` and from `/std/Str/trim_bounds`, each passing a different step function, so the parameter joins to a conflict and every call through it stays indirect — once per character of every parse. Each pass declines for its own structural reason: `specialize_scc_calls` requires a recursive SCC, and `Str/fold` has no self-edge in the known-callee call graph at all, since its recursion runs through closures jumped into a local continuation; `specialize_call_patterns` and `specialize_jump_patterns` both key on `tagged_tuple_values`, and a `CpsAtom::Fun` is not one; `contify_calls` needs a single external call site and there are two; `inline_known_calls` refuses a multi-site callee above eight nodes.

**As a return value.** `State(S, A)` is a struct over `(S) -> {A, S}`, so a `State` action *is* a function and `bind` builds a new one. In `programs/state_monad.crs` the loop returns `Fun(/std/State/bind/1)` from one arm and `Fun(/std/State/pure/1)` from the other, and `State/bind/1` applies the result of the recursive call as `apply Closure`. No pass reaches that: a call's resume is not an `ApplyCont` or `Switch` edge, which is the same structural fact the return protocol was built on. That protocol's own eligibility already names these functions, pinning them because their return edges carry a function reference where it needs a construction.

**What is not missing.** `rewrite_atoms` already promotes `CpsCallee::Closure(v)` to `Known(f)` the moment `v` is known to be `Fun(f)`, and inlining, contification, projection forwarding, dead-binding elimination and the return protocol all run behind that promotion. The absent fact is the one that would make a function known where its sites disagree.

**Every count above was surveyed at `d771eaac`.** `main` has since edited `/std/Str.crs`, `/std/Str/utf8.crs`, `/std/Parse.crs` and `/std/Nat.crs` — which is where `Str/fold`, its callers, and the UTF-8 walk all live — so the call-site count, and with it the disagreement the argument boundary rests on, is a fact about files in flight. The shape is not in doubt; the arithmetic is. **M1 re-surveys before relying on it**, and none of these figures should be quoted onward without that.

**Precondition, and not a milestone here.** Every routine that copies a body declines one nesting a `LetFun` or `RecInit`, and a nested lambda is what higher-order code is made of — `Str/fold`'s body *is* one. Lifting that is a separate capability with its own corpus-wide risk and its own measurement, tracked in the roadmap beside this document. **Nothing below can be built until it lands**, and it is stated here only so the dependency is not discovered twice.

## Design

**A known function argument cannot be rebuilt at the clone's entry, and does not need to be.** The tagged-tuple case binds its constructor back with a `LetValue` and threads the dynamic fields as fresh parameters; there is no analogue, because `CpsValueExpr` is `Literal`, `List`, and `Tuple` — nothing binds a value to a function reference. The model to follow is `specialize_scc_calls`': clone, repoint the disagreeing site, and let the ordinary propagation finish, since the clone then has one caller passing `Fun(f)`, `record_known_literals` records the parameter, and `rewrite_atoms` devirtualizes. Simpler than the tuple case — no rebuild, no field threading, no argument splicing — but by a different route than the clone binding it.

**The jump case cannot borrow that model, because nothing propagates into a continuation parameter.** `known_values` builds its inputs from `ApplyFun` sites alone, so a known function jumped into a continuation establishes nothing. That clone must substitute the reference for its parameter directly and drop the parameter, which the existing global substitution already performs — including the closure-callee promotion — once the clone's fresh parameter is mapped to `Fun(f)`. One idea, two pieces of work.

**Two profitability gates, mirroring the two that exist.** `deconstructs_param` asks whether a body projects a field out of a parameter; the analogue asks whether a body *applies* it, and must look for `CpsCallee::Closure(param)` explicitly, since a closure callee is not an atom and `visit_atoms_mut` does not reach it — the exception `demand.rs` and `analysis.rs` already carry. `continuation_projects` gets the same analogue over a continuation body.

**The growth budget has to be chosen rather than inherited.** `specialize_call_patterns` caps a clone at `BRANCH_SPECIALIZATION_GROWTH_LIMIT`, twenty-four live nodes, calibrated for peeling one constructor off a small callee; `specialize_scc_calls` uses `SCC_CLONE_NODE_LIMIT`, two hundred and fifty-six. A UTF-8 walker is not a twenty-four-node function, so inheriting the smaller limit would decline the target while appearing to support it. Function specialization is bounded by how many distinct functions reach a parameter rather than by the callee's size, so it takes the larger limit, and the module-wide clone budgets bound the total unchanged.

**The return boundary is deliberately not designed here.** Making a returned function direct means knowing which functions a call can return and dispatching on that at the call site — the closure analogue of what the return protocol did for constructions, needing a set-valued fact where the protocol needed a syntactic one. Whether it is worth building at all is a question M3 answers, not this section.

## Milestones

- **M1 — a known function argument is a call pattern.** Extend `specialize_call_patterns` to recognize `CpsAtom::Fun` beside a tagged tuple, keyed on `(callee, index, function)`, cloning and repointing without a rebuild and leaving the parameter to `record_known_literals`. Gate on the body applying the parameter; take the larger node limit. *Acceptance: a fixture whose callee is called from two functions with two different function arguments emits a direct call in each clone and no `call_ref` survives in either, failing before and passing after; the emitted module validates before Binaryen sees it; and the emitted module's size is recorded, since a clone is a copy.*
- **M2 — a known function reference is a jump pattern.** The same for `specialize_jump_patterns`, substituting the reference into the clone and dropping the parameter, since no propagation reaches a continuation parameter. This is what reaches `/std/Str/fold`'s own recursion, which carries its next step through a continuation as a value. *Acceptance: a join entered with two different function references and applying its parameter emits a direct call in each clone; size recorded as above.*
- **M3 — what M1 and M2 bought, and whether the return boundary is worth building.** A `Stage::Cont` survey of the corpus: which functions stop escaping, which then contify, and whether `/std/Nat/of_str/1`'s per-character `Option` falls to the return protocol — its return edges are already visible constructions, so the prediction is that it does, and the survey decides it rather than assumes it. Then re-time `programs/parse_digits.crs` with the passes toggled and nothing else changed. *Acceptance: the survey reports the escape and contification deltas; the timing and the size delta are recorded beside a probe that reproduces them, never in prose.*

**The stopping rule.** `programs/state_monad.crs` and `programs/state_manual.crs` compute the same result and differ only in abstraction, which is what they were written for. **If M3 finds that gap closed, the return boundary retires unbuilt and this document retires with it.** If the gap survives, the return boundary is restated as its own specification, scoped by what M3 found and not by what this one guessed. The predecessor's history is that specifying a mechanism ahead of its survey got the shape wrong twice; the difference here is that the survey is allowed to end the work rather than only to scope it.

## Non-goals

- **Dictionary passing, and any witness-directed specialization.** There is nothing to specialize: elaboration resolves the witness and inlining removes the wrapper, verified by the absence of any `Monad` in the optimized CPS of both monadic programs.
- Defunctionalizing every closure in the module. The target is a closure whose function is *statically known at some site*, not the general case.
- Re-keying the closure type families, which stay single-result and arity-keyed, and which is what keeps an escaping function out of the return protocol.
- Any change to what Core, Ersd, or the kernel decide. This is a backend representation question throughout.
- Raising `MULTI_SITE_INLINE_LIMIT`. It was probed against exactly this and cannot help: no inline budget devirtualizes an `apply Closure`.

## Rejected

- **Strengthening `curios-cont`'s call graph instead of teaching the specializers a pattern.** `analyze_calls` records `Known` callee edges only, which is precisely why `Str/fold` reads as a non-recursive singleton and why the SCC specializer skips it; `curios-ersd`'s reference graph already carries the nesting edge that would make such recursion visible. Adding it here would make more functions read as recursive, and `known_values` deliberately skips recursive functions when recording known literals — so the change buys SCC eligibility at the cost of constant propagation elsewhere, on a corpus where the propagation is known to pay and the eligibility is speculative. Reconsider if M3 finds the cloning insufficient.
- **Doing it in `curios-ersd`, where the lambdas are still semantic.** Not for want of the fact — that crate's analysis carries a *better* reference graph than Cont's, nesting edges included. For ownership: devirtualization, inlining, contification and the return protocol all live in Cont, and a specialization whose whole payoff is unlocking them belongs beside them rather than one stage upstream of all four.
- **Treating the two boundaries as one mechanism.** The argument boundary is a clone whose parameter propagation resolves; the jump boundary is a clone whose parameter must be substituted; the return boundary needs a fact no analysis computes. Specifying them together would price each at another's cost.
- **A general control-flow analysis first.** A 0-CFA over function values would subsume all three boundaries and is the principled shape, but M1 and M2 are two existing passes recognizing one more atom, and a 0-CFA would still need cloning to act on what it found. It is the answer if M3 says the return boundary is worth building, not before.

## Tests

- A fixture whose callee takes a function parameter, is called from two functions with two different function arguments, and is too large to inline — the intersection the Problem section identifies — asserting each clone emits a direct call and no `call_ref` survives in either. It must fail before the milestone and pass after, which is what distinguishes the fix from a budget change.
- A continuation analogue: a join entered with two different function references and applying its parameter, asserting the same.
- The gates refuse where they should: a callee that merely stores or forwards its function parameter is not cloned.
- **A fixture that reaches the standard-library fold.** Every existing structural fixture takes its taint from `proc/args!` and never reads standard input, which is why the return protocol's own probe reports zero on all of them; a claim about `/std/Str/fold` needs a fixture that calls it.
- Inherited, because every new client is exposed to them: a value free in another function's body stays boxed, and the emitted module is validated before Binaryen sees it.

## Retirement criteria

Before this specification is deleted: the applies-this-parameter gates, the clone keys, and which node budget governs each are recorded where the specializers state their existing ones; M3's survey, timing and size delta live beside a probe that reproduces them; the stopping rule is applied rather than deferred, so the return boundary is either restated as its own specification with its open question named or recorded as retired unbuilt with the figure that retired it; the roadmap subitems are checked unlinked summaries; and no reference to this filename remains.
