# A test is a declared description, and a proof is a `let`

**Decision.** A test is declared — `test name = body;`, a contextual keyword as `satisfy` is — and is a name and a description with nothing between them: no parameters, no parentheses, and a body that is a `/std/Test`, whose representation is private to its module, built through the combinators it exports (`assert`, `equal`, `all`, `perform`, `try`) and eliminated only by `Test/main`. Its verdict is computed when it runs — `passed`, `failed`, `trapped` or `exited N`. A claim about every instantiation is not a description and nothing that runs decides it: it is a proposition, so it is an ordinary `let` whose type states the claim and whose body proves it, checked wherever its unit is — `let _right_identity(n: Nat) -> Eq()(n + 0, n) = Eq/refl();`, the leading `_` marking a declaration that exists for its type.

A test lowers to a definition of kind `Test` and type `() -> /std/Test`, collected per unit in `Module::tests` in declaration order. Asked for a test compilation, the elaborator replaces the unit's final term with `Test/main([("path", thunk), …])` over its registered tests, built in Core once the unit's items have elaborated, checked against `Io({})` as every tail is, and judged by the kernel like any program. `curios test` runs each test in an instantiation of its own, with `[argv0, index]` as its arguments, so one test's effects, traps and exits never reach another, and the selection protocol is spelled once, in Curios, in `Test/main`. `wonder diagnostics` asks a library through the same tail.

**Rationale.**

- **Every registered item kind has its keyword; `let` registers nothing.** Discovery by type, name or attribute would make a `let` register, and discovery by type would run every nullary `Test`-valued helper as a test the day it is written. A declared test keeps an identity through the pipeline — its path names it in the report, the filter and `wonder tests` — and its collection order is the schedule.
- **Synthesizing the tail in Core** keeps the program the runner executes inside the ordinary soundness story, elaborated, zonked and certified, without changing the surface language; a unit with no tests compiles to `Test/main([])`, which exits 0.
- **The description is private for the reason `Io` is**: a consumer can build a `Test` and do nothing else with one, so the harness's rungs — a `verdict` decided at run time, an `action` performed in `Io` — change without any consumer having assumed a shape. A `Bool` body says nothing about how it was decided.
- **A proof is better stated as a `let`.** The type states the proposition and the body the proof, checked on every build, where a proof passed to a test combinator buries the proposition in an argument list and reports a payload-free tag about a fact established at elaboration. A broken proof fails the build rather than reddening a line; the price is that `curios test` shows no inventory of proofs.
- **The thunk stays in the lowering** because `Test/main` holds every test in one list and forces only the one its index selected. **`Test/perform` takes a thunk** because a `!` reads its monad from its region, regions open only at value bodies, lambda bodies and match arms, and honoring an inline `Io(Test)` argument would hoist the effect into the surrounding pure region; the lambda `() =>` is a fresh region.

**Rejected.**

- **Parameters meaning a theorem**, decided by asking whether the body converts with a proof tag under the whole telescope, or **dispatch on a declared type**, `test f(n: Nat) -> Eq()(n + 0, n)`: each gives `test` two meanings where a `let` already states a proof, and a verdict is a fact about one instance while a telescope quantifies over all.
- **A second keyword**, `theorem f(x)` beside `test f()`: the theorem/example split does not run along arity, and with proofs in `let` there is none left to name.
- **Empty parentheses**, `test foo() = …`, which spell a telescope the form does not admit.
- **Checking the written entry and the synthesized tail together**: the tail pairs each declaration with its path and raises nothing of its own, and would have to be carried to finalization, where a witness premise is decided.
- **Verdict caching**: a test payload is filed in the store like any program's, under a reserved executable name, but a verdict is a fact about an execution, and the store holds only what sources determine.
