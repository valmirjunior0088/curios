# A test is a declared description, and a proof is a `let`

**Decision.** A test is declared — `test name = body;`, a contextual keyword as `satisfy` is — and is a name and a description with nothing between them: no parameters, no parentheses, and a body that is a `/std/Test({})`, whose representation is private to its module, built through the combinators it exports (`pure`, `bind`, `assert`, `equal`, `all`, `perform`, `try`, `using`, `scope`, `timeout`) and eliminated only inside that module: by `Test/main`, and by its witness of `/std/Program`, which performs one that closes a program. Its verdict is computed when it runs — `passed`, `failed`, `trapped` or `exited N`. A claim about every instantiation is not a description and nothing that runs decides it: it is a proposition, so it is an ordinary `let` whose type states the claim and whose body proves it, checked wherever its unit is — `let _right_identity(n: Nat) -> Eq()(n + 0, n) = Eq/refl();`, the leading `_` marking a declaration that exists for its type.

A test lowers to a definition of kind `Test` and type `() -> /std/Test({})`, collected per unit in `Module::tests` in declaration order. A unit holds its tests only where it is compiled tested: as the subject of `curios test`, and of every question `wonder` answers, its lints included. Built — for a program, or for the units compiled after it — it lowers none, so a test costs its unit's builds nothing. Nothing names a test: its path is its report line and what a filter selects, and its name binds nothing while staying unique among its module's declarations, so a build that leaves every test out means what it would with them. Asked for a test compilation, the elaborator replaces the unit's final term with `Test/main([("path", thunk), …])` over the tests in scope that a filter selects, every one where none is given — tests only the unit compiled tested holds — built in Core once the unit's items have elaborated, checked against `Io(Bool)`, the verdict `Test/main` answers, and judged by the kernel like any program. The unit holds every test it declares whatever the filter: which tests run is the program's, and what its tail does not reach is linked into nothing, so a filter narrows the back end, where most of a test program's cost is, and a tail scheduling none is built no further. `curios test` runs each test in an instantiation of its own, with `[argv0, index]` as its arguments, so one test's effects, traps and exits never reach another, and the selection protocol is spelled once, in Curios, in `Test/main`. The runner reads a verdict off what the entry hands back and never off an exit code, so a test that exits has reported nothing and is `exited N` whatever `N`. A question about a library compiles no tail, which raises nothing of its own.

`Test(A)` carries successful intermediate values and propagates the first failure without invoking its continuation. Its `Io` embedding preserves suspension; one generic `Try(M, E)` embedding requires a declared base embedding and `Show(E)`. Only `Test({})` closes a program or registers as a test, so an arbitrary successful payload is never silently discarded.

`Test/scope` and `Test/timeout` protect the complete interpretation of their function bodies. Internally, an assertion failure is an outcome carried inside `Io` until the enclosing scope has released its resources, then resumes propagating through `Test`. Suspension and cooperative cancellation follow `/std/Io`'s contract; a guest trap or process exit promises no guest finalizer.

**Rationale.**

- **Every registered item kind has its keyword; `let` registers nothing.** Discovery by type, name or attribute would make a `let` register, and discovery by type would run every nullary `Test`-valued helper as a test the day it is written. A declared test keeps an identity through the pipeline — its path names it in the report, the filter and `wonder tests` — and its collection order is the schedule.
- **A build holds no test, by its declaration.** A test weighs on its unit's build as any declaration does, elaborated, certified and erased with it, and nothing a build runs reads one. What is left out follows the declaration's form and never liveness: a helper only tests read stays in the build and is checked there as any declaration is, so deleting a test changes nothing a build checks.
- **Synthesizing the tail in Core** keeps the program the runner executes inside the ordinary soundness story, elaborated, zonked and certified, without changing the surface language; a tail scheduling no test is `Test/main([])`, which would run nothing and answer that every test held, so it is judged and built no further.
- **The verdict is the value the entry answers** because that is the one thing a test's body cannot produce: a body can exit with any code, print any line and trap, and a `Test`, being sealed, is eliminated by `Test/main` alone. An exit code is the program's own, as it is under `run`, so a runner reading one as a verdict would count a test that exits 0 before it asserts anything as passed; [Go](https://go.dev/doc/go1.16) fails a test that calls `os.Exit(0)` for the same reason.
- **The description is private for the reason `Io` is**: a consumer can build a `Test` and do nothing else with one, so the carrier's successful payloads, failures and suspended actions change without any consumer having assumed a shape. A `Bool` body says nothing about how it was decided.
- **A proof is better stated as a `let`.** The type states the proposition and the body the proof, checked on every build, where a proof passed to a test combinator buries the proposition in an argument list and reports a payload-free tag about a fact established at elaboration. A broken proof fails the build rather than reddening a line; the price is that `curios test` shows no inventory of proofs.
- **The thunk stays in the lowering** because `Test/main` holds every test in one list and forces only the one its index selected. Its fixed `Test({})` result selects the monad of the body's `!` regions ([Bang sequencing is governed by the region's type](../surface/bang-sequencing-is-governed-by-the-regions-type.md)). `Test(A)` witnesses `Monad`, and assertions return `Test({})`, so the body sequences assertions and lifted host actions directly. `Test/perform` and `Test/try` take thunks to delimit their independent computations.

**Rejected.**

- **Parameters meaning a theorem**, decided by asking whether the body converts with a proof tag under the whole telescope, or **dispatch on a declared type**, `test f(n: Nat) -> Eq()(n + 0, n)`: each gives `test` two meanings where a `let` already states a proof, and a verdict is a fact about one instance while a telescope quantifies over all.
- **A second keyword**, `theorem f(x)` beside `test f()`: the theorem/example split does not run along arity, and with proofs in `let` there is none left to name.
- **Empty parentheses**, `test foo() = …`, which spell a telescope the form does not admit.
- **Checking the written entry and the synthesized tail together**: the tail pairs each declaration with its path and raises nothing of its own, and would have to be carried to finalization, where a witness premise is decided.
- **A verdict in the exit code**, `0` for a pass and `1` for a failure, or a code set apart for a pass, as [Rust's harness](https://doc.rust-lang.org/src/test/test_result.rs.html) sets `50` apart for a test run in a process of its own: `/std/Process/exit` is every test's to call, so whatever code a runner reads as a verdict is one a test can exit with.
- **Verdict caching**: a test payload is filed in the store like any program's, under a reserved executable name, but a verdict is a fact about an execution, and the store holds only what sources determine.
- **A test-only module**, `test mod`: a module is a namespace, and what it holds is no property of it.
- **Leaving out what only tests reach**, by liveness: whether a build checks a declaration would follow from who reads it.
- **A test named within its subtree**, as a private definition is: a reference from anything a build holds would resolve in a test compilation and not in a build.
- **A filter in the unit**, its tests outside the selection left out as a build leaves every test out: a command-line argument would be part of what a unit is, the store would hold one tested unit per filter, and a filtered run would share none with `wonder` and `lint`.
