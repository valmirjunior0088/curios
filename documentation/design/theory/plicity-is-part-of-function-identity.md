# Plicity is part of function identity

**Decision.** A binder's plicity — explicit, implicit (`@`) or witness (`use`) — is part of a function type's identity and calling convention. Function types differing only in plicity do not convert, and every written function binder and constructor-pattern argument is checked against the plicity of the slot it claims. After a mark comes what the site's plain member would be — a type where the site declares, a binder where it binds, a value where it supplies — and a `use` member has no binder anywhere: a signature writes `use Concept(args)` and a lambda `use _`, which holds the slot's place and states nothing. An omitted implicit or witness lambda binder is inserted from the expected function type, mirroring hidden-argument insertion at a call, and one rule matches the members written to the slots they fill — a call's arguments, a lambda's binders and a concept literal's entries alike: plain members are written, in order, and between two of them the hidden members are written from the first of their run, the rest left out. A bare reference whose type leads with hidden binders has them inserted only where a hidden-headed function type could never convert — a ground explicit arrow or a rigid non-arrow expectation — so that insertion rescues guaranteed mismatches and changes no accepted program; a flexible or hidden-headed expectation keeps the polymorphic value whole. Reduction stays positional and erasure sort-driven, so plicity has no runtime effect.

**Rationale.**

- **Plicity decides which binders elaboration inserts**, so it must be stable under conversion, or a convertible annotation or alias could reinterpret a call. Lambda-side insertion lets a polymorphic definition omit the hidden binders it does not name and write the ones it does, by position in their run rather than by label, so no named-argument selection arises and the slot a written member fills depends on nothing but how many were written before it (`curios-elab`'s `align`). Constructor patterns take no insertion, because the match matrix lays out payload columns before elaboration knows the constructor's signature.
- **A witness is reached by resolution, so a name on one has no reader.** The witness scope is exactly the `use` members in scope, and what resolution finds there it finds by type. A dictionary a program does want to name is an ordinary value — a `let`, a plain or `@` parameter of the concept's type — passed on with `use value`. With no binder, `use` is followed by one thing at each kind of site, and a lambda cannot restate a slot's type that its expected function type already states.
- **One parser reads a mark** (`curios-text`'s `parse_mark`), and each site says what follows it, so a form a site does not take is refused by that site's rule: `a_refused_form_names_its_rule` holds one row per rule. A list that a function type and a lambda share is refused by neither before its arrow.

**Rejected.**

- **Plicity-blind conversion of function types**; **binding an implicit or witness slot with a plain binder**; **inserting omitted hidden constructor-pattern arguments** by analogy with lambdas.
- **A named `use` member.** No program read the name, and every job it could do is done without it: resolution passes a witness on, a `use` type parameter puts one in a type, an `@` parameter of concept type names a second dictionary, and a literal over the method wrappers hands the resolved one back as a value.
- **`use Concept(args)` in a lambda.** A lambda holds a slot's place and its expected type states the member; the lambda that has no expected type is written as a `let` with a telescope.
- **A plain member written as its type alone in a definition's telescope.** A function type needs the form and a definition does not: the parameter would be one its body cannot name, which `_: T` already says on purpose, and admitting it turns a forgotten annotation — `let f(x) -> Nat = x;` — into a parameter of type `x`. The unnamed `@T` stays, because the body does use a bound it never names.
- **`@T` in a lambda.** After `@` a lambda reads a binder whatever the word looks like — `(@Nat, x) => x` binds a variable called `Nat` — so a type there would make one word mean two things.
