# An exit yields any `Io`, and there is no `Never`

**Decision.** `Intrinsic::ProcExit` is typed at `(@A: Type, code: Nat) -> Io(A)`: the description ends the process and yields whatever the region that holds it wanted, so an arm that exits ends a region of any type, and `/std/proc/exit` carries the same type. There is no `Never`: an empty `Type`-sorted carrier is not needed for this, and a user who declares one gets nothing from it, because nothing inhabits it.

**Rationale.** A term that never returns is unsound exactly when it inhabits a type nothing total inhabits — the forgery is the problem, not the non-return. `Io(A)` is never such a type, whatever `A` is: [effects are descriptions, and the carrier has no eliminator](effects-are-descriptions-and-the-carrier-has-no-eliminator.md), so an inhabitant of `Io(False)` is a description that yields nothing and proves nothing, and the perimeter row that states this — [a term outside `Io` performs no effect](../../soundness/per-term-rules/a-term-outside-io-performs-no-effect.md) — is what `exit`'s type now rests on. The earlier answer typed the payload at `{}`, which is inhabited and therefore forges nothing either; it was sufficient, not necessary, and it cost every exiting arm its region: `/syn/Test`'s scheduler and `/std/Async`'s deadlock exit could end their regions with an exit only because those regions happened to be unit, and any other region needed the detour `let _ = proc/exit(1)!; …` followed by a value the branch never produces. The polymorphic type removes the detour and claims nothing the unit type did not: no eliminator reaches `A`, and erasure drops it. What a binding that reads nothing loses is inference — `let _ = proc/exit(1)!` leaves `A` unsolved, and is written `proc/exit(@{}, 1)` where the shape is wanted at all. [Totality of the erased program](totality-of-the-erased-program.md) keeps both of its clauses for `exit`, on operational rather than soundness grounds: (T) is unchanged, since a `Nat` defined through an exit does not terminate, so a type mentioning it does not form; (V) keeps it because an exit reachable from a `Prop`-sorted term sits where erasure deletes, so the process would not exit where the author wrote that it should — a wrong program rather than a false proof.

**Rejected.** Restricting *which* type `exit` may be given, which two weaker designs tried before the unit answer. Refusing a `Prop`-sorted result leaves `Exit(Empty, 0)` at a constructor-free `Empty : Type`, and a `Type`-sorted empty inductive eliminates into `Prop` unguarded — `guard_large_elimination` returns at its first check, and zero constructors leave no arms to verify. Making `Never` a core bottom type with `Never ≤ A` in subsumption relocates the same permissiveness into the relation every check goes through, and the restricted clause admits `Never ≤ Empty` for the same reason. Both put an uninhabited *`Type`-sorted* carrier into the erased program, which is the forgery; `Io(A)` is a different kind of thing, an opaque description, and that is why it can be polymorphic where they could not. Keeping the unit payload, which was the answer until this one: sound, and the reason it was chosen, but it refused programs for no soundness gain, and its own rationale conceded that an `Io`-polymorphic bottom was sound once the carrier had no eliminator.
