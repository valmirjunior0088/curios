# Guest coordination uses write-once cells and bounded channels

**Decision.** Guest instances coordinate through write-once cells and positive-capacity channels. These objects live in the guest heap and their operations return `Io` descriptions. A cell publishes one answer. A channel holds a bounded queue: each nonblocking push or take commits and reports its own outcome. `Push` distinguishes accepted, full and closed; `Take(A)` distinguishes an item, empty and ended. Closing preserves queued items for draining. Capacity zero is refused through a decided bound carried by the raw intrinsic as well as its public declaration.

**Readiness observes a condition.** `/std/Async/Wait` is opaque, with factories for host readiness, elapsed time, a filled cell and readable or writable channel ends. Its private guest probes only observe. The scheduler scans them whenever it becomes idle, before blocking or declaring deadlock; an ordinary lifted `Io` fill therefore needs no notification. One claim cell shared across a park's alternatives permits exactly one enqueue. Claimed and cancelled registrations are pruned. After waking, an offer retries its committing operation and reparks if another fiber consumed the opportunity. Selection retains list-order priority.

**Ownership follows values.** Runnable jobs, parked registrations, handle waits, sleepers and probes are values threaded through the scheduler. Futures, cancellation, completion and claims use cells; signals use capacity-one channels and coalesce repeated notifications. A sender that needs receipt acknowledgement includes a reply cell in its buffered message and waits for the receiver to fill it. Enqueueing and acknowledgement are separate events. These objects have meaning within one guest instance; cross-process transport is a separate contract.

**Rationale.** A notification list can outlive the selection that registered it, leaving an abandoned receive counted as a willing receiver. Observing present conditions removes that bookkeeping. Bounded storage makes backpressure explicit, while an acknowledgement states exactly which event the sender needs. [The emitter](../../../curios-emit/README.md#cells-and-channels-occupy-the-guest-heap) owns the ring layout and reference release; [the continuation IR](../../../curios-cont/README.md#mutation-hides-behind-instruction-atomicity) owns operation sequencing and the cell-and-channel knot protocol.

**Rejected.** A general rewritable cell alongside the write-once cell would keep two mutation vocabularies. A shared queue made solely from write-once cells can retain consumed message chains through old ends. A mutable one-slot box adds no capability beyond a capacity-one channel. Unbounded queues give up the storage bound. Capacity-zero rendezvous entangles buffering with receipt; reply cells express receipt directly.

**Rejected.** `Bool` for push and `Option(A)` for take merge distinct outcomes that a later observation cannot recover atomically. Repairing notification lists with selection claims retains unnecessary registration state. Public arbitrary probes, or committing offer attempts used as probes, permit effects or consume values during an idle scan. A scheduler-specific intrinsic probe adds compiler vocabulary where private library observations suffice.

**Session state is threaded too.** Each Tui reader, ticker and drawing loop keeps its own `Session` value. Reading returns the updated input buffer, size queries return the updated cached size, and drawing returns the frame history. Resize events update the drawing session through `Session/resized` before rendering. Separate public role types were rejected: these loops already state the ownership, and their values can travel through the existing API.
