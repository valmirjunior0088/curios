# A tuple type is keyed by the part of its identity conversion keeps

**Decision.** A witness may be keyed on a tuple type, and the head it keys on is the part of the type conversion does not delegate to the subterms: its *shape* — the label at each field position, `""` where the field is positional, arity implied by the length, field types excluded — `HeadKey::TupleType(Vec<String>)`. It lives in `curios-elab/src/concept.rs` and is read off a weak-head normal form by `HeadKey::of_whnf` in the first-order position and the higher-kinded one, so `satisfy (@A: Type, @B: Type, use Show(A), use Show(B)) => Show({A, B}) { … }` registers, as does `satisfy Functor(Pair)` for a `let Pair(A: Type) -> Type = {Nat, A};`. Every other rule — regularity, one witness per key, the orphan rule, deferral — applies unchanged, because a shape is one more thing a parameter can be rigidly headed by and nothing else. **A function type is not keyed**, which is the half of this decision that was tried and retired; the last section says why.

**Rationale.** For `List(Nat)` the head is `List` and `Nat` is checked by unification after lookup. A tuple type has no name to be headed by, so the question is what part of it plays that role: rigid, cheap to read off a weak-head form, and exactly the part conversion does not delegate to the subterms. `compare_tuple_type` (`curios-elab/src/convert.rs`) refuses two tuple types whose labels differ before it enqueues a single field, and equates them iff the labels agree and the fields convert; `TupleType`'s hand-written `Eq`/`Hash` (`curios-core/src/term/shape.rs`) reassert those labels on top of the label-blind telescope identity for the same reason. A key that reads exactly what conversion refuses on and leaves the rest to unification splits the type along the seam the language already splits it on. Reading it costs a walk down the spine and evaluates nothing: the weak-head form of a tuple type is the node itself, and `Telescope::labels` opens no binder.

Three consequences follow rather than being decided. `{Nat, Bool}`, `{a: Nat, b: Bool}` and `{x: Nat, y: Bool}` are three keys because they are three types, so a witness for one does not serve another and the miss is reported with a hint naming the rule. A shape is owned by no module — the answer `mount_of_head` already gives for an intrinsic former — so the orphan rule reads: declared where the concept is declared, or by a privileged root. That is `List`'s standing today, and it makes `/std/Tuple`'s arity ceiling a promise rather than a default, which is why the ceiling was chosen with room.

**Rejected.** *Arity alone.* `{A, B}` and `{x: A, y: B}` would be one key though they are two types; the one-witness-per-key rule would refuse the second because the first exists, and a goal at one would silently reach the other's body.

*A single arity-blind `Tuple` head.* One witness per concept would cover every tuple type, but its body cannot be written: no term in the language ranges over a tuple of unknown arity. Only a compiler that writes bodies could fill it, which is derivation and a different objective, and a key nobody can write a witness for buys nothing.

*The component, domain or result heads in the key.* Keys would overlap: `Show({Nat, B})` and `Show({A, Bool})` would both register and `Show({Nat, Bool})` would be ambiguous, the instance-overlap problem the one-head-per-parameter discipline exists to make unrepresentable. A telescope variable or a binder-headed domain has no head to contribute in any case.

*A nominal product in `/std`* — `Pair(A, B)`, `Triple(A, B, C)` — carrying the witnesses instead. `(1, true)` has type `{Nat, Bool}` and never `Pair(Nat, Bool)`, so every call site would pay a conversion and the language's own product would be the one type its standard library has no opinion about.

*Componentwise resolution wired into the compiler* for concepts known to distribute over products. Which concepts those are is library knowledge; the compiler has no business knowing that `Show` distributes and `Monad` does not.

*The tuple former owned by every root*, and *ownership through a component the declaring root owns*. Both reopen the link-time collision the orphan rule exists to prevent: two independent packages each declaring `Show({Nat, Nat})` would collide with neither in the wrong, and components are not in the key for the second to reach anyway.

*A `Monad` or `Lift` witness at a function shape, by anyone.* `/std` declines the slot deliberately — the reader-monad idiom is the nominal wrapper, whose result parameter sits last precisely so the family partially applies as a monad — and the orphan rule refuses everyone else.

**The function half, tried and retired.** A function type was keyed on its *plicity vector* — the mark at each parameter position, arity implied, domains and result excluded — by the same argument: `compare_func_type` refuses two function types whose vectors differ before it enqueues a domain, so the vector was the half of identity conversion kept for itself, and reading it evaluated nothing.

It was removed, and the reason was in this document from the start: a shape is owned by no module, so the orphan rule reads "declared where the concept is declared, or by a privileged root" — and for functions the useful key space is nearly one point, `(_) -> _` above all, so a concept's owner claiming a shape claimed it program-wide and forever. Tuples carry that cost harmlessly because their key space is large and ownership partitions naturally; functions do not.

What made it worth the hazard was one consumer, `/std/Test/Property`, whose function instance had a single canonical meaning. That concept is gone ([A test is a check that runs, and a proof is a `let`](a-test-is-a-check-that-runs-and-a-proof-is-a-let.md)), and nothing replaced it: `Show` at a function type is meaningless, `Eql` at one undecidable, `Monad` at one declined deliberately in favour of `/std/State`'s nominal wrapper. A feature whose only sanctioned use has left, and whose shape is a program-wide land grab, is better absent — so `HeadKey::of_whnf` returns `None` for a function type and a `satisfy` keyed on one is refused as unkeyable, with the report a variable head already gets.
