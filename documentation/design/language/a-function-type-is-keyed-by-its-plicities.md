# A function type is keyed by its plicities

**Decision.** A witness may be keyed on a function type, and the head it keys on is the type's *plicity vector*: the mark at each parameter position, arity implied by the length, domains and result excluded. `HeadKey::FuncType(Vec<Plicity>)` (`curios-elab/src/concept.rs`) is that head, read off a weak-head normal form by `HeadKey::of_whnf` in both the first-order position and the higher-kinded one, so `satisfy (@A: Type, @R: Type, use Draw(A), use Property(R)) => Property((A) -> R) { … }` registers and `satisfy Fun(Reader)` registers for a `let Reader(A: Type) -> Type = (Nat) -> A;`. Every other rule — regularity, one witness per key, the orphan rule, deferral — applies to a function key unchanged, because a plicity vector is one more thing a parameter can be rigidly headed by and nothing else.

**Rationale.** For `List(Nat)` the head is `List` and `Nat` is checked by unification after lookup. A function type has no name to be headed by, so the question is what part of it plays that role: rigid, cheap to read off a weak-head form, and exactly the part conversion does not delegate to the subterms. That part is the plicity vector. `compare_func_type` (`curios-elab/src/convert.rs`) refuses two function types whose vectors differ — arity included — before it enqueues a single domain, and equates them iff the vectors agree and the domains and result convert; its binder names feed freshness, never equality. A key that reads the marks and leaves the subterms to unification therefore splits the type along the same seam conversion already splits it on, exactly as the tuple shape does ([A tuple type is keyed by its shape](a-tuple-type-is-keyed-by-its-shape.md)). Reading it costs a copy of the marks and evaluates nothing: the weak-head form of a function type is the node itself.

Three consequences follow rather than being decided. `(A) -> B`, `(A, B) -> C` and `(A) -> (B) -> C` are three keys because they are three types — Curios does not curry at the type level, so arity is identity — while `(a: Nat) -> Nat` and `(b: Nat) -> Nat` are one key, because binder names are alpha-convertible in a function type: the exact opposite of tuple labels, and the same rule seen from the other side, since the key is whatever half of identity conversion keeps for itself. The result type is not in the key, so under the one-witness-per-key rule a concept commits, per shape, to one result discipline — which is precisely what the property-testing specification leans on. And a plicity vector is owned by no module — the answer `mount_of_head` already gives for an intrinsic former and a tuple shape — so the orphan rule reads, for a function key: declared where the concept is declared, or by a privileged root. That bites harder than the tuple case, because the useful key space is nearly one point — `(_) -> _` above all — so a concept's owner claiming a shape claims it program-wide, forever. The intended consumers are concepts whose function instance has one canonical meaning, `Property` first; `Monad` at a function shape is declined deliberately — `/std/State` documents the nominal wrapper as the idiom — which keeps `syntax.md`'s "a `(Str, Bool) -> Bool` has nowhere to sequence one" a fact rather than a default.

**Rejected.** *Arity alone.* `(A) -> B` and `(@A: T) -> B` would be one key though they are two types, and the one-witness-per-key rule would refuse the second because the first exists — a key coarser than the identity it stands for.

*Binder names in the key.* Names are not identity in a function type — `compare_func_type` uses `first_hint` only to mint fresh openings — so a name-bearing key would split one type into as many keys as it has spellings, and a well-typed goal would miss a registered witness over a renaming.

*The domain or result heads in the key.* Keys would overlap: `Property((Nat) -> R)` and `Property((A) -> Test)` would both register and `Property((Nat) -> Test)` would be ambiguous, which is the instance-overlap problem the one-head-per-parameter discipline exists to make unrepresentable. A binder-headed domain has no head to contribute in any case.

*A single arity-blind `Func` head.* One witness per concept would cover every function type, but its body cannot be written: no term in the language ranges over a function of unknown arity. A key nobody can write a witness for buys nothing.

*Curry-normalizing the key* — keying `(A, B) -> C` as if it were `(A) -> (B) -> C`. The two do not convert, so one key would stand for two types no single witness body can serve, and resolution would depend on a normalization conversion itself refuses to perform.

*A `Monad` or `Lift` witness at a function shape, by anyone.* `/std` declines the slot deliberately — the reader-monad idiom is the nominal wrapper, whose result parameter sits last precisely so the family partially applies as a monad — and the orphan rule refuses everyone else.
