# Erased positions are non-strict

**Decision.** An expression in an erased value position — an argument to an erased parameter, an erased structure or constructor field, an operand slot instantiated at a proposition or a type, the value a `let` binds at a proposition or a type, locally or as a top-level item — is not evaluated: its refusals do not occur and its computation costs nothing. A binding is classified by its type as every other slot is, so `let p = lemma(n); f(p)` and `f(lemma(n))` are one program, and a lemma applied at the top level does not run before the program does. A top-level *function* is not a binding in this sense: writing one computes nothing, and its body is erased whatever it returns. What still evaluates under call-by-value regardless of its result's sort is a direct call of a function whose result erases, standing where erasure keeps a value. Type-level positions need no guard, because no term of non-`Io` type can perform an effect — [Effects are descriptions, and the carrier has no eliminator](effects-are-descriptions-and-the-carrier-has-no-eliminator.md) — so an effectful subterm a type never forces is erased with the type.

**Rationale.** Not evaluating erased value positions is what erasure is for: proofs are certificates whose computation must cost nothing at runtime, which is what lets the `/std` lemma corpus decorate data structures without runtime traversals. Nothing observable is lost by it. No term outside `Io` performs an effect, so an erased expression performed none — an exit is an `Io` too, so `let _ = proc/exit(3); …` builds a description and the program goes on. [Totality of the erased program](totality-of-the-erased-program.md) makes every proof and every type total, so the expression would have returned. What is left is a refusal: a lemma applied to `n * 1000000 * 1000000` leaves the `Nat` carrier at run time although Core's value is fine, and a binding that computed it stopped a program its inline spelling let run. A proof that can give a program a behaviour is not irrelevant, so the binding is an erased position like the others, and the direction is the permitted one — the run time yields Core's value or a refusal, and this removes a refusal.

**Rejected.** A transitive host-effect analysis that evaluates an erased position when its expression may reach a host operation: real machinery that still cannot preserve divergence, so it buys only a partial strictness guarantee. Retyping never-returning operations at an **empty** `Type`-sorted carrier, because it narrows the observable gap without closing it — an elimination immediately launders the effect back into an erased position, and an empty carrier is precisely what an elimination into a proposition passes through unguarded. Retyping at the *opaque* carrier is what landed instead, `Io(A)` for any `A`, since an `Io` has no eliminator and so nothing to launder: [An exit yields any `Io`, and there is no `Never`](an-exit-yields-any-io-and-there-is-no-never.md). Leaving a bound proof to the optimizer, which drops a dead binding: nothing below Core says a call is total, so the call stays, and once it is inlined what remains is an arithmetic operation that may refuse, which the optimizer keeps for exactly that reason.
