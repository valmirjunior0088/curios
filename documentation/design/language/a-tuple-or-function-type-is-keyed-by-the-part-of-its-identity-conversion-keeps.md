# A tuple or function type is keyed by the part of its identity conversion keeps

**Decision.** A witness may be keyed on a tuple type or on a function type, and the head it keys on is the part of the type conversion does not delegate to the subterms. For a tuple type that is its *shape*: the label at each field position, `""` where the field is positional, arity implied by the length, field types excluded — `HeadKey::TupleType(Vec<String>)`. For a function type it is the *plicity vector*: the mark at each parameter position, arity implied by the length, domains and result excluded — `HeadKey::FuncType(Vec<Plicity>)`. Both live in `curios-elab/src/concept.rs` and are read off a weak-head normal form by `HeadKey::of_whnf` in the first-order position and the higher-kinded one, so `satisfy (@A: Type, @B: Type, use Show(A), use Show(B)) => Show({A, B}) { … }` and `satisfy (@A: Type, @R: Type, use Draw(A), use Property(R)) => Property((A) -> R) { … }` register, as do `satisfy Functor(Pair)` for a `let Pair(A: Type) -> Type = {Nat, A};` and `satisfy Fun(Reader)` for a `let Reader(A: Type) -> Type = (Nat) -> A;`. Every other rule — regularity, one witness per key, the orphan rule, deferral — applies unchanged, because a shape or a plicity vector is one more thing a parameter can be rigidly headed by and nothing else.

**Rationale.** For `List(Nat)` the head is `List` and `Nat` is checked by unification after lookup. A tuple or function type has no name to be headed by, so the question is what part of it plays that role: rigid, cheap to read off a weak-head form, and exactly the part conversion does not delegate to the subterms. `compare_tuple_type` (`curios-elab/src/convert.rs`) refuses two tuple types whose labels differ before it enqueues a single field, and equates them iff the labels agree and the fields convert; `TupleType`'s hand-written `Eq`/`Hash` (`curios-core/src/term/shape.rs`) reassert those labels on top of the label-blind telescope identity for the same reason. `compare_func_type` refuses two function types whose plicity vectors differ — arity included — before it enqueues a single domain, and equates them iff the vectors agree and the domains and result convert; its binder names feed freshness, never equality. A key that reads exactly what conversion refuses on and leaves the rest to unification splits each type along the seam the language already splits it on. Reading either costs a walk down the spine and evaluates nothing: the weak-head form of a tuple or function type is the node itself, and `Telescope::labels` opens no binder.

Four consequences follow rather than being decided. `{Nat, Bool}`, `{a: Nat, b: Bool}` and `{x: Nat, y: Bool}` are three keys because they are three types, so a witness for one does not serve another and the miss is reported with a hint naming the rule; `(A) -> B`, `(A, B) -> C` and `(A) -> (B) -> C` are three keys for the same reason, since Curios does not curry at the type level and arity is identity, while `(a: Nat) -> Nat` and `(b: Nat) -> Nat` are one key because binder names are alpha-convertible in a function type — the exact opposite of tuple labels, and the same rule seen from the other side. A function type's result is not in the key, so under the one-witness-per-key rule a concept commits, per shape, to one result discipline — which is precisely what [A parameterized test is a property](a-parameterized-test-is-a-property.md) leans on. And neither a shape nor a plicity vector is owned by any module — the answer `mount_of_head` already gives for an intrinsic former — so the orphan rule reads, for either key: declared where the concept is declared, or by a privileged root. That is `List`'s standing today, and it makes `/std/Tuple`'s arity ceiling a promise rather than a default, which is why the ceiling was chosen with room. It bites harder for functions, because the useful key space is nearly one point — `(_) -> _` above all — so a concept's owner claiming a shape claims it program-wide, forever. The intended consumers are concepts whose function instance has one canonical meaning, `Property` first; `Monad` at a function shape is declined deliberately — `/std/State` documents the nominal wrapper as the idiom — which keeps `syntax.md`'s "a `(Str, Bool) -> Bool` has nowhere to sequence one" a fact rather than a default.

**Rejected.** *Arity alone.* `{A, B}` and `{x: A, y: B}` would be one key though they are two types, and so would `(A) -> B` and `(@A: T) -> B`; the one-witness-per-key rule would refuse the second because the first exists — a key coarser than the identity it stands for.

*Binder names in a function key.* Names are not identity in a function type — `compare_func_type` uses `first_hint` only to mint fresh openings — so a name-bearing key would split one type into as many keys as it has spellings, and a well-typed goal would miss a registered witness over a renaming.

*A single arity-blind `Tuple` or `Func` head.* One witness per concept would cover every tuple or function type, but its body cannot be written: no term in the language ranges over a tuple or a function of unknown arity. Only a compiler that writes bodies could fill it, which is derivation and a different objective, and a key nobody can write a witness for buys nothing.

*The component, domain or result heads in the key.* Keys would overlap: `Show({Nat, B})` and `Show({A, Bool})` would both register and `Show({Nat, Bool})` would be ambiguous, exactly as `Property((Nat) -> R)` and `Property((A) -> Test)` would — the instance-overlap problem the one-head-per-parameter discipline exists to make unrepresentable. A telescope variable or a binder-headed domain has no head to contribute in any case.

*Curry-normalizing a function key* — keying `(A, B) -> C` as if it were `(A) -> (B) -> C`. The two do not convert, so one key would stand for two types no single witness body can serve, and resolution would depend on a normalization conversion itself refuses to perform.

*A nominal product in `/std`* — `Pair(A, B)`, `Triple(A, B, C)` — carrying the witnesses instead. `(1, true)` has type `{Nat, Bool}` and never `Pair(Nat, Bool)`, so every call site would pay a conversion and the language's own product would be the one type its standard library has no opinion about.

*Componentwise resolution wired into the compiler* for concepts known to distribute over products. Which concepts those are is library knowledge; the compiler has no business knowing that `Show` distributes and `Monad` does not.

*The tuple former owned by every root*, and *ownership through a component the declaring root owns*. Both reopen the link-time collision the orphan rule exists to prevent: two independent packages each declaring `Show({Nat, Nat})` would collide with neither in the wrong, and components are not in the key for the second to reach anyway.

*A `Monad` or `Lift` witness at a function shape, by anyone.* `/std` declines the slot deliberately — the reader-monad idiom is the nominal wrapper, whose result parameter sits last precisely so the family partially applies as a monad — and the orphan rule refuses everyone else.
