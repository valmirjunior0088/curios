# A tuple is read at its own final type

**Decision.** The `$tuple/N` heap types are declared *final* and unrelated to one another, and a field read finds the object's exact type by testing every roster arity that could hold the field, widest first, casting on the last. They were a prefix subtype chain — `$tuple/4 <: $tuple/3 <: … <: $tuple/1` — so a single `ref.cast (ref $tuple/1)` could read field 0 of any tuple whatever its arity. That was the cheapest possible reader and the most expensive possible cast.

**The chain made every read of a real object a host call.** Wasmtime's `ref.cast`/`ref.test` to a concrete type compares the object's type index against the target and, on inequality, calls the `is_subtype` libcall — a host call through a per-store `HashMap<u64, bool, NopHasher>` cache (`wasmtime-internal-cranelift`'s `func_environ/gc.rs`, and `wasmtime`'s `runtime/store/gc.rs`; the engine's own FIXME names issue #13484). The only short-circuit is the target being final, and no `$tuple/N` was. Every real node is wider than the prefix it was read through — a `cons` is a `$tuple/3` read as a `$tuple/1` — so the fast path was structurally unreachable for exactly the reads a program performs in a loop.

**Exhausting the roster is what makes the reader correct without an assumption.** No reader may suppose an object's arity is its constructor's, only that it is at least that: [a variant travels as the fields of its widest constructor](a-variant-travels-as-the-fields-of-its-widest-constructor.md), so a surviving whole-value use of a narrow constructor materialises at its region's width, and `takeable` declines a multi-width source rather than reading it at the narrowest. Testing every roster arity from `index + 1` upward assumes nothing about which constructor arrived. The cost is bounded by the module-global roster, which is 2 to 5 across the entire corpus including a `Toml` + `Map` + `List` + `Result` program, so the chain is short whatever the order; widest-first is a preference that happens to hit first in every family measured, because the wide constructor is the payload-carrying one and the payload-carrying one is what a loop walks.

**What it bought, and the shape of the evidence.** Measured 2026-08-20 on x86-64 Linux, release, whole-process, min of 5, every anchor checked on every run: `chain` 339.6 → 131.1 ms (−61.4%) and `spines` 100.5 → 78.8 ms (−21.6%), against `lcg` +0.8%, `trees` +0.8% and `churn` +0.1%. The three flat columns are flat for reasons stated in advance — `lcg` declares no variant, `trees`' leaf rides the i31 so its family never reads a tag and its one boxed constructor casts exactly, `churn`'s hot loop is not a variant walk — and the two that moved are exactly the two whose hot loop reads a multi-constructor heap family. That the prediction and the split agree is what makes this a class rather than a coincidence. `a_tuple_is_read_at_its_own_final_type` in `curios`'s codegen tests holds the figures and pins the shape.

**Rejected — a `likely` hint carried on the IR.** The original design had `TupleGet` carry the widths its producer expects, so the emitter could both order *and prune* the cascade. Pruning is the part that fails: it is a correctness claim about widening dressed as a hint, and getting a producer's list wrong is a trap rather than a slowdown. It also cost more than it bought — a width list on the op means `CpsIntrinsic` loses `Copy`, `Ord` and `Hash`, rippling through some fifty sites and silently breaking CSE for two reads that differ only in their hint. Exhaustion needs none of it and measured the figures above.

**Rejected — keeping the chain under the cascade.** It needs no fallback, since a prefix cast still catches a widened object. But a *failed* `ref.test` on a non-final type is itself the libcall, so it only moves the cost from `fork`, `cons` and `some` to `leaf`, `nil` and `none`. Finality is what makes a negative free, and the roster fallback is its price.

**Rejected — dispatching on arity alone.** Distinct-arity families would need no tag read at all, but a widened narrow constructor has its sibling's arity, so the tag stays the discriminant and the cascade only decides which exact type to read it through.

**Rejected — waiting for the engine.** Issue #13484's "true solution" stores supertypes inline where compiled code can reach them, which would delete the host call but still walk supertype arrays — several dependent loads against one compare — and it would arrive on the engine's schedule, under an invariant this pipeline does not need once its types are final. JavaScriptCore already inlines the check with Cohen's type display, so the browser product was never paying the libcall; that is an argument for not designing against one engine, not for keeping a cast nobody needs.

**Boundaries, and what the successor took back.** This decides how an object's *type* is found, not what its *fields* are declared as. Every field is still `(ref null any)`, so every scalar read out of one still unboxes — the subject of [a monomorphic field carries its own type](../../roadmap/typed-heap-fields-spec.md), whose census this decision's measurement fed.

That successor's first step then removed the cascade from the case this decision was built for, exactly as this file predicted a re-keying would. A variant family is now one final struct at its own width, minted by the Ersd door and named by `CpsValueExpr::Variant`/`CpsIntrinsic::VariantGet`, so a family read is a single exact cast with no roster search — and Binaryen's closed-world passes finally see one type per family instead of one per arity. **What stands unchanged is the decision itself**: finality is what makes a negative free, and it was direction-neutral between the two keyings, which is why the nominal scheme inherited it rather than replacing it. The cascade survives for structural tuples, where no nominal identity exists to key on.
