# Every gate step catches what no other step does

**Decision.** The hand-off gate in `CLAUDE.md` is a minimal set, not a convenient one: a step earns its place by being the only thing that fails when something specific is wrong, and a step whose findings another step already reports is removed rather than kept for reassurance. What each one is the sole check for is below, and a step added later states the same before it is added.

**Rationale.** A gate is read under time pressure, and a reader who cannot tell which step would have caught a given mistake will start skipping the slow ones. Naming the unique catch makes that judgement unnecessary: nothing in the list is redundant, so nothing in the list is optional.

**`clippy` subsumes `check`, and nothing subsumes the workspace test run.** `cargo clippy --workspace --all-targets --all-features` is the same compilation as `cargo check` with more lints, so `check` appears in neither this gate nor the check workflow. What it reaches is bounded, though: it stops at erasure and certification, so `curios-cont` and `curios-wasm` are exercised only by the cross-stage corpus `cargo test --workspace` runs. How far that reach goes, and what it lets a contributor skip between steps, is `CLAUDE.md`'s iterating guidance.

**The two documentation steps check different halves and neither reports the other's findings.** `cargo x rust-docs` is the workspace's rustdoc under `[workspace.lints.rustdoc] all = "deny"`, inherited by every crate through `[lints] workspace = true` so no step carries an environment variable that can be forgotten in one of them. It has been red on its own while every step above it was green: a broken intra-doc link is checked nowhere else. It documents private items because these crates state their invariants on `pub(crate)` ones, and without that it lints a small fraction of the prose it exists to check. `cargo x std-docs` is the same check for `/std`'s pages, rendered from the prelude image the compiler was built with, so a doc comment the record cannot carry and a page the renderer cannot lay out are caught there and nowhere else.

**The browser and editor trees are reached by no cargo invocation above them.** `cargo x js` builds the bundle for `wasm32-unknown-unknown`; the two npm bridges install from their lock file before testing; the Zed extension is formatted, linted and built for `wasm32-wasip2`. A workspace command touches none of them, so each is its own step or it is unchecked.

**The Zed extension checks its own pin, because the extension owns it.** Zed installs the grammar from a pushed commit rather than from the checkout, so the rev in `editors/zed/extension.toml` is the only thing tying the extension to a grammar, and a regenerated grammar whose rev was not moved leaves every install building the previous one. `cargo x zed test` asks that question from inside the extension, where the manifest and the answer live together. The pinned rev is an ordinary commit, so both trees resolve offline whenever it is already on `origin` — every state but one. That one is a regenerated grammar not yet pushed, and there the step *should* fail: it is saying push the grammar and then move the rev, which is the two-commit sequence those moves already follow.

**Rejected.** `cargo check` beside `clippy`, which compiles the same code and reports a subset. A doctest step in this gate: no crate carries a documentation example, so `cargo test --workspace --doc` passes over an empty set — the check workflow keeps it as the tripwire for the day one is written, where a permanently-passing step costs nothing and a locally-run one costs a reader's attention. Denying rustdoc's lints through an environment variable rather than the root manifest: two places to set it is one place to forget it, and the gate and CI would then disagree silently. Leaving the grammar rev to CI alone, which is what let two pushes land red before anyone read the job — the check is cheap and local, and only its failure mode is remote.
