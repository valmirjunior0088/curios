# A test is a declared description, run by a synthesized tail

**Decision.** A test is declared — `test name() = body;`, a contextual keyword exactly as `satisfy` is — and its body is a description: a value of `/syn/Test`, whose representation is private to its module, built through the combinators `/std/Test` exports (`prove`, `refl`, `check`, `equal`, `perform`) and eliminated only by `Test/main`. The declaration is the function-definition sugar it lowers to — an ordinary definition of kind `Test` and declared type `() -> /syn/Test`, collected per unit in `Module::tests` in declaration order — and the parentheses are required — empty for the test this decision describes, and holding a telescope for a property ([A parameterized test is a property](../language/a-parameterized-test-is-a-property.md)). What runs the tests is a program the compiler builds: asked for a test compilation, the elaborator replaces the unit's final term with `Test/main([("path", thunk), …])` over its registered tests — built in Core once the unit's items have elaborated, so the tail schedules the elaborated definitions and can read them — checks it against `Io({})` as every authored tail is checked, and the kernel judges it like any program. `curios test` runs each test in an instantiation of its own, `[argv0, index]` as the arguments, so one test's effects, traps and exits never reach another; the selection protocol is spelled once, in Curios, in `Test/main`. Because the tail is where a parameterized test's `Property` goal is raised, `wonder diagnostics` checks a unit that registers tests as its test program too — a program elaborated once under both tails, the written entry kept and the test tail checked beside it and dropped, a library through the same `()` entry `curios test` compiles it with — so the oracle and the language server see what only the runner used to.

**Rationale.** Every registered item kind in the language has its declaration keyword; `let` registers nothing. Discovery — by type, by name pattern, or by attribute — would make a `let` register for the first time, and discovery by type specifically would run every nullary `Test`-valued helper as a test the day it is written. A declared item also gives the test an identity that survives the pipeline: the path names it in the report, the filter, and `wonder tests`, and the collection order *is* the schedule, so nothing downstream re-derives either. Synthesizing the tail in Core, rather than writing a file or generating surface syntax, keeps the program the runner executes inside the ordinary soundness story — elaborated, zonked, certified — while changing nothing about the surface language; a unit with no tests compiles to `Test/main([])`, which runs nothing and exits 0.

**The description is a description for the same reason `Io` is.** A consumer can build a `Test` and can do nothing else with one — the representation is private, so only the harness's own module matches it. That is what lets the harness grow rungs (a `theorem()` settled at compile time, a `verdict` decided at run time, an `action` performed in `Io`) without any consumer having assumed a shape. `Bool`-only bodies were rejected on exactly this ground: a `Bool` says nothing about *how* it was decided, so a proved proposition and a runtime comparison would report alike and the kernel's rung could not exist.

**`Test/perform` takes a thunk because regions are worth keeping.** A `!` reads its monad from its sequencing region, and regions open only at value bodies, lambda bodies and match arms — a call argument is none of these. Honoring an inline `Io(Test)` argument would have hoisted the effect into the surrounding pure region, changing the region rules for one library's convenience. The thunk costs three characters — `() =>` — and its lambda body is a fresh region with its type pushed from `() -> Io(Test)`, so the inline form sequences exactly where it reads as sequencing.

**What this does not buy.** Verdict caching. A test payload is filed in the store like any program's — under a reserved executable name no identifier can spell — so an unchanged package recompiles nothing, but every invocation runs every selected test: a verdict is a fact about an execution, not about sources, and the store deliberately holds only what sources determine.
