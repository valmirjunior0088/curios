# One crate is the authority for one external concern

**Decision.** Every external dependency with a surface worth governing is named in exactly one manifest, and that crate is its authority: `curios-profile` for `tracing`, `curios-archive` for rkyv, `curios-num` for `num-bigint` and `num-traits`, `curios-package` for TOML, `curios-runtime` for `wasmtime`, `curios-utilities` for `stacker`. Each names its own pin rather than taking a `[workspace.dependencies]` row, and nothing above it spells the dependency's types.

**Rationale.** A shared row concentrates *configuration* and not authority. Any crate may add `foo = { workspace = true }` without anyone deciding it should, whereas a dependency that exists in one manifest cannot be added elsewhere without writing the version down again — which is a question a reviewer asks. The pin and the feature set then have one home, so two crates cannot disagree about either: `curios` and `curios-runtime` cannot drift on the Wasmtime version, and that matters because `curios` precompiles a `.cwasm` the launcher deserializes, and Wasmtime records its own version in the artifact and refuses a mismatch at load time.

**What makes a facade possible is sealing, not the shape of the surface.** A dependency whose surface is a *mechanism* is absorbed trivially: rkyv appears only in derives and `With` adapters, `tracing` only inside macros, so one crate holds each and no signature mentions them. A dependency whose surface is a *type* takes one more step — the owning crate wraps it in a type of its own and keeps the original private, so no consumer names it. `curios-num`'s `Natural` holds a private `BigUint` and its constructor is `pub(crate)` for exactly this reason, stated at the constructor: its bound would print `BigUint` in rustdoc "on a type whose whole purpose is that no one above this crate says it."

**A feature that must not reach every consumer is a feature flag, not a reason to give up the rule.** Wasmtime is the case: `curios` needs Cranelift and `curios-runtime`'s default build must not have it, and Cargo features are additive and unify across a workspace build. That is solved by `curios-runtime` declaring a `cranelift` feature which `curios` opts into, not by keeping the dependency in a shared row — the pin stays single, and the feature sets stay apart.

**Amended — this entry used to name `num-bigint` and `wasmtime` as the two cases the rule could not cover, and both have since been covered.** The claim was that `BigUint` is data appearing in public signatures across eight crates, so a facade "would change the spelling everywhere and concentrate nothing", and that Wasmtime's feature split made a shared workspace row "exactly right". Sealing dissolved the first: the facade does not re-export the bignum, it hides it, so the spelling above `curios-num` is `Natural` and `Integer` and there is no `BigUint` to change. A feature flag dissolved the second. The correction is recorded rather than overwritten because the two rejections were stated as properties of the dependencies, and they were properties of the technique that had been tried — which is the failure mode a rejected alternative is most prone to.

**Rejected.** A `[workspace.dependencies]` table as the governing mechanism: it makes versions consistent, which is the easy half, and says nothing about who may take the dependency, which is the half that decides whether a boundary holds. Re-exporting the foreign type from the owning crate rather than sealing it: the pin concentrates and the vocabulary does not, so every consumer still names the foreign type and the facade buys only a shorter path to it.
