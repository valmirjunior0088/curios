# curios-verdicts

The store as a compilation sees it: the `Cache` the fold consults for units already judged, and the payload family an invocation consults before compiling a program it has already compiled — both believed on a verified record rather than on an address. The store's families and keys belong to `curios-package`, what a stored unit is to `curios-unit`, and why believing one is sound to [Cached verdicts](../documentation/design/soundness/cached-verdicts.md) and [Reused payloads](../documentation/design/soundness/reused-payloads.md); the mechanism belongs to the crate rustdoc.

## Design

### Beside the pipeline, over the package, and under neither

**Decision.** This crate depends on `curios-pipeline`, whose `Cache` trait it implements, and on `curios-package`, whose store layout and keys it reads and writes through; neither holds the implementation. It links no back end: `cargo tree -p curios-verdicts --edges normal` contains neither `curios-binaryen` nor `curios-native`, and the one machine-dependent fact a payload address carries, the engine that will run it, is handed in by the crate that owns the runtime.

**Rationale.** `Cache` in `curios-package` would make the crate answering what is in a compilation depend on the driver that folds stages over the answer; in `curios-pipeline` it would make the pure fold name a manifest. The `wonder` engine reads verdicts for every question it answers and links neither Binaryen nor Wasmtime, and a store read has no use for either. `curios-package` depends on `curios-text` and so links the surface language, its lowering and `curios-core`; the dependency this boundary keeps out is the driver's.

**Rejected.** The implementation in `curios`, handing the `wonder` engine a `dyn Cache`, whose trait cannot keep a unit without filing it; computing the engine fingerprint here behind a feature, which unifies across a workspace build and puts Cranelift under every consumer.

### A disagreeing slot is a baseline, for a question and for a build

**Decision.** `Verdicts::earlier` hands back a slot's unit when the slot is intact and read from files the asking source could have read, whatever those files and the units before it hold now, and says which units of the fold contain what the slot's record names them by (`curios_pipeline::After`). The store's own `Cache` offers the fold the nearest earlier compilation of a unit as its baseline — what an attached session last had in hand for it, then that slot, then the same two of the unit compiled for the other kind, built or tested (`curios_text::UnitSource::other`), then what the scope offered — and the `wonder` engine's cache asks it for the same answer, so `run`, `compile` and `test` compile a moved unit over its baseline as a question does, and file it. What a question compiled over a baseline it files as it files what it compiled whole: it asks `Verdicts::taken_on_disk`, and files where the disk holds every text its fold has read.

**Rationale.** A unit compiled over a baseline is stored as the index a whole compile of the same text stores, naming the same objects ([A stored unit is a baseline for an item-level recompile](../documentation/design/compilation/a-stored-unit-is-a-baseline-for-an-item-level-recompile.md)), so the slot is the one a whole compile would have written whichever command wrote it, and the next baseline is no further from a whole compile than the last. No verdict a build files rests on what the elaborator kept: which of a baseline's verdicts stand is the certifier's decision, from the reads its own walk filed ([Cached verdicts](../documentation/design/soundness/cached-verdicts.md)). A baseline is offered whatever moved before it, since what a declaration read of another unit is asked again by the stage that read it, by the digest it recorded, wherever that unit is not the one the record names.

**Rejected.** A build compiling a moved unit whole, which pays for every declaration of the unit where a question pays for what moved, to store the same index; withholding what a question compiled over a baseline, which leaves every question after a saved edit recompiling what moved until a build files the unit.

### An entry's unit is filed by the executable it is, and a handle with no store keeps for its session

**Decision.** A handle is told which executable the entry its fold ends in is (`Verdicts::executing`), and files the unit of that entry's own declarations under `curios_package::entry_slot`: the compiler, the package's name and the executable's, and what it declared. A handle told of none files no entry's unit. A handle with no store behind it (`Verdicts::kept_by`) reads and files nothing, and keeps in its session what its fold compiles, each unit told from another by the prefixes it claims and where it reads from.

**Rationale.** Every entry claims the empty prefix, so a unit's address would file every program of a project in one place, each overwriting the last. What tells two entries apart is what tells their payloads apart, the one identity in a compilation that cannot collide. A file no package declares has no project, hence nowhere to file a unit, and a session asking about it at every keystroke still has the last unit it compiled of it: a kept unit is believed on what a recompile over it asks again, which needs no store ([Cached verdicts](../documentation/design/soundness/cached-verdicts.md)).

**Rejected.** The entry's path as its identity, which keys a unit on where a project sits and not on what it builds. A store beside a loose file, a generated directory nobody pointed the compiler at.

### A slot's objects are kept in packs beside it, at its address

**Decision.** A unit's slot holds its record and its index, and the objects the index names are kept in packs under the slot's address (`curios_package::Store::objects`): each pack a file named by the digest of its bytes, closing on a sorted table of the digests it holds (`curios_unit::Pack`). A filing writes the objects its address lacks, as the packs' tables say, in one pack, then the slot, renamed into place, so a slot never names an object not yet written. A pack is held to its name the first time an object of it is read, which vouches for every object it holds, and one that is not its name is damaged and taken away, so what only it held is written again by the next filing that names it. The filing that writes a pack merges the smallest packs of the address into one, wherever each no longer holds at least twice the objects of the one before it, the runs of each kind run again into one ([A compile costs what it reads](../documentation/design/compilation/a-compile-costs-what-it-reads.md), the sixth bound).

**Rationale.** A slot's address names no unit before it, so it is a unit's address through every edit, and a unit's baseline is its own address's slot, its other kind's, the unit a session holds, or the prelude's image: what a slot names is in its address's packs once a filing there wrote what the image held, and no lookup asks across addresses, where a table of every pack in the store, git's multi-pack index or restic's index files, would be one file every filer of a shared store writes. Packs are written once and named by what they hold, as restic's are ([restic's design](https://restic.readthedocs.io/en/latest/design.html)), so two filers writing the same objects write the same pack, and a merge never rewrites a slot. Which objects a pack holds is read off its end, so a filing reads no pack whole to know what it lacks, and a compile finds the candidates filed for what a declaration was lowered to by the prefix their names share, read out of each pack whose table names one (`curios_utilities::Candidates`).

**Rejected.** An index naming the pack each object is in, which makes what a unit stores follow the order it was filed in. One directory of packs for the store, which every filer of a shared store lists and every restore probes. Merging at collection alone, which leaves a day of saves in hundreds of packs; merging every pack into one past a count, as git's `gc.autoPackLimit` does ([`gc.txt`](https://code.googlesource.com/git/+/v2.20.0/Documentation/config/gc.txt)), which writes the whole unit again.

### What no slot names is collected five days after a collection first finds it so

**Decision.** A filing collects its address where a day has passed since the last collection: an object the slot it just wrote does not name is noted with the time a collection first found it so, one named again is forgotten, and one unnamed for five days is dropped from its pack (`Packs::collect`). A read writes nothing.

**Rationale.** Go's build cache keeps a time for each file and renews it on a read at most once an hour, trimming what went unused for five days ([`cache.go`](https://go.dev/src/cmd/go/internal/cache/cache.go)). A pack holds many objects, and the packs holding a live unit are read by every restore of it, so a time renewed by reads would keep each dead object beside the live ones for as long as the unit is used; git keeps a time for each unreachable object of a cruft pack for the same reason ([`gitformat-pack`](https://git-scm.com/docs/gitformat-pack#_cruft_packs)). A filer that found an object present as a collection beside it drops it names an object no pack holds, which is a miss and never a belief.

**Rejected.** A pack's written time as its objects', which drops what a second checkout sharing the store still names every five days. A time renewed by reads, which never collects a dead object of a unit in use.
